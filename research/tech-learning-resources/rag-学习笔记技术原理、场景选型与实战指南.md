# RAG 学习笔记：技术原理、场景选型与实战指南

### 一、核心技术方案速览

在大模型应用开发中，主要有以下几类技术方案，它们不是互斥的，而是经常组合使用：

| 技术方案 | 核心逻辑 | 一句话定位 |
| --- | --- | --- |
| RAG（检索增强生成） | 从外部知识库检索相关内容，喂给大模型生成答案 | 让模型"查资料"再回答 |
| 推荐系统（协同过滤/生成式推荐） | 从用户历史行为中学习偏好，预测用户感兴趣的内容 | 让模型"猜喜好"再推荐 |
| Agent（智能体） | 大模型自主规划任务，调用工具/API 完成多步骤目标 | 让模型"自己想办法"完成任务 |
| Fine-tuning（微调） | 用特定领域数据重新训练模型，让模型内化专业知识 | 让模型"变成专家" |
| Prompt Engineering | 通过精心设计的提示词控制模型输出 | 让模型"听懂指令" |
| Function Calling / Tool Use | 大模型调用外部函数或 API 获取实时数据 | 让模型"使用工具" |

---

### 二、核心判断框架：选型前先问这三个问题

**问题1：用户的需求靠"查知识"满足，还是靠"理解偏好"满足？**

- 查知识（政策、文档、FAQ）→ 优先考虑 RAG
- 理解偏好（推荐什么吃、买什么）→ 优先考虑推荐系统

**问题2：所需数据是静态的，还是实时动态的？**

- 静态（规章制度、产品手册）→ 可以向量化存入知识库，适合 RAG
- 实时动态（库存、订单、价格）→ 需要 API 调用，适合 Agent + Function Calling

**问题3：任务是单步的，还是需要多步规划？**

- 单步（回答一个问题）→ RAG 或直接 LLM 调用
- 多步（订餐 → 查优惠 → 下单 → 确认）→ 需要 Agent

### 三、按业务场景的技术选型

#### 场景一：企业内部知识库问答

**典型需求**：员工问 HR 政策、IT 操作手册、合规规定

**推荐方案**：RAG（标准向量检索）

**技术组合**：文档解析 → 文本切分（Chunking）→ Embedding 向量化 → 向量数据库存储 → 向量检索召回 → 大模型生成答案

**关键设计点**：

- Chunk 策略：按段落切分，保留标题上下文，避免语义断裂
- 元数据：记录文档版本、更新时间，支持过滤过期内容
- 知识库更新机制：文档变更时自动触发重新向量化

**参考项目**：infiniflow/ragflow、datawhalechina/all-in-rag

---

#### 场景二：智能客服（电商/本地生活）

**典型需求**：回答商品咨询、退换货政策、订单状态查询

**推荐方案**：RAG + Agent + Function Calling 混合架构

**知识库分层设计**（来自美团电商实践）：

- 静态知识库：平台规则、商品知识、FAQ → 向量数据库，周更新
- 准实时知识库：促销活动、库存状态 → Elasticsearch，小时级更新
- 实时数据接口：订单状态、物流信息 → 直接 API 调用，实时

**关键设计点**：

- 混合检索：向量检索 + 关键词检索（BM25），解决精确匹配问题
- 查询改写（Query Rewrite）：将口语化问题转为检索友好的标准表达
- 重排序（Rerank）：对召回结果二次排序，提升相关性（实测从 74% → 89%）
- 降级方案：知识库故障时回退到规则引擎

---

#### 场景三：个性化推荐（吃什么、买什么、看什么）

**推荐方案**：推荐系统（协同过滤 / 生成式推荐），不是 RAG

**为什么不用 RAG**：推荐数据是行为数据（点击、购买、停留时长），不是文档知识；核心是"理解偏好"，不是"检索知识"。

**RAG 在推荐场景的辅助作用**：生成推荐理由时，用 RAG 从评价数据中检索支撑内容。

**参考案例**：美团 MTGR，外卖首页订单量 +1.22%

---

#### 场景四：复杂任务自动化（AI Agent）

**典型需求**：帮我订一家周五晚上适合商务宴请的餐厅、帮我规划一次周末旅行

**推荐方案**：Multi-Agent 架构

**适合 Agent 的判断标准**：任务需要 2 步以上的规划；需要调用多个外部系统；中间步骤的结果会影响后续决策。

**关键设计点**：工具定义要精确（工具描述不清是 Agent 选错工具的主要原因）；状态管理要持久化；涉及支付等敏感操作需要人工介入节点。

**参考案例**：美团"小美" App，LangGraph Agentic RAG

---

#### 场景五：专业领域问答（法律、医疗、金融）

**推荐方案**：RAG + 领域微调（Fine-tuning）组合

**为什么需要微调**：通用模型对专业术语理解不准确；专业领域的幻觉风险代价更大。

**特殊考虑**：

- 金融场景：数字精确性要求极高，表格解析能力是关键瓶颈
- 法律场景：条文之间有引用关系，GraphRAG 比普通向量检索更适合
- 医疗场景：需要结合最新诊疗指南，知识库更新频率要求高

---

#### 场景六：文档处理与内容生成

**选型判断**：

- 文档总量 < 模型上下文窗口（如 128K tokens）→ 直接用长上下文 LLM，简单效果好
- 文档总量 > 模型上下文窗口，或文档数量很多 → 用 RAG

---

#### 场景七：代码库问答与开发辅助

**推荐方案**：代码专用 RAG（Code RAG）

**与普通 RAG 的区别**：按函数/类/模块切分（不是按字符数）；需要代码专用 Embedding（如 CodeBERT）；结合 AST（抽象语法树）做代码结构理解。

### 四、技术组合的常见模式

| 模式 | 适用场景 | 代表工具 |
| --- | --- | --- |
| 纯 RAG | 静态知识库问答、FAQ 机器人 | LlamaIndex、LangChain |
| RAG + Rerank | 对答案准确性要求较高 | BGE-Reranker |
| Agentic RAG | 需要多轮检索、自适应查询 | LangGraph、AutoGen |
| RAG + Agent + Function Calling | 复杂业务场景 | 电商智能客服 |
| GraphRAG | 需要跨实体推理、关系分析 | microsoft/graphrag、LightRAG |

### 五、RAG 的核心失败场景（PM 必知）

| 失败类型 | 具体表现 | 根本原因 | 解决方向 |
| --- | --- | --- | --- |
| 检索失败 | 找到的内容和问题不相关 | 问题表述与文档表述差异大 | Query Rewrite、混合检索 |
| 知识边界模糊 | 知识库没有答案，但模型仍然"编"了一个 | 模型不知道自己不知道 | 相似度阈值过滤、Prompt 约束 |
| 多跳推理失败 | 答案需要拼接多个文档的信息 | 单次检索只能召回局部信息 | GraphRAG、多轮检索 |
| 时效性问题 | 回答了已经过期的政策 | 知识库未及时更新 | 元数据过滤、自动同步机制 |
| 文档解析失败 | 表格、图片中的信息丢失 | 文档解析能力不足 | 专用解析引擎（如 RAGFlow 的 DeepDoc） |
| 长文档截断 | 答案在文档末尾，被 Chunk 切断 | Chunk 策略不合理 | 滑动窗口、语义切分 |
| 精确匹配失败 | 订单号、SKU 等精确信息检索不到 | 向量检索不擅长精确匹配 | 混合检索（向量 + BM25） |

### 六、模型微调（Fine-tuning）适用场景

#### 三类真正需要微调的场景

**第一类：风格和格式的强约束**：需要模型输出严格符合某种固定格式，Prompt 控制不住。比如必须输出标准 JSON、或者永远用某种特定语气回复用户。

**第二类：大量专业术语和领域知识的内化**：通用模型对垂直领域专业术语理解很差，RAG 也帮不上忙（问题不是"缺少知识"，而是"模型根本不理解这个词"）。

**第三类：推理延迟和成本极度敏感**：需要小模型（7B）在特定任务上达到大模型效果，通过微调"以小博大"。

#### 奶茶店收银员比喻

- **RAG**：给收银员一本产品手册，顾客问什么翻手册找答案，手册随时可以更新。
- **微调**：让收银员参加三个月专项培训，把所有知识背进脑子里，张口就来，完全符合品牌调性。

选培训（微调）的时机：品牌有严格话术规范、有大量行业黑话、有 1000 家门店需要复制。  
不选培训的时机：菜单每周都在变（知识过期快）、只有一家店（成本高于收益）。

#### 微调的判断流程

1. 先试 Prompt Engineering → 效果够用？停。
2. 加上 RAG → 效果够用？停。
3. 分析问题根源：是"缺少知识"→ 继续优化 RAG；是"格式/风格不对"或"术语不理解"→ 考虑微调。
4. 评估 ROI：数据准备成本 + 训练成本 + 维护成本 vs 业务收益。

**核心结论**：微调解决"模型不够聪明"或"模型说话方式不对"的问题，RAG 解决"模型不知道"的问题。大多数业务问题属于后者。

### 七、RAG 系统评估体系

**检索质量**：召回率（Recall）、精确率（Precision）、MRR（Mean Reciprocal Rank）

**生成质量**：

- 答案忠实度（Faithfulness）：答案是否真的来自检索内容，而非模型编造
- 答案相关性（Answer Relevance）：答案是否回答了用户的问题
- 上下文相关性（Context Relevance）：检索到的内容是否和问题相关

**业务效果**：自动解决率、用户满意度、响应时延

推荐评估框架：RAGAS（[https://github.com/explodinggradients/ragas）](https://github.com/explodinggradients/ragas%EF%BC%89)

### 九、美团真实案例：推荐系统 vs RAG 的边界

**美团"小美" AI Agent**（2025年9月上线）：搭载自研大模型 LongCat-Flash-Chat，采用"一个总调度 + 多个执行专家"的 Multi-Agent 架构。"推荐餐厅"这类场景用的是直接 API 调用，不是 RAG。

**美团 MTGR**（外卖推荐系统）：用类 LLM 的 HSTU 架构，把用户历史行为序列当 Token 建模，外卖首页订单量 +1.22%。这是推荐系统，不是 RAG。

**RAG 在美团的实际用途**：生成 POI 推荐理由（从评价数据检索支撑内容）、客服知识库问答、商家运营支持等静态知识场景。

**核心认知**：RAG 适合知识密集型场景，推荐系统适合行为密集型场景。判断标准：用户需求主要靠"查知识"满足，还是靠"理解偏好"满足？

### 十、面试级判断框架：RAG vs 提示词工程 vs 微调

#### 10.1 先建立基本认知：三者不是竞争关系

很多人面试时容易犯的错误是把三者对立起来，其实它们是不同层次的工具。

提示词工程是最轻量的控制手段，成本几乎为零，应该永远是第一个尝试的方案。RAG 解决的是"模型不知道某些知识"的问题，本质是给模型一个外挂的记忆系统。微调解决的是"模型的行为模式不符合要求"的问题，本质是改变模型本身。

一个成熟的系统往往是三者叠加的：先用提示词工程定义行为规范，再用 RAG 补充领域知识，最后在特定场景下用微调固化能力。

**核心金句**：提示词工程是调整模型的"行为"，RAG 是扩展模型的"知识"，微调是改变模型的"能力"。

---

#### 10.2 提示词工程：什么时候用，什么时候不够用

**适合用提示词工程的场景：**

- 输出格式控制：比如"永远用 JSON 格式回答"、"回答不超过 100 字"
- 角色设定：比如"你是一个严谨的法律助手，不要给出具体建议"
- 行为约束：比如"如果不确定，就说不知道，不要猜测"
- 任务分解：Chain-of-Thought 提示让模型一步步推理

**提示词工程不够用的信号：**

- 你在 Prompt 里塞了大量背景知识（比如把整个产品手册都写进去了）→ 应该换 RAG
- 模型的"性格"或"风格"怎么调都不对（比如客服机器人总是太生硬）→ 应该考虑微调
- 同一个 Prompt 在不同问题上效果极不稳定 → 说明模型本身的能力边界到了

---

#### 10.3 RAG：四个核心判断标准

**用 RAG 的核心判断标准（四个问题）：**

**问题一：知识是否在模型训练数据之外？** 公司内部文档、最新政策、私有数据库，这些模型天然不知道，必须用 RAG。

**问题二：知识是否会频繁更新？** 如果知识每天都在变（比如商品价格、政策法规），微调根本跟不上，RAG 可以做到小时级甚至分钟级更新。

**问题三：知识量是否超过上下文窗口？** 如果你有 10 万份文档，不可能全塞进 Prompt，RAG 的检索机制可以按需取用。

**问题四：是否需要溯源和可解释性？** 金融、医疗、法律场景要求"你的答案来自哪里"，RAG 天然支持引用来源，微调做不到这一点。

**RAG 不适合的场景（面试中很容易被追问）：**

- 实时数据场景（查当前股价、查订单状态）→ 数据无法预先向量化，应该用 Function Calling 直接调 API
- 纯推理场景（解数学题、写代码）→ 不需要外部知识，RAG 反而会引入噪音
- 知识高度结构化且关系复杂的场景（法律条文引用关系）→ 普通向量检索会丢失关系信息，应该用 GraphRAG

---

#### 10.4 微调：最容易被滥用的技术

**微调的本质**：用特定数据改变模型的权重，让模型在某类任务上的"默认行为"发生改变。它解决的不是"知识不够"的问题，而是"行为模式不对"的问题。

**真正适合微调的五类场景：**

**场景一：输出格式高度定制化。** 需要模型输出特定的 JSON Schema，或按照公司内部报告模板格式输出。提示词工程可以做到，但不稳定；微调之后格式遵从率可以从 70% 提升到 99%。

**场景二：专业术语和领域语言内化。** 医疗场景中，模型需要准确理解"适应症"、"禁忌症"、"不良反应"的细微差别；通用模型理解不准确，微调可以让模型真正"懂行"。

**场景三：特定风格和语气固化。** 品牌客服要求所有回复都有特定的语气和措辞风格；提示词工程每次都要重复描述，微调之后模型天然就是这个风格。

**场景四：推理模式迁移。** 有大量高质量的专家推理过程（医生的诊断思路、律师的分析框架），想让模型学会这种推理方式，这是微调最擅长的。

**场景五：降低推理成本。** 一个大模型通过微调可以在特定任务上达到更大模型的效果，从而用更小的模型服务更多请求，这是工业界微调的重要动机之一。

**微调不适合的场景：**

- 知识时效性要求高的场景 → 微调的知识是静态的，训练完就固化了，无法实时更新
- 数据量不足的场景 → 微调需要高质量标注数据，通常至少几百到几千条，数据不够反而会让模型退化
- 问题可以用 Prompt 解决的场景 → 微调成本高、周期长，能用 Prompt 解决就不要微调

---

#### 10.5 决策流程：面试中展示系统性思维的关键

遇到一个新场景，按以下顺序思考：

```
// 代码块
第一步：先试 Prompt Engineering
  → 如果效果达标，就此打住，不要过度工程化

第二步：如果 Prompt 不够，分析根本原因
  → 是"模型不知道某些知识"？→ 上 RAG
  → 是"模型的行为模式不对"？→ 考虑微调
  → 是"需要实时数据"？→ Function Calling
  → 是"需要多步骤规划"？→ Agent

第三步：如果 RAG 效果不好，再分析
  → 检索质量差？→ 优化 Chunking、换 Embedding 模型、加 Rerank
  → 生成质量差？→ 优化 Prompt、加 Few-shot 示例
  → 专业术语理解差？→ RAG + 领域微调组合

第四步：微调是最后的手段，上之前要问
  → 有没有足够的高质量训练数据？
  → 有没有评估基准来衡量微调效果？
  → 维护成本是否可接受（模型版本管理、重新训练周期）？
```

#### 10.6 面试场景示例：律师事务所合同审查助手

**面试官问**："假设你要为一家律师事务所做一个合同审查助手，你会怎么选型？"

**回答思路：**

合同审查的核心需求是理解合同条款、识别风险点、对比标准条款。这里有两类知识：一类是通用法律知识（模型已有），一类是公司内部的合同模板和历史案例（模型没有）。

对于内部知识，用 RAG 建立合同知识库，把历史合同、标准条款、风险案例向量化存储。由于法律条文之间有大量引用关系，普通向量检索会丢失这些关系，所以考虑用 GraphRAG 而不是普通 RAG。

对于输出格式，律师需要结构化的风险报告，格式非常固定，这里可以用微调来固化输出格式，也可以用 Few-shot Prompt 先验证效果。

对于实时数据，如果需要查最新的司法解释或判例，需要接入法律数据库 API，用 Function Calling 实现。

最后，整个系统的评估要关注答案忠实度（不能编造法律条文）和引用溯源（每个结论必须标注来源），这是法律场景的硬性要求。
