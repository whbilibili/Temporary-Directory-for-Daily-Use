## 第一层：基础概念题

### Q1：什么是 Graph RAG？它和传统 RAG 的核心区别是什么？

**参考答案：**

传统 RAG（Retrieval-Augmented Generation）的检索单元是文本块（chunk），通过向量相似度找到最相关的若干段落后拼接给 LLM。它的本质是"局部语义匹配"，对跨文档、跨段落的关联关系无能为力。

Graph RAG 在此基础上引入了知识图谱层。核心流程分为两阶段：

**索引阶段**：对原始文档做实体抽取（Entity Extraction）和关系抽取（Relation Extraction），构建一张以实体为节点、关系为边的知识图谱；再对图做社区检测（Community Detection），将关联紧密的实体聚合成社区，并为每个社区生成摘要（Community Summary）。

**检索阶段**：提供两种互补的检索路径：
- **Local Search**：从查询实体出发，沿图的邻居关系做 K 跳游走，适合"某个具体实体的详细信息"类问题。
- **Global Search**：汇总所有社区摘要，做 Map-Reduce 式全局推理，适合"整个语料库的宏观趋势"类问题。

核心区别在于：传统 RAG 检索的是"相似文本片段"，Graph RAG 检索的是"结构化知识子图"，后者天然支持多跳推理和全局摘要。

---

### Q2：Graph RAG 适合哪些场景？哪些场景不适合？

**参考答案：**

**适合的场景：**
- 多跳推理：如"A 公司的 CEO 毕业于哪所大学？"需要跨越多个实体关系。
- 全局摘要：如"这批财报中，哪些风险因素被反复提及？"需要跨文档聚合。
- 关系探索：如知识图谱问答、供应链分析、医疗知识库。
- 长文档理解：文档内部实体关系复杂，向量检索容易丢失结构信息。

**不适合的场景：**
- 简单事实查询：如"XX 产品的价格是多少？"传统 RAG 已足够，Graph RAG 引入了不必要的开销。
- 实时性要求极高：图的构建和社区检测是离线批处理，无法做到秒级更新。
- 语料库极小：图结构的优势在大规模、高密度关联的语料上才能体现。
- 非结构化程度极高：如纯图片、音频，无法直接抽取实体关系。

### Q3：什么是社区检测？Leiden 算法相比 Louvain 有什么改进？

**参考答案：**

社区检测（Community Detection）是图分析中将节点划分为若干"社区"的过程，同一社区内的节点连接紧密，不同社区间连接稀疏。在 Graph RAG 中，社区对应一组语义相关的实体集合，社区摘要是 Global Search 的核心检索单元。

**Louvain 算法**的核心思想是贪心优化模块度（Modularity）：先将每个节点视为独立社区，然后反复将节点移入能最大化模块度增益的邻居社区，直到收敛。它速度快，但存在一个已知缺陷：可能产生"内部不连通"的社区（即社区内部存在孤立子图），这在语义上是不合理的。

**Leiden 算法**在 Louvain 基础上增加了一个"精炼（Refinement）"阶段：在每轮社区合并后，对社区内部做子社区分裂，确保每个社区都是内部连通的。这使得 Leiden 产生的社区质量更高、更稳定，且理论上保证收敛到更优解。

在 Graph RAG 的实现中，Leiden 还支持层级社区（Hierarchical Communities），不同层级对应不同粒度的摘要，检索时可按需选择层级。

---

### Q4：Graph RAG 中的 Local Search 和 Global Search 分别是什么？如何选择？

**参考答案：**

**Local Search（局部搜索）**：
- 流程：将查询向量化 → 在实体嵌入空间中找到最相关的种子实体 → 从种子实体出发做 K 跳图游走，收集邻居实体、关系、关联文本块 → 拼接上下文给 LLM。
- 特点：上下文精准、token 消耗少、延迟低。
- 适用：针对特定实体的具体问题，如"张三的工作经历是什么？"

**Global Search（全局搜索）**：
- 流程：加载所有社区摘要 → 并行调用 LLM 对每个社区摘要生成局部答案（Map 阶段）→ 汇总所有局部答案生成最终回答（Reduce 阶段）。
- 特点：覆盖全局、支持宏观推理，但 token 消耗大、延迟高。
- 适用：需要跨文档聚合的宏观问题，如"这批文档中最常见的主题是什么？"

**选择策略**：实际系统中通常做查询意图分类，将问题路由到对应路径；也可以做 Hybrid Search，先 Local 再 Global，用 RRF（Reciprocal Rank Fusion）融合两路结果。

## 第二层：核心算法题

### Q5：实体抽取和关系抽取的工程实现方案有哪些？各有什么优缺点？

**参考答案：**

**方案一：基于 LLM 的 Prompt 抽取（主流方案）**

直接用 LLM（如 GPT-4、Claude）通过 Prompt 抽取实体和关系，输出结构化 JSON。

优点：无需标注数据、泛化能力强、可处理复杂语义。
缺点：成本高（每个 chunk 都要调用 LLM）、速度慢、输出格式不稳定需要后处理。

工程优化：使用 Gleaning 机制——第一轮抽取后，让 LLM 检查是否有遗漏，进行补充抽取，通常做 1-2 轮即可显著提升召回率。

**方案二：基于 NLP 工具的传统方案**

使用 spaCy、Stanford NLP、HanLP 等工具做 NER（命名实体识别）和关系抽取。

优点：速度快、成本低、可离线运行。
缺点：依赖预训练模型，对领域特定实体（如医疗、法律）效果差，关系抽取能力弱。

**方案三：Fine-tuned 小模型**

在领域数据上微调 BERT/RoBERTa 等模型做 NER 和关系分类。

优点：在特定领域精度高、推理速度快。
缺点：需要标注数据、维护成本高、泛化能力弱。

**实际工程选择**：通用场景用 LLM Prompt 方案；高频、大规模场景用小模型做粗筛 + LLM 做精抽取的两阶段流水线。

### Q6：什么是实体链接（Entity Linking）？为什么在 Graph RAG 中很重要？

**参考答案：**

实体链接（Entity Linking，也叫实体消歧）是将文本中提到的实体指称（mention）映射到知识库中唯一实体的过程。例如，"苹果公司"、"Apple Inc."、"AAPL" 应该被识别为同一个实体节点。

**在 Graph RAG 中的重要性：**

如果不做实体链接，同一个实体会以多种形式出现在图中，导致：
1. 图结构碎片化：本应连通的节点变成孤立节点，多跳推理断链。
2. 社区质量下降：相关实体被分散到不同社区，摘要质量变差。
3. 检索召回率低：查询"Apple"时找不到"苹果公司"相关的节点。

**工程实现方案：**

```python
# 基于嵌入相似度的实体链接
def entity_linking(mention: str, entity_index: dict, threshold: float = 0.85):
    mention_emb = embed(mention)
    candidates = []
    for entity_id, entity_emb in entity_index.items():
        sim = cosine_similarity(mention_emb, entity_emb)
        if sim > threshold:
            candidates.append((entity_id, sim))
    if candidates:
        # 返回相似度最高的实体
        return max(candidates, key=lambda x: x[1])[0]
    else:
        # 创建新实体
        return create_new_entity(mention)
```

实际系统中还会结合上下文信息（mention 周围的文本）做更精准的消歧。

### Q7：图嵌入（Graph Embedding）在 Graph RAG 中有什么作用？Node2Vec 和 GraphSAGE 的区别是什么？

**参考答案：**

图嵌入将图中的节点（实体）映射为低维稠密向量，使得图结构信息可以被向量检索系统利用。在 Graph RAG 中，图嵌入主要用于：
1. 实体检索：将查询向量与实体嵌入做相似度匹配，找到种子实体。
2. 实体链接：通过嵌入相似度判断两个实体指称是否指向同一实体。
3. 社区初始化：为社区检测算法提供更好的初始划分。

**Node2Vec**：
- 原理：通过随机游走（Random Walk）在图上采样节点序列，然后用 Word2Vec 的 Skip-Gram 模型训练节点嵌入。
- 特点：通过调整游走策略（BFS vs DFS 偏向），可以捕获同质性（homophily）或结构等价性（structural equivalence）。
- 缺点：Transductive，无法处理训练时未见过的新节点（冷启动问题）。

**GraphSAGE**：
- 原理：通过聚合邻居节点的特征来生成节点嵌入（Inductive Learning）。
- 特点：Inductive，可以为新节点生成嵌入，只需要节点的特征和邻居关系。
- 缺点：需要节点有初始特征，纯结构图（无节点特征）效果不如 Node2Vec。

**在 Graph RAG 中的选择**：如果图是静态的，Node2Vec 更简单高效；如果图需要动态更新（频繁新增实体），GraphSAGE 更合适。

### Q8：RRF（Reciprocal Rank Fusion）是什么？在 Graph RAG 的混合检索中如何应用？

**参考答案：**

RRF（Reciprocal Rank Fusion，倒数排名融合）是一种无参数的多路检索结果融合算法。对于每个文档，其 RRF 分数为：

```
RRF_score(d) = sum(1 / (k + rank_i(d)))
```

其中 `rank_i(d)` 是文档 d 在第 i 路检索结果中的排名，`k` 是平滑常数（通常取 60）。

**在 Graph RAG 混合检索中的应用：**

Graph RAG 通常有三路检索结果需要融合：
1. **向量检索**：基于文本块嵌入的语义相似度排名。
2. **图检索（Local Search）**：基于图游走的实体关联度排名。
3. **关键词检索（BM25）**：基于词频的精确匹配排名。

```python
def rrf_fusion(results_list: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    scores = {}
    for results in results_list:
        for rank, doc_id in enumerate(results, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

# 使用示例
vector_results = ["doc_3", "doc_1", "doc_5"]
graph_results  = ["doc_1", "doc_4", "doc_3"]
bm25_results   = ["doc_2", "doc_1", "doc_3"]

final_ranking = rrf_fusion([vector_results, graph_results, bm25_results])
```

RRF 的优势在于不需要对不同检索路径的分数做归一化，鲁棒性强，在实践中效果通常优于简单加权融合。

## 第三层：工程实践题

### Q9：Graph RAG 的完整索引流水线是什么？每个阶段的工程挑战是什么？

**参考答案：**

完整索引流水线分为六个阶段：

**阶段一：文档加载与切分**
- 工程挑战：切分粒度影响实体抽取质量。chunk 太小，实体关系跨 chunk 丢失；chunk 太大，LLM 上下文窗口不够。
- 实践：通常用 512-1024 token 的 chunk，并保留 10-20% 的重叠（overlap）。

**阶段二：实体与关系抽取**
- 工程挑战：LLM 调用成本高，大规模语料需要并发控制和断点续传。
- 实践：使用异步并发（asyncio + semaphore 限流）+ 结果缓存（已处理的 chunk 跳过）。

**阶段三：实体链接与去重**
- 工程挑战：同一实体的多种表述需要合并，但过度合并会导致信息丢失。
- 实践：基于嵌入相似度 + 规则（如字符串归一化）的两阶段去重。

**阶段四：图构建**
- 工程挑战：大规模图的内存占用和构建速度。
- 实践：使用 NetworkX 做原型，生产环境迁移到 Neo4j 或 TigerGraph。

**阶段五：社区检测**
- 工程挑战：Leiden 算法在超大图（百万节点）上耗时较长。
- 实践：使用 graspologic 库的并行实现，或对图做分层采样后再检测。

**阶段六：社区摘要生成**
- 工程挑战：每个社区都需要调用 LLM 生成摘要，成本和时间是瓶颈。
- 实践：按社区大小排序，优先处理大社区；小社区（节点数 < 3）可跳过或用模板生成。

### Q10：如何设计 Graph RAG 的存储架构？各组件分别存什么？

**参考答案：**

生产级 Graph RAG 通常采用多存储协同架构：

| 存储组件 | 存储内容 | 选型示例 |
|---------|---------|---------|
| 图数据库 | 实体节点、关系边、图结构 | Neo4j、TigerGraph、Amazon Neptune |
| 向量数据库 | 实体嵌入、文本块嵌入、社区摘要嵌入 | Qdrant、Weaviate、Pinecone |
| 关系数据库 | 文档元数据、实体属性、社区元数据 | PostgreSQL、MySQL |
| 缓存层 | 热点查询结果、社区摘要 | Redis |
| 对象存储 | 原始文档、Parquet 格式的图快照 | S3、OSS |

**关键设计决策：**

1. **实体嵌入存在哪里？** 同时存图数据库（作为节点属性，用于图算法）和向量数据库（用于 ANN 检索），两者通过实体 ID 关联。

2. **社区摘要存在哪里？** 文本存关系数据库，嵌入存向量数据库，通过 community_id 关联。

3. **如何保证一致性？** 索引更新时，图数据库、向量数据库、关系数据库需要事务性更新。实践中通常用消息队列（Kafka）做异步同步，接受最终一致性。

### Q11：Graph RAG 的检索延迟如何优化？有哪些工程手段？

**参考答案：**

**问题分析：** Graph RAG 的延迟主要来自三个环节：
1. 图游走（K 跳查询）：图数据库查询延迟。
2. LLM 调用：生成最终答案的推理延迟。
3. 上下文拼接：大量检索结果的处理延迟。

**优化手段：**

**1. 图查询优化**
- 为高频查询的实体属性建立索引（Neo4j 的 Index）。
- 限制游走深度（通常 K=2 已足够，K=3 开始指数级膨胀）。
- 使用子图剪枝：提前过滤低权重边，减少游走节点数。

**2. 缓存策略**
- 社区摘要缓存：摘要是静态的，可以永久缓存在 Redis 中。
- 查询结果缓存：对相似查询（嵌入相似度 > 0.95）直接返回缓存结果。
- 实体嵌入缓存：热点实体的嵌入向量缓存在内存中。

**3. 异步与并行**
- Local Search 和 Global Search 并行执行，最后融合结果。
- Global Search 的 Map 阶段（各社区并行生成局部答案）天然可并行。

**4. 自适应跳数（Adaptive K-hop）**
- 根据查询复杂度动态调整游走深度：简单查询 K=1，复杂多跳查询 K=3。
- 实现：先做 K=1 检索，如果置信度不够再扩展到 K=2。

### Q12：如何评估 Graph RAG 系统的质量？有哪些评估指标？

**参考答案：**

Graph RAG 的评估分为三个层次：

**层次一：组件级评估**

| 组件 | 评估指标 |
|------|---------|
| 实体抽取 | Precision / Recall / F1（与人工标注对比） |
| 关系抽取 | Relation F1 |
| 社区检测 | 模块度（Modularity）、社区内聚度 |
| 检索 | Recall@K、MRR（Mean Reciprocal Rank） |

**层次二：端到端评估**

使用 RAGAS 框架的四个核心指标：
- **Faithfulness（忠实度）**：答案是否有检索内容支撑，不产生幻觉。
- **Answer Relevancy（答案相关性）**：答案是否回答了问题。
- **Context Precision（上下文精确率）**：检索到的内容有多少是有用的。
- **Context Recall（上下文召回率）**：有用的内容有多少被检索到了。

**层次三：与传统 RAG 的对比评估**

在多跳推理数据集（如 HotpotQA、MuSiQue）上对比：
- Graph RAG 在多跳问题上通常比传统 RAG 高 15-30% 的 F1。
- 传统 RAG 在单跳简单问题上延迟更低、成本更低。

## 第四层：系统设计题

### Q13：如果让你从零设计一个生产级 Graph RAG 系统，你会怎么做？

**参考答案（系统设计思路）：**

**第一步：明确需求**
- 语料规模：百万文档 vs 千文档，决定图的规模和存储选型。
- 更新频率：实时更新 vs 批量更新，决定索引架构。
- 查询类型：多跳推理为主 vs 全局摘要为主，决定检索策略。
- 延迟要求：秒级 vs 分钟级，决定缓存和并行策略。

**第二步：整体架构**

```
[文档输入] 
    → [文档处理服务] (切分、清洗)
    → [抽取服务] (实体/关系抽取，LLM 驱动，异步队列)
    → [图构建服务] (实体链接、图更新)
    → [社区检测服务] (Leiden，批处理)
    → [摘要生成服务] (社区摘要，LLM 驱动)
    → [嵌入服务] (实体嵌入、摘要嵌入)

[查询输入]
    → [意图分类] (Local / Global / Hybrid)
    → [Local Search 路径] (实体检索 → 图游走 → 上下文拼接)
    → [Global Search 路径] (社区摘要加载 → Map-Reduce)
    → [RRF 融合]
    → [LLM 生成答案]
```

**第三步：关键技术选型**
- 图数据库：Neo4j（中小规模）或 TigerGraph（大规模）。
- 向量数据库：Qdrant（开源自部署）或 Pinecone（托管）。
- 消息队列：Kafka（解耦索引流水线各阶段）。
- 缓存：Redis（社区摘要、热点查询）。
- 编排：Airflow 或 Prefect（批处理流水线调度）。

**第四步：可观测性**
- 每个阶段记录处理耗时、成功率、错误率。
- 图质量监控：节点数、边数、社区数的趋势变化。
- 检索质量监控：在线 A/B 测试，对比 Graph RAG vs 传统 RAG 的用户满意度。

### Q14：Graph RAG 的增量更新如何实现？有哪些难点？

**参考答案：**

**难点分析：**

Graph RAG 的增量更新比传统 RAG 复杂得多，因为新文档的加入可能影响：
1. 新实体的加入（简单）。
2. 已有实体的属性更新（中等）。
3. 新关系的加入，可能改变图的连通性（复杂）。
4. 社区结构的变化，需要重新检测社区（最复杂）。
5. 社区摘要的更新（依赖社区结构）。

**工程方案：**

**方案一：全量重建（简单但低效）**
- 定期（如每天）对全量语料重新跑索引流水线。
- 适合：语料更新频率低、规模不大的场景。

**方案二：增量图更新 + 局部社区重检测**
- 新文档处理后，只更新受影响的图区域。
- 对发生变化的子图重新运行社区检测。
- 只重新生成变化社区的摘要。
- 难点：如何判断"受影响的子图"范围，避免级联更新。

**方案三：版本化图（Graph Versioning）**
- 为图维护版本号，新文档创建新版本的图。
- 查询时可以指定版本，支持历史回溯。
- 适合：对数据一致性要求高的场景（如法律、金融）。

**实践建议：** 大多数生产系统采用"准实时"策略——新文档先进传统 RAG 索引（秒级），异步触发图更新流水线（分钟到小时级），两套索引并行服务，图索引更新完成后切换。

## 第五层：深度追问题

### Q15：Graph RAG 中的"幻觉"问题比传统 RAG 更严重还是更轻？为什么？

**参考答案：**

这是一个有争议的问题，答案是"取决于幻觉的类型"：

**Graph RAG 能减少的幻觉：**
- **关系幻觉**：传统 RAG 可能错误地将两个实体关联（因为它们在同一文本块中），Graph RAG 通过显式的关系边避免了这类错误。
- **跨文档幻觉**：传统 RAG 在多跳推理时容易"脑补"中间步骤，Graph RAG 通过图路径提供了可验证的推理链。

**Graph RAG 可能引入的新幻觉：**
- **抽取幻觉**：实体抽取和关系抽取本身由 LLM 完成，可能引入错误的实体或关系，这些错误会被固化到图中并影响后续所有查询。
- **摘要幻觉**：社区摘要由 LLM 生成，可能对社区内容做出不准确的概括，且这种错误会被放大（因为摘要是 Global Search 的主要信息来源）。

**工程应对：**
- 对抽取结果做置信度过滤，低置信度的关系不加入图。
- 社区摘要生成时要求 LLM 引用原文，便于溯源验证。
- 在答案生成时，同时提供原始文本块作为 grounding，让 LLM 优先参考原文。

### Q16：如何处理 Graph RAG 中的多语言和跨语言场景？

**参考答案：**

**挑战：**
- 同一实体在不同语言中有不同表述（"北京" vs "Beijing" vs "Pékin"），实体链接更复杂。
- 不同语言的文档可能描述同一事件，需要跨语言关系抽取。
- 社区摘要的语言需要与查询语言匹配。

**工程方案：**

**1. 多语言嵌入模型**
使用支持多语言的嵌入模型（如 multilingual-e5、LaBSE），使不同语言的同义实体在嵌入空间中距离接近，从而支持跨语言实体链接。

**2. 语言标准化**
在图构建阶段，将所有实体名称统一翻译为一种语言（通常是英语）作为规范形式，同时保留原始语言名称作为别名。

**3. 查询时语言路由**
检测查询语言，优先检索同语言的文本块，同时通过实体 ID 关联跨语言内容。

**4. 多语言社区摘要**
为每个社区生成多语言版本的摘要，或在查询时动态翻译。

### Q17：GraphRAG 和 Knowledge Graph QA（KGQA）有什么区别？

**参考答案：**

这是一个很好的辨析题，两者经常被混淆：

**Knowledge Graph QA（KGQA）**：
- 前提：已有一个结构化的知识图谱（如 Wikidata、Freebase）。
- 任务：将自然语言问题转化为图查询语言（SPARQL、Cypher），在图上执行查询得到答案。
- 特点：答案精确、可解释，但依赖高质量的预构建知识图谱，无法处理图谱中没有的知识。

**Graph RAG**：
- 前提：有原始文档语料，知识图谱是从文档中自动抽取构建的。
- 任务：结合图结构检索和 LLM 生成，回答开放域问题。
- 特点：不依赖预构建知识图谱，可以处理任意文档，但答案是生成式的，可能有幻觉。

**联系：** Graph RAG 可以看作是"自动构建知识图谱 + 基于图的 RAG"，而 KGQA 是"使用已有知识图谱做精确查询"。在实际系统中，两者可以结合：用 KGQA 处理可以精确查询的问题，用 Graph RAG 处理需要推理和生成的问题。

### Q18：如果 Graph RAG 的效果不如传统 RAG，你会如何排查？

**参考答案：**

这是一道典型的工程排查题，考察系统性思维：

**排查框架（从数据到模型）：**

**Step 1：确认问题类型**
- 是所有问题都差，还是特定类型的问题差？
- 如果只是简单单跳问题差，可能是 Graph RAG 引入了不必要的复杂度，这是正常的。

**Step 2：检查图质量**
```python
# 图质量诊断
print(f"节点数: {G.number_of_nodes()}")
print(f"边数: {G.number_of_edges()}")
print(f"连通分量数: {nx.number_connected_components(G)}")
print(f"平均度: {sum(dict(G.degree()).values()) / G.number_of_nodes():.2f}")
# 如果连通分量数很多，说明图碎片化严重，实体链接有问题
```

**Step 3：检查实体抽取质量**
- 抽取的实体是否覆盖了查询中的关键实体？
- 关系是否正确？有没有明显错误的关系？

**Step 4：检查检索路径**
- Local Search：种子实体是否找对了？K 跳游走是否覆盖了相关节点？
- Global Search：社区摘要是否包含了回答问题所需的信息？

**Step 5：检查上下文拼接**
- 最终送给 LLM 的上下文是否包含了正确信息？
- 上下文是否太长导致 LLM 注意力分散（Lost in the Middle 问题）？

**常见根因：**
1. 实体链接失败 → 图碎片化 → 多跳推理断链。
2. 社区摘要质量差 → Global Search 效果差。
3. 查询路由错误 → 简单问题走了 Global Search，复杂问题走了 Local Search。
4. chunk 切分不合理 → 实体关系跨 chunk 丢失。

## 附录：高频考点速查

| 考点 | 核心要点 |
|------|---------|
| Graph RAG vs 传统 RAG | 结构化知识 vs 文本片段；多跳推理；全局摘要 |
| Leiden vs Louvain | Leiden 保证社区内部连通；支持层级社区 |
| Local vs Global Search | Local：实体游走，精准低延迟；Global：社区摘要，宏观高成本 |
| 实体链接 | 防止图碎片化；嵌入相似度 + 规则两阶段 |
| Gleaning 机制 | 多轮抽取提升召回率 |
| RRF 融合 | 无参数多路融合；公式 1/(k+rank) |
| 存储架构 | 图DB + 向量DB + 关系DB + Redis 四层协同 |
| 增量更新 | 全量重建 vs 局部社区重检测 vs 版本化图 |
| 幻觉问题 | 减少关系幻觉；引入抽取幻觉和摘要幻觉 |
| 评估指标 | RAGAS 四指标；多跳数据集 HotpotQA |
