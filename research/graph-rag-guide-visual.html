🔑 Graph RAG 的核心思路

Graph RAG = 知识图谱 + RAG。在传统 RAG 的"切片→嵌入→检索→生成"流程中，引入知识图谱作为中间层，将非结构化文本转化为结构化的实体-关系网络，从而实现：

  • 多跳推理：沿着关系链路回答需要多步推理的问题
  • 全局视角：通过社区摘要提供宏观概览
  • 精确事实：实体属性提供确定性答案
  • 可解释性：答案可溯源到具体实体和关系
📌 一句话定义 Graph RAG 是一种将文档先转化为知识图谱，再基于图结构进行检索和推理的 RAG 范式。它不是替代传统 RAG，而是在传统 RAG 基础上增加了结构化理解能力。

🧩 核心概念

理解 Graph RAG 的基础构件

🔵 实体 (Entity)

知识图谱中的节点，代表现实世界中的对象。每个实体有名称、类型、描述和属性。

人物组织技术概念

🔗 关系 (Relation)

连接两个实体的有向边，描述实体间的语义联系。包含关系类型、权重和描述。

负责使用属于依赖

🏘️ 社区 (Community)

通过图聚类算法（如 Leiden）将紧密关联的实体分组。每个社区有层级摘要，支持不同粒度的查询。

📄 文本单元 (Text Unit)

原始文档的切片，是实体和关系的来源依据。每个实体/关系都记录了对应的 text_unit_ids，支持答案溯源。

🏗️ 知识图谱的层级结构

原始文档 → 文本单元 → 实体 + 关系 → 社区层级 → 社区摘要

⚙️ 完整流程

Graph RAG 的两大阶段：索引构建 & 查询检索

1

文档切片 (Chunking)

将原始文档按 token 数切分为重叠的文本单元，典型配置：chunk_size=1200, overlap=100

2

实体关系抽取 (Entity & Relation Extraction)

用 LLM 从每个 chunk 中抽取实体和关系三元组，支持多轮 gleanings 提升召回率

3

实体消歧与合并 (Entity Resolution)

处理同一实体的不同表述（别名、缩写），合并为统一节点

4

图构建 (Graph Construction)

将抽取结果构建为 NetworkX 图，计算节点度、边权重等图统计量

5

社区检测 (Community Detection)

使用 Leiden 算法进行层级聚类，生成多层级社区结构

6

社区摘要生成 (Community Summarization)

为每个社区生成自然语言摘要，描述该社区的主题和关键发现

7

向量化存储 (Embedding & Storage)

对实体描述、关系描述、社区摘要分别生成向量，存入向量数据库

🔍 Local Search（局部搜索）

适用于具体的、有明确实体指向的问题。流程：

问题 → 实体链接 → 子图遍历 → 上下文组装 → LLM 生成

🌐 Global Search（全局搜索）

适用于宏观的、需要全局视角的问题。流程：

问题 → 社区筛选 → Map（并行摘要） → Reduce（合并） → 最终答案
💡 选择策略 问题涉及特定实体 → Local Search；问题需要概览/总结/对比 → Global Search；不确定 → 两者并行，取最优。

🔬 关键技术细节

深入理解每个环节的实现要点

抽取 Prompt 的核心要素：

  • 实体类型约束：预定义允许的实体类型列表，避免抽取过于泛化
  • 输出格式规范：要求 JSON 格式输出，包含 entities 和 relations 两个数组
  • 多轮 Gleanings：第一轮抽取后，追问"是否还有遗漏的实体？"，提升召回率
  • 关系方向性：明确要求标注关系的方向（source → target）
Python
EXTRACT_PROMPT = """
-Goal-
Given a text document, identify all entities and their relationships.

-Steps-
1. Identify all entities (types: {entity_types})
2. For each pair of related entities, identify the relationship
3. Return in JSON format

-Output Format-
{{
  "entities": [
    {{"name": "...", "type": "...", "description": "..."}}
  ],
  "relations": [
    {{"source": "...", "target": "...", "type": "...", "description": "..."}}
  ]
}}
"""

Leiden 算法是 Louvain 的改进版，解决了 Louvain 可能产生断裂社区的问题。核心步骤：

  • 局部移动：将节点移动到使模块度增益最大的邻居社区
  • 精炼：在每个社区内部进一步细分（Louvain 没有这步）
  • 聚合：将社区压缩为超节点，递归执行

通过 resolution 参数控制社区粒度：值越大社区越小越多，值越小社区越大越少。Graph RAG 通常在多个 resolution 下运行，生成层级社区结构。

同一实体可能以不同名称出现（如"微软"、"Microsoft"、"MSFT"），需要合并：

  • 字符串相似度：编辑距离、Jaccard 相似度
  • 向量相似度：实体描述的 embedding 余弦相似度
  • LLM 判断：将候选对交给 LLM 判断是否为同一实体
  • 图结构线索：共享大量邻居的节点更可能是同一实体

实践中通常采用"先粗筛（向量相似度 > 0.85）再精排（LLM 判断）"的两阶段策略。

大社区可能包含数百个实体，无法一次性放入 LLM 上下文。采用 Map-Reduce 策略：

  • Map 阶段：将社区内实体分批，每批生成局部摘要
  • Reduce 阶段：将所有局部摘要合并为最终社区摘要

摘要内容包括：社区主题、关键实体、重要发现、实体间的核心关系模式。

🚧 工程落地挑战

从 Demo 到生产的关键问题

💰 成本控制

实体抽取需要对每个 chunk 调用 LLM，100 页文档可能需要数百次 API 调用。

应对策略：使用小模型做初筛 + 大模型做精抽；批量处理；缓存已处理的 chunk。

📈 图规模膨胀

大规模文档集可能产生数十万节点和百万级边，图遍历性能下降。

应对策略：图剪枝（删除低度节点）；分层索引；图数据库（Neo4j/Nebula）替代内存图。

🔄 增量更新

新文档加入时，需要更新图结构、重新检测社区、重新生成摘要。

应对策略：局部更新（只影响新增实体的邻域）；延迟重建社区；版本化图快照。

🎯 抽取质量

LLM 抽取的实体和关系可能有错误、遗漏或幻觉。

应对策略：多轮 gleanings；交叉验证（多个 chunk 提到的关系更可信）；人工审核高权重节点。

🔧 全链路优化工程实践

对标传统 RAG 的优化手段，Graph RAG 每个环节的对应优化策略

📐 优化框架 传统 RAG 的优化路径（索引→查询→检索→重排→上下文→生成）同样适用于 Graph RAG，但每个环节都有图特有的优化手段。

📑 索引阶段优化

传统 RAG 对应：分块策略优化（语义分块、递归分块）

Graph RAG 优化方向：

  • 多轮抽取 (Gleanings)：首轮抽取后追问遗漏，提升实体召回率 15-30%
  • 实体类型约束：预定义领域实体类型，减少噪声实体
  • 关系权重计算：基于共现频率和 LLM 置信度计算边权重
  • 图剪枝：删除低度节点和低权重边，控制图规模
Python
def prune_graph(G, min_degree=2, min_edge_weight=0.3):
    """图剪枝：删除低度节点和低权重边"""
    # 删除低度节点
    low_degree = [n for n, d in G.degree() if d < min_degree]
    G.remove_nodes_from(low_degree)
    # 删除低权重边
    low_weight = [(u, v) for u, v, d in G.edges(data=True)
                  if d.get("weight", 1.0) < min_edge_weight]
    G.remove_edges_from(low_weight)
    return G

🔍 查询阶段优化

传统 RAG 对应：HyDE、查询改写、多查询并行

Graph RAG 三大查询优化：

1️⃣ 实体链接

从问题中识别实体，在图中锚定对应节点。先精确匹配，再向量模糊匹配（处理别名/缩写）。

2️⃣ 查询分解

将复杂多跳问题分解为可独立回答的子问题，分别检索后合并答案。

3️⃣ 图感知 HyDE

生成"假设实体列表"而非假设文档，用假设实体在向量库中找真实实体，扩大检索种子集。

💡 组合策略

实体链接 → 查询分解 → 图感知 HyDE，三者可串联使用，逐步扩大检索覆盖面。

🎯 检索阶段优化

传统 RAG 对应：BM25 + 向量混合检索，RRF 融合

Graph RAG 三路混合检索：

稠密检索 (40%) + 稀疏检索 (20%) + 图遍历 (40%) → RRF 融合

🔄 动态跳数控制

根据问题复杂度动态调整图遍历深度：1跳（直接关系）、2跳（间接关系）、3跳（深层关系）。由 LLM 判断所需跳数。

🏷️ 关系类型过滤

不是所有关系都与问题相关。让 LLM 判断哪些关系类型与当前问题相关，只遍历相关类型的边，减少噪声。

📊 重排阶段优化

传统 RAG 对应：Cross-Encoder 精排

Graph RAG 的图结构感知重排：

三维度融合打分

维度信号来源权重
语义相关性Cross-Encoder 分数50%
图距离与种子实体的最短路径30%
节点重要性PageRank 分数20%

🌈 社区感知多样性

类似 MMR（最大边际相关性）的图版本：在保证相关性的同时，优先选择来自不同社区的节点，确保结果覆盖多个主题维度，避免信息冗余。

📋 上下文阶段优化

传统 RAG 对应：上下文压缩、Lost-in-Middle 优化

Graph RAG 的结构化上下文组装：

四层上下文结构

1

社区背景

全局视角，提供主题概览

2

核心实体

精确事实，实体属性和描述

3

关系网络

结构信息，实体间的连接

4

原文片段

细节支撑，可溯源的原始文本

✂️ 子图剪枝

按相关性分数排序，在 token 预算内贪心选取节点。确保最相关的信息优先进入上下文窗口。

🗜️ 路径精简

将多跳路径压缩为自然语言描述，减少 token 消耗。如"张三→项目A→Python→3.11"压缩为"张三负责的项目A使用Python 3.11"。

✨ 生成阶段优化

传统 RAG 对应：Self-RAG、CRAG、引用溯源

Graph RAG 的生成优化：

🔍 图引导自我修正

生成答案后，用图中的事实验证答案一致性。发现不一致则修正后重新生成，确保事实准确。

📎 引用溯源

每个实体/关系都记录了来源 text_unit_ids。生成时要求 LLM 标注引用，答案可追溯到原始文档片段。
