# AI 技术选型指南：不同场景下的技术方案

> 整理自：RAG 学习过程中的场景分析、美团/电商真实落地案例、GitHub 开源项目研究
> 更新时间：2026-04-08

---

## 一、核心技术方案速览

在大模型应用开发中，主要有以下几类技术方案，它们不是互斥的，而是经常组合使用：

| 技术方案 | 核心逻辑 | 一句话定位 |
|---|---|---|
| **RAG**（检索增强生成） | 从外部知识库检索相关内容，喂给大模型生成答案 | 让模型"查资料"再回答 |
| **推荐系统**（协同过滤/生成式推荐） | 从用户历史行为中学习偏好，预测用户感兴趣的内容 | 让模型"猜喜好"再推荐 |
| **Agent**（智能体） | 大模型自主规划任务，调用工具/API 完成多步骤目标 | 让模型"自己想办法"完成任务 |
| **Fine-tuning**（微调） | 用特定领域数据重新训练模型，让模型内化专业知识 | 让模型"变成专家" |
| **Prompt Engineering** | 通过精心设计的提示词控制模型输出 | 让模型"听懂指令" |
| **Function Calling / Tool Use** | 大模型调用外部函数或 API 获取实时数据 | 让模型"使用工具" |

---

## 二、核心判断框架：选型前先问这三个问题

```
问题1：用户的需求靠"查知识"满足，还是靠"理解偏好"满足？
  → 查知识（政策、文档、FAQ）→ 优先考虑 RAG
  → 理解偏好（推荐什么吃、买什么）→ 优先考虑推荐系统

问题2：所需数据是静态的，还是实时动态的？
  → 静态（规章制度、产品手册）→ 可以向量化存入知识库，适合 RAG
  → 实时动态（库存、订单、价格）→ 需要 API 调用，适合 Agent + Function Calling

问题3：任务是单步的，还是需要多步规划？
  → 单步（回答一个问题）→ RAG 或直接 LLM 调用
  → 多步（订餐 → 查优惠 → 下单 → 确认）→ 需要 Agent
```

## 三、按业务场景的技术选型

### 场景一：企业内部知识库问答

**典型需求**：员工问 HR 政策、IT 操作手册、合规规定

**推荐方案**：RAG（标准向量检索）

**技术组合**：
- 文档解析（PDF/Word/Excel）→ 文本切分（Chunking）→ Embedding 向量化 → 向量数据库存储
- 用户提问 → 向量检索召回相关片段 → 大模型生成答案

**关键设计点**：
- Chunk 策略：按段落切分，保留标题上下文，避免语义断裂
- 元数据：记录文档版本、更新时间，支持过滤过期内容
- 知识库更新机制：文档变更时自动触发重新向量化

**不适合的情况**：需要查询实时数据（如当前库存）、需要跨系统操作

**参考项目**：`infiniflow/ragflow`、`datawhalechina/all-in-rag`

---

### 场景二：智能客服（电商/本地生活）

**典型需求**：回答商品咨询、退换货政策、订单状态查询

**推荐方案**：RAG + Agent + Function Calling 混合架构

**技术组合**：

```
用户提问
  ↓
意图识别（判断是知识类问题还是操作类问题）
  ↓
  ├── 知识类（退货政策、商品参数）→ RAG 检索知识库 → 大模型生成答案
  └── 操作类（查订单、查物流）→ Function Calling 调用业务 API → 大模型整合结果
```

**知识库分层设计**（来自美团电商实践）：
- 静态知识库：平台规则、商品知识、FAQ → 向量数据库，周更新
- 准实时知识库：促销活动、库存状态 → Elasticsearch，小时级更新
- 实时数据接口：订单状态、物流信息 → 直接 API 调用，实时

**关键设计点**：
- 混合检索：向量检索 + 关键词检索（BM25），解决精确匹配问题（订单号、SKU）
- 查询改写（Query Rewrite）：将口语化问题转为检索友好的标准表达
- 重排序（Rerank）：对召回结果二次排序，提升相关性
- 降级方案：知识库故障时回退到规则引擎

**成本控制**：
- 简单问题（FAQ 命中率 > 90%）→ 用轻量模型（GPT-3.5 级别）
- 复杂推理问题 → 才调用重量级模型（GPT-4 级别）

**参考项目**：`langchain-ai/rag-from-scratch`（Query Translation 部分）

---

### 场景三：个性化推荐（吃什么、买什么、看什么）

**典型需求**：根据用户偏好推荐餐厅、商品、内容

**推荐方案**：推荐系统（协同过滤 / 生成式推荐），**不是 RAG**

**核心逻辑**：从用户历史行为序列中学习偏好模式，预测用户对候选内容的兴趣分

**技术路线**：
- 传统路线：DLRM（Deep Learning Recommendation Model）+ 特征工程
- 生成式路线（2024-2025 趋势）：HSTU 架构，把用户行为序列当 Token 建模，类似 LLM 的 Scaling Law

**为什么不用 RAG**：
- 推荐数据是行为数据（点击、购买、停留时长），不是文档知识
- 需要实时个性化，无法预先向量化
- 核心是"理解偏好"，不是"检索知识"

**RAG 在推荐场景的辅助作用**：
- 生成推荐理由（"这家餐厅适合你，因为你之前喜欢..."）→ 用 RAG 从评价数据中检索支撑内容
- 冷启动场景（新用户无行为数据）→ 用 RAG 从用户描述中检索相似偏好

**参考案例**：美团 MTGR（Meituan Generative Recommendation），外卖首页订单量 +1.22%

### 场景四：复杂任务自动化（AI Agent）

**典型需求**：帮我订一家周五晚上适合商务宴请的餐厅、帮我规划一次周末旅行

**推荐方案**：Multi-Agent 架构

**技术组合**：
```
用户自然语言输入
  ↓
主 Agent（意图理解 + 任务规划）
  ↓
  ├── 子 Agent A：搜索餐厅（调用地图/点评 API）
  ├── 子 Agent B：查询可用时间（调用日历 API）
  ├── 子 Agent C：查询优惠（调用促销系统 API）
  └── 子 Agent D：完成预订（调用订座 API）
  ↓
主 Agent 汇总结果，生成最终回复
```

**关键设计点**：
- 工具定义要精确：工具描述不清是 Agent 选错工具的主要原因
- 状态管理：长任务的中间状态要持久化，不能只存在上下文里
- 降级与容错：某个子 Agent 失败时的处理策略
- 人工介入节点：涉及支付、敏感操作时需要用户确认

**适合 Agent 的判断标准**：
- 任务需要 2 步以上的规划
- 需要调用多个外部系统
- 中间步骤的结果会影响后续决策

**参考案例**：美团"小美" App，LangGraph Agentic RAG

### 场景五：专业领域问答（法律、医疗、金融）

**典型需求**：合同条款解读、药品说明查询、财报分析

**推荐方案**：RAG + 领域微调（Fine-tuning）组合

**为什么需要微调**：
- 专业术语理解：通用模型对"不可抗力条款"、"适应症"等专业概念理解不准确
- 输出格式规范：法律文书、医疗建议有特定的表达规范
- 幻觉风险更高：专业领域的错误代价更大，需要更强的"只基于检索内容回答"的约束

**技术组合**：
- 领域语料微调 → 让模型理解专业术语
- RAG 检索最新法规/指南 → 解决知识时效性问题
- 严格的引用溯源 → 每个结论必须标注来源文档和段落

**特殊考虑**：
- 金融场景：数字精确性要求极高，表格解析能力是关键瓶颈
- 法律场景：条文之间有引用关系，GraphRAG（知识图谱）比普通向量检索更适合
- 医疗场景：需要结合最新诊疗指南，知识库更新频率要求高

**参考项目**：`microsoft/graphrag`（法律/金融复杂推理场景）、`LightRAG`（轻量图 RAG）

### 场景六：文档处理与内容生成

**典型需求**：合同摘要、报告生成、多文档对比分析

**推荐方案**：长上下文 LLM 或 RAG（取决于文档规模）

**选型判断**：
```
文档总量 < 模型上下文窗口（如 128K tokens）
  → 直接塞入上下文，用长上下文 LLM（GPT-4o、Claude 3.5）
  → 简单、效果好、无需额外工程

文档总量 > 模型上下文窗口，或文档数量很多
  → 用 RAG，先检索相关片段再生成
  → 需要额外的检索工程，但可处理海量文档
```

**多文档对比场景的特殊处理**：
- 普通 RAG 容易只检索到单个文档的内容，遗漏对比维度
- 解法：先对每个文档分别提取结构化信息，再做横向对比

### 场景七：代码库问答与开发辅助

**典型需求**：理解代码库、回答"这个函数在哪里定义"、生成符合项目规范的代码

**推荐方案**：代码专用 RAG（Code RAG）

**与普通 RAG 的区别**：
- Chunking 策略不同：按函数/类/模块切分，而不是按字符数切分
- Embedding 模型不同：需要代码专用 Embedding（如 CodeBERT）
- 检索粒度不同：需要支持"找到调用了 X 函数的所有地方"这类结构化查询
- 结合 AST（抽象语法树）做代码结构理解

**参考工具**：GitHub Copilot、Cursor、Codeium 背后都有类似架构

## 四、技术组合的常见模式

### 模式一：纯 RAG（最简单）
```
适用：静态知识库问答、FAQ 机器人
技术栈：Embedding + 向量数据库 + LLM
代表工具：LlamaIndex、LangChain 基础链
```

### 模式二：RAG + Rerank（提升精度）
```
适用：对答案准确性要求较高的场景
在纯 RAG 基础上增加：BGE-Reranker 等重排序模型
效果：检索相关性从 74% → 89%（电商客服实测数据）
```

### 模式三：Agentic RAG（动态检索）
```
适用：需要多轮检索、自适应查询的场景
大模型自主决定"是否需要检索"、"检索什么"、"是否需要再次检索"
代表框架：LangGraph、AutoGen
```

### 模式四：RAG + Agent + Function Calling（全能型）
```
适用：复杂业务场景，既需要知识检索，又需要操作系统
典型案例：电商智能客服、本地生活 AI 助手
```

### 模式五：GraphRAG（复杂推理）
```
适用：需要跨实体推理、关系分析的场景（法律、金融、学术研究）
在向量检索基础上增加：知识图谱构建 + 图检索
代表项目：microsoft/graphrag、HKUDS/LightRAG
```

## 五、RAG 的核心失败场景（PM 必知）

理解 RAG 在哪里会失败，比理解它在哪里成功更重要：

| 失败类型 | 具体表现 | 根本原因 | 解决方向 |
|---|---|---|---|
| 检索失败 | 找到的内容和问题不相关 | 问题表述与文档表述差异大 | Query Rewrite、混合检索 |
| 知识边界模糊 | 知识库没有答案，但模型仍然"编"了一个 | 模型不知道自己不知道 | 相似度阈值过滤、Prompt 约束 |
| 多跳推理失败 | 答案需要拼接多个文档的信息 | 单次检索只能召回局部信息 | GraphRAG、多轮检索 |
| 时效性问题 | 回答了已经过期的政策 | 知识库未及时更新 | 元数据过滤、自动同步机制 |
| 文档解析失败 | 表格、图片中的信息丢失 | 文档解析能力不足 | 专用解析引擎（如 RAGFlow 的 DeepDoc）|
| 长文档截断 | 答案在文档末尾，被 Chunk 切断 | Chunk 策略不合理 | 滑动窗口、语义切分 |
| 精确匹配失败 | 订单号、SKU 等精确信息检索不到 | 向量检索不擅长精确匹配 | 混合检索（向量 + BM25）|

## 六、评估体系：怎么衡量系统好不好

### RAG 系统的核心评估维度

```
检索质量
  ├── 召回率（Recall）：相关文档有没有被找到
  ├── 精确率（Precision）：找到的文档有多少是相关的
  └── MRR（Mean Reciprocal Rank）：最相关文档排在第几位

生成质量
  ├── 答案忠实度（Faithfulness）：答案是否真的来自检索内容，而非模型编造
  ├── 答案相关性（Answer Relevance）：答案是否回答了用户的问题
  └── 上下文相关性（Context Relevance）：检索到的内容是否和问题相关

业务效果
  ├── 自动解决率：无需转人工的对话占比
  ├── 用户满意度：对话后的评分
  └── 响应时延：从提问到回答的时间
```

**推荐评估框架**：[RAGAS](https://github.com/explodinggradients/ragas)，可量化上述指标

## 七、技术选型决策树

```
用户需求是什么？
│
├── 回答关于"知识/文档"的问题
│   ├── 文档是静态的 → RAG
│   │   ├── 需要精确匹配（订单号等）→ RAG + 混合检索
│   │   ├── 需要跨文档推理 → GraphRAG
│   │   └── 文档有复杂格式（表格/图片）→ RAGFlow 类工具
│   └── 文档需要实时更新 → RAG + 定时同步 or Function Calling
│
├── 根据用户偏好推荐内容
│   └── 推荐系统（协同过滤 / 生成式推荐），不是 RAG
│
├── 完成一个多步骤的复杂任务
│   └── Agent（+ RAG 作为知识工具，+ Function Calling 作为操作工具）
│
├── 需要模型掌握特定领域的专业知识
│   └── Fine-tuning（+ RAG 补充时效性知识）
│
└── 控制模型输出格式和风格
    └── Prompt Engineering（最轻量，优先尝试）
```
