# AI Agent 评估体系（Evals）学习指南

> 整理自 Anthropic 官方工程博客《Demystifying evals for AI agents》及业界主流 Benchmark 实践，系统梳理 AI Agent 评估的核心方法论、评分器设计与落地路线图。

### 一、为什么评估（Evals）如此重要

良好的评估体系帮助团队更自信地发布 AI Agent。没有它，团队很容易陷入被动循环——只能在生产环境中发现问题，而修复一个失败又会引发其他问题。

**没有评估的典型困境：**

- 用户报告 Agent 在某次变更后"感觉更差"，但团队无法验证
- 调试完全被动：等待投诉 → 手动重现 → 修复 → 祈祷没有回归
- 无法区分真正的回归和随机噪声
- 新模型发布时，需要数周手动测试才能决定是否升级

**有评估的收益：**

- 在问题影响用户之前就让行为变化变得可见
- 快速验证新模型：拥有评估的团队可以在几天内完成模型升级决策
- 为产品和研究团队提供最高带宽的沟通通道
- 评估驱动开发（Eval-Driven Development）：在 Agent 能力实现之前就定义成功标准

### 二、核心概念定义

| 术语 | 定义 |
| --- | --- |
| **任务（Task）** | 具有定义输入和成功标准的单个测试用例 |
| **试验（Trial）** | 每次尝试任务的一次运行（因模型输出有随机性，需多次试验） |
| **评分器（Grader）** | 评估 Agent 性能某些方面的逻辑，一个任务可有多个评分器 |
| **记录（Transcript）** | 试验的完整记录，包括输出、工具调用、推理、中间结果 |
| **结果（Outcome）** | 试验结束时环境的最终状态（如数据库中是否存在预订记录） |
| **评估框架（Evaluation Harness）** | 端到端运行评估的基础设施，提供指令和工具、并发运行任务、记录步骤、评分并汇总结果 |
| **评估套件（Evaluation Suite）** | 旨在衡量特定能力或行为的任务集合 |

### 三、三类评分器

#### 1. 基于代码的评分器（Deterministic）

**方法：** 字符串匹配、二进制测试（单元测试通过/失败）、静态分析（lint/类型检查）、结果验证、工具调用验证

**优势：** 快速、便宜、客观、可重现、易于调试

**劣势：** 对不完全匹配预期模式的有效变化很脆弱，缺乏细微差别

**最适合：** 编码 Agent（代码是否运行、测试是否通过）

#### 2. 基于模型的评分器（LLM-as-Judge）

**方法：** 基于标准的评分、自然语言断言、成对比较、基于参考的评估、多判官共识

**优势：** 灵活、可扩展、捕获细微差别、处理开放式任务

**劣势：** 有不确定性、比代码更昂贵、需要与人工评分器校准

**最适合：** 对话 Agent（沟通质量、同理心）、研究 Agent（综合质量）

**注意事项：**

- 给 LLM 一条出路（如"当信息不足时返回 Unknown"），避免幻觉
- 用孤立的 LLM 评估每个维度，而非一个 LLM 评估所有维度
- 必须与人类专家定期校准

#### 3. 人工评分器（Human）

**方法：** 领域专家审查、众包判断、抽样检查、A/B 测试

**优势：** 黄金标准质量，匹配真实用户判断

**劣势：** 昂贵、缓慢

**最适合：** 校准 LLM 评分器、评估高风险决策

### 四、两个关键指标：pass@k 与 pass^k

Agent 行为在运行之间存在随机性，需要用两个指标来全面衡量：

**pass@k**：Agent 在 k 次尝试中至少获得一个正确解决方案的概率

- 随着 k 增加而上升
- 适用于"一次成功就够"的工具场景
- 例：编码 Agent 的 pass@1 衡量首次尝试成功率

**pass^k**：所有 k 次试验都成功的概率

- 随着 k 增加而下降
- 适用于"每次都必须可靠"的面向用户场景
- 例：客服 Agent 需要高 pass^k

**示例：** 如果 Agent 每次试验成功率为 75%，运行 3 次试验：

- pass@3 ≈ 98%（至少一次成功）
- pass^3 ≈ 42%（三次全部成功）

### 五、四类 Agent 的评估方法

#### 编码 Agent

**核心方法：** 确定性评分器（单元测试通过/失败）

**代表 Benchmark：**

- **SWE-bench Verified**：来自 12 个流行 Python 项目的 2294 个真实 GitHub Issue，通过运行测试套件评分。LLM 在一年内从 40% 进步到 >80%
- **Terminal-Bench**：端到端技术任务（从源码构建 Linux 内核、训练 ML 模型）
- **HumanEval**：代码生成能力评估

**评估示例（YAML）：**

```YAML
// 代码块
task:
  id: "fix-auth-bypass_1"
  desc: "修复密码字段为空时的身份验证绕过"
  graders:
    - type: deterministic_tests
      required: [test_empty_pw_rejected.py]
    - type: llm_rubric
      rubric: prompts/code_quality.md
    - type: static_analysis
      commands: [ruff, mypy, bandit]
    - type: tool_calls
      required:
        - {tool: read_file}
        - {tool: edit_file}
        - {tool: run_tests}

```

#### 对话 Agent

**核心方法：** 需要第二个 LLM 模拟用户，结合状态检查 + LLM 标准

**代表 Benchmark：**

- **τ-Bench / τ2-Bench**：模拟跨零售支持和航空预订等领域的多轮交互，一个模型扮演用户角色

**成功维度示例（客服 Agent）：**

- 票是否解决（状态检查）
- 是否在 <10 轮内完成（记录约束）
- 语气是否适当（LLM 标准）

#### 研究 Agent

**核心方法：** 结合基础性检查 + 覆盖检查 + 来源质量检查

**代表 Benchmark：**

- **BrowseComp**：测试 AI Agent 是否可以在开放网络上找到"大海捞针"——设计得易于验证但难以解决的问题

**挑战：** 研究质量具有主观性，基本事实随参考内容变化，需要频繁与专家人工判断校准

#### 计算机使用 Agent（GUI Agent）

**核心方法：** 在真实或沙盒环境中运行，检查最终状态

**代表 Benchmark：**

- **WebArena**：基于浏览器的任务，使用 URL 和页面状态检查验证
- **OSWorld**：完整操作系统控制，检查文件系统状态、应用配置、数据库内容

### 六、能力评估 vs 回归评估

| 类型 | 目标 | 通过率 | 用途 |
| --- | --- | --- | --- |
| **能力评估** | "这个 Agent 能做什么好？" | 从低开始，逐步爬升 | 衡量进步，针对 Agent 挣扎的任务 |
| **回归评估** | "Agent 是否仍然处理它以前处理的所有任务？" | 接近 100% | 防止倒退，持续运行 |

**毕业机制：** 当能力评估通过率足够高后，可以"毕业"成为持续运行的回归套件。

**评估饱和警告：** 当 Agent 通过所有可解决的任务时，评估饱和发生，没有改进信号。SWE-Bench Verified 分数已从 30% 接近 >80% 的饱和，需要不断设计更难的任务。

### 七、从零到一：构建评估的路线图

#### 第一步：尽早开始，从 20-50 个任务起步

不要等到有数百个任务才开始。从真实失败中得出的 20-50 个简单任务是很好的开始。等待时间越长，评估就越难构建——早期产品需求自然转化为测试用例，等待太久则需要从实时系统中逆向工程成功标准。

#### 第二步：从手动测试转化

从你在开发过程中运行的手动检查开始——每次发布前验证的行为、最终用户尝试的常见任务。如果已经投入生产，查看错误跟踪器和支持队列，将用户报告的失败转换为测试用例。

#### 第三步：编写明确的任务和参考解决方案

一个好的任务是两个领域专家可以独立达到相同通过/失败判定的任务。任务规范中的歧义成为指标中的噪声。每个任务都应该创建参考解决方案（已知工作的输出），证明任务是可解决的。

#### 第四步：构建平衡的问题集

同时测试行为**应该**发生和**不应该**发生的情况。单方面的评估创造单方面的优化——如果只测试 Agent 是否在应该的时候搜索，可能最终得到一个几乎搜索所有内容的 Agent。

#### 第五步：构建稳定的评估框架

每个试验应该从干净的环境开始（隔离）。运行之间不必要的共享状态（剩余文件、缓存数据）可能导致由于基础设施不稳定性而非 Agent 性能的失败。

#### 第六步：深思熟虑地设计评分器

- 尽可能选择确定性评分器
- 避免检查 Agent 是否遵循了非常具体的步骤（太僵化），而是评估 Agent 产生的内容
- 为具有多个组件的任务建立部分学分
- 让评分器抵抗绕过或黑客攻击

#### 第七步：持续阅读记录（Transcripts）

除非阅读来自多次试验的记录，否则不会知道评分器是否工作良好。当任务失败时，记录会告诉你 Agent 是否犯了真正的错误，还是评分器拒绝了有效的解决方案。

### 八、主流评估工具与框架

| 工具 | 类型 | 特点 |
| --- | --- | --- |
| **LangSmith** | 评估 + 追踪 | LangChain 生态，支持 LLM-as-Judge，可视化 trace |
| **Langfuse** | 评估 + 可观测性 | 开源，支持自定义评分器，成本追踪 |
| **Braintrust** | 评估平台 | 专注 LLM 评估，支持 A/B 测试 |
| **Promptfoo** | 评估框架 | 开源，支持多模型对比，CLI 友好 |
| **AgentBench** | Benchmark | 跨环境泛化能力测试 |
| **AgentBoard** | Benchmark | 决策过程的细粒度分析 |
| **SWE-bench** | Benchmark | 真实软件工程问题，代码 Agent 标准测试集 |
| **τ-Bench** | Benchmark | 对话 Agent，多轮交互评估 |

### 九、常见陷阱与反模式

1. **评估太晚才开始**：等到 Agent 上线后才构建评估，此时逆向工程成功标准非常困难
2. **只测试正向路径**：忽略测试"不应该发生"的行为，导致 Agent 过度触发某些行为
3. **评分器过于僵化**：检查工具调用的具体顺序，惩罚了找到更好路径的 Agent
4. **忽略评估饱和**：评估通过率接近 100% 后不更新，失去改进信号
5. **不读记录**：只看分数不看过程，无法发现评分器本身的问题
6. **环境不隔离**：试验之间共享状态，导致结果不可重现
