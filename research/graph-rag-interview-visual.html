Level 1

基础概念题

理解 Graph RAG 的核心定义、适用场景和基本组件

传统 RAG 的检索单元是文本块（chunk），通过向量相似度找到最相关的若干段落后拼接给 LLM。它的本质是"局部语义匹配"，对跨文档、跨段落的关联关系无能为力。

Graph RAG 在此基础上引入了知识图谱层。核心流程分为两阶段：

索引阶段

对原始文档做实体抽取（Entity Extraction）和关系抽取（Relation Extraction），构建一张以实体为节点、关系为边的知识图谱；再对图做社区检测（Community Detection），将关联紧密的实体聚合成社区，并为每个社区生成摘要。

检索阶段

  • Local Search：从查询实体出发，沿图的邻居关系做 K 跳游走，适合"某个具体实体的详细信息"类问题。
  • Global Search：汇总所有社区摘要，做 Map-Reduce 式全局推理，适合"整个语料库的宏观趋势"类问题。
💡
核心区别

传统 RAG 检索的是"相似文本片段"，Graph RAG 检索的是"结构化知识子图"，后者天然支持多跳推理和全局摘要。

适合的场景

  • 多跳推理：如"A 公司的 CEO 毕业于哪所大学？"需要跨越多个实体关系。
  • 全局摘要：如"这批财报中，哪些风险因素被反复提及？"需要跨文档聚合。
  • 关系探索：如知识图谱问答、供应链分析、医疗知识库。
  • 长文档理解：文档内部实体关系复杂，向量检索容易丢失结构信息。

不适合的场景

  • 简单事实查询：如"XX 产品的价格是多少？"传统 RAG 已足够。
  • 实时性要求极高：图的构建和社区检测是离线批处理，无法做到秒级更新。
  • 语料库极小：图结构的优势在大规模、高密度关联的语料上才能体现。
  • 非结构化程度极高：如纯图片、音频，无法直接抽取实体关系。

社区检测是图分析中将节点划分为若干"社区"的过程，同一社区内的节点连接紧密，不同社区间连接稀疏。在 Graph RAG 中，社区对应一组语义相关的实体集合，社区摘要是 Global Search 的核心检索单元。

Louvain 算法

核心思想是贪心优化模块度（Modularity）：先将每个节点视为独立社区，然后反复将节点移入能最大化模块度增益的邻居社区，直到收敛。速度快，但可能产生"内部不连通"的社区。

Leiden 算法

在 Louvain 基础上增加了"精炼（Refinement）"阶段：在每轮社区合并后，对社区内部做子社区分裂，确保每个社区都是内部连通的。产生的社区质量更高、更稳定，且理论上保证收敛到更优解。

✅
关键优势

Leiden 还支持层级社区（Hierarchical Communities），不同层级对应不同粒度的摘要，检索时可按需选择层级。

维度 Local Search Global Search
流程 查询向量化 → 找种子实体 → K 跳图游走 → 收集上下文 → LLM 生成 加载社区摘要 → Map（并行生成局部答案）→ Reduce（汇总最终答案）
特点 上下文精准、token 消耗少、延迟低 覆盖全局、支持宏观推理，但 token 消耗大、延迟高
适用 针对特定实体的具体问题 需要跨文档聚合的宏观问题

选择策略：实际系统中通常做查询意图分类，将问题路由到对应路径；也可以做 Hybrid Search，先 Local 再 Global，用 RRF 融合两路结果。

Level 2

核心算法题

深入实体抽取、图嵌入、检索融合等关键算法

方案一：基于 LLM 的 Prompt 抽取（主流方案）

直接用 LLM 通过 Prompt 抽取实体和关系，输出结构化 JSON。

优点：无需标注数据、泛化能力强。缺点：成本高、速度慢、输出格式不稳定。

工程优化：使用 Gleaning 机制——第一轮抽取后，让 LLM 检查是否有遗漏，进行补充抽取，通常做 1-2 轮即可显著提升召回率。

方案二：基于 NLP 工具的传统方案

使用 spaCy、Stanford NLP、HanLP 等工具做 NER 和关系抽取。速度快、成本低，但对领域特定实体效果差。

方案三：Fine-tuned 小模型

在领域数据上微调 BERT/RoBERTa 等模型。在特定领域精度高，但需要标注数据、维护成本高。

💡
实际工程选择

通用场景用 LLM Prompt 方案；高频、大规模场景用小模型做粗筛 + LLM 做精抽取的两阶段流水线。

实体链接（Entity Linking）是将文本中提到的实体指称映射到知识库中唯一实体的过程。例如，"苹果公司"、"Apple Inc."、"AAPL" 应该被识别为同一个实体节点。

不做实体链接的后果

  • 图结构碎片化：本应连通的节点变成孤立节点，多跳推理断链。
  • 社区质量下降：相关实体被分散到不同社区，摘要质量变差。
  • 检索召回率低：查询"Apple"时找不到"苹果公司"相关的节点。

工程实现

# 基于嵌入相似度的实体链接 def entity_linking(mention, entity_index, threshold=0.85): mention_emb = embed(mention) candidates = [] for entity_id, entity_emb in entity_index.items(): sim = cosine_similarity(mention_emb, entity_emb) if sim > threshold: candidates.append((entity_id, sim)) if candidates: return max(candidates, key=lambda x: x[1])[0] else: return create_new_entity(mention)

图嵌入将图中的节点映射为低维稠密向量，使得图结构信息可以被向量检索系统利用。主要用于：实体检索、实体链接、社区初始化。

维度 Node2Vec GraphSAGE
原理 随机游走 + Word2Vec Skip-Gram 聚合邻居节点特征（Inductive Learning）
特点 可捕获同质性或结构等价性 可为新节点生成嵌入
缺点 Transductive，无法处理新节点 需要节点有初始特征
适用 静态图，简单高效 动态更新图，频繁新增实体

RRF（Reciprocal Rank Fusion，倒数排名融合）是一种无参数的多路检索结果融合算法。公式：

RRF_score(d) = Σ 1 / (k + rank_i(d)) # k 是平滑常数（通常取 60）

在 Graph RAG 中融合三路结果

  • 向量检索：基于文本块嵌入的语义相似度排名
  • 图检索（Local Search）：基于图游走的实体关联度排名
  • 关键词检索（BM25）：基于词频的精确匹配排名
def rrf_fusion(results_list, k=60): scores = {} for results in results_list: for rank, doc_id in enumerate(results, start=1): scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + rank) return sorted(scores.items(), key=lambda x: x[1], reverse=True)

RRF 的优势在于不需要对不同检索路径的分数做归一化，鲁棒性强，在实践中效果通常优于简单加权融合。

Level 3

工程实践题

索引流水线、存储架构、延迟优化与质量评估

完整索引流水线分为六个阶段，每个阶段都有独特的工程挑战：

01
文档加载与切分

chunk 太小实体关系丢失，太大 LLM 窗口不够。通常 512-1024 token + 10-20% overlap。

02
实体与关系抽取

LLM 调用成本高，需异步并发 + semaphore 限流 + 结果缓存 + 断点续传。

03
实体链接与去重

基于嵌入相似度 + 规则（字符串归一化）的两阶段去重，避免过度合并。

04
图构建

原型用 NetworkX，生产环境迁移到 Neo4j 或 TigerGraph 处理大规模图。

05
社区检测

Leiden 算法在超大图上耗时较长，使用 graspologic 并行实现或分层采样。

06
社区摘要生成

按社区大小排序优先处理大社区；小社区（节点数 < 3）可跳过或用模板生成。

生产级 Graph RAG 通常采用多存储协同架构：

存储组件 存储内容 选型示例
图数据库 实体节点、关系边、图结构 Neo4j、TigerGraph、Neptune
向量数据库 实体嵌入、文本块嵌入、摘要嵌入 Qdrant、Weaviate、Pinecone
关系数据库 文档元数据、实体属性、社区元数据 PostgreSQL、MySQL
缓存层 热点查询结果、社区摘要 Redis
对象存储 原始文档、Parquet 格式图快照 S3、OSS

关键设计决策

  • 实体嵌入：同时存图数据库（节点属性）和向量数据库（ANN 检索），通过实体 ID 关联。
  • 社区摘要：文本存关系数据库，嵌入存向量数据库，通过 community_id 关联。
  • 一致性保证：用消息队列（Kafka）做异步同步，接受最终一致性。

延迟主要来自三个环节：图游走查询、LLM 调用推理、上下文拼接处理。

1. 图查询优化

  • 为高频查询的实体属性建立索引
  • 限制游走深度（K=2 已足够，K=3 开始指数级膨胀）
  • 子图剪枝：提前过滤低权重边

2. 缓存策略

  • 社区摘要缓存：静态内容永久缓存在 Redis
  • 查询结果缓存：相似查询（嵌入相似度 > 0.95）直接返回缓存
  • 实体嵌入缓存：热点实体嵌入缓存在内存

3. 异步与并行

  • Local Search 和 Global Search 并行执行，最后融合
  • Global Search 的 Map 阶段天然可并行

4. 自适应跳数（Adaptive K-hop）

根据查询复杂度动态调整游走深度：先做 K=1 检索，如果置信度不够再扩展到 K=2。

层次一：组件级评估

组件 评估指标
实体抽取Precision / Recall / F1
关系抽取Relation F1
社区检测模块度（Modularity）、社区内聚度
检索Recall@K、MRR

层次二：端到端评估（RAGAS 框架）

  • Faithfulness：答案是否有检索内容支撑，不产生幻觉
  • Answer Relevancy：答案是否回答了问题
  • Context Precision：检索到的内容有多少是有用的
  • Context Recall：有用的内容有多少被检索到了

层次三：与传统 RAG 对比

在多跳推理数据集（HotpotQA、MuSiQue）上，Graph RAG 通常比传统 RAG 高 15-30% 的 F1；但传统 RAG 在单跳简单问题上延迟更低、成本更低。

Level 4

系统设计题

从零设计生产级系统、增量更新方案

第一步：明确需求

  • 语料规模：百万文档 vs 千文档 → 决定图规模和存储选型
  • 更新频率：实时 vs 批量 → 决定索引架构
  • 查询类型：多跳推理 vs 全局摘要 → 决定检索策略
  • 延迟要求：秒级 vs 分钟级 → 决定缓存和并行策略

第二步：整体架构

[文档输入] → [文档处理服务] (切分、清洗) → [抽取服务] (实体/关系抽取，LLM 驱动，异步队列) → [图构建服务] (实体链接、图更新) → [社区检测服务] (Leiden，批处理) → [摘要生成服务] (社区摘要，LLM 驱动) → [嵌入服务] (实体嵌入、摘要嵌入) [查询输入] → [意图分类] (Local / Global / Hybrid) → [Local Search] (实体检索 → 图游走 → 上下文拼接) → [Global Search] (社区摘要 → Map-Reduce) → [RRF 融合] → [LLM 生成答案]

第三步：关键技术选型

  • 图数据库：Neo4j（中小规模）或 TigerGraph（大规模）
  • 向量数据库：Qdrant（开源自部署）或 Pinecone（托管）
  • 消息队列：Kafka（解耦索引流水线各阶段）
  • 编排：Airflow 或 Prefect（批处理流水线调度）

第四步：可观测性

每个阶段记录处理耗时、成功率、错误率。图质量监控（节点数、边数、社区数趋势）。在线 A/B 测试对比用户满意度。

难点分析

新文档的加入可能影响：新实体加入（简单）→ 已有实体属性更新（中等）→ 新关系改变图连通性（复杂）→ 社区结构变化需重新检测（最复杂）→ 社区摘要更新（依赖社区结构）。

三种工程方案

方案 策略 适用场景
全量重建 定期对全量语料重新跑索引流水线 更新频率低、规模不大
增量图更新 只更新受影响子图 + 局部社区重检测 中等规模、准实时需求
版本化图 维护图版本号，支持历史回溯 数据一致性要求高（法律、金融）
💡
实践建议

大多数生产系统采用"准实时"策略——新文档先进传统 RAG 索引（秒级），异步触发图更新流水线（分钟到小时级），两套索引并行服务。

Level 5

深度追问题

幻觉问题、多语言处理、KGQA 辨析、效果排查

答案是"取决于幻觉的类型"：

Graph RAG 能减少的幻觉

  • 关系幻觉：通过显式的关系边避免错误关联两个实体
  • 跨文档幻觉：通过图路径提供可验证的推理链，避免"脑补"中间步骤

Graph RAG 可能引入的新幻觉

  • 抽取幻觉：LLM 抽取可能引入错误实体/关系，被固化到图中影响后续所有查询
  • 摘要幻觉：社区摘要可能不准确概括，且错误会被放大（摘要是 Global Search 主要信息来源）

工程应对

  • 对抽取结果做置信度过滤，低置信度关系不加入图
  • 社区摘要生成时要求 LLM 引用原文，便于溯源验证
  • 答案生成时同时提供原始文本块作为 grounding

挑战

同一实体在不同语言中有不同表述（"北京" vs "Beijing" vs "Pékin"），实体链接更复杂；不同语言文档可能描述同一事件；社区摘要语言需与查询语言匹配。

工程方案

  • 多语言嵌入模型：使用 multilingual-e5、LaBSE 等，使不同语言同义实体在嵌入空间中距离接近
  • 语言标准化：将所有实体名称统一翻译为英语作为规范形式，保留原始语言名称作为别名
  • 查询时语言路由：检测查询语言，优先检索同语言文本块，通过实体 ID 关联跨语言内容
  • 多语言社区摘要：为每个社区生成多语言版本摘要，或查询时动态翻译
维度 KGQA Graph RAG
前提 已有结构化知识图谱（Wikidata、Freebase） 有原始文档语料，图从文档中自动抽取
任务 将自然语言转化为图查询语言（SPARQL、Cypher） 结合图结构检索和 LLM 生成
特点 答案精确、可解释，但依赖预构建图谱 不依赖预构建图谱，但答案是生成式的
局限 无法处理图谱中没有的知识 可能有幻觉

联系：Graph RAG 可以看作"自动构建知识图谱 + 基于图的 RAG"，而 KGQA 是"使用已有知识图谱做精确查询"。实际系统中两者可以结合。

排查框架（从数据到模型）

Step 1：确认问题类型 — 是所有问题都差，还是特定类型？如果只是简单单跳问题差，可能是正常的。

Step 2：检查图质量

# 图质量诊断 print(f"节点数: {G.number_of_nodes()}") print(f"边数: {G.number_of_edges()}") print(f"连通分量数: {nx.number_connected_components(G)}") print(f"平均度: {sum(dict(G.degree()).values()) / G.number_of_nodes():.2f}") # 连通分量数很多 → 图碎片化严重 → 实体链接有问题

Step 3：检查实体抽取质量 — 抽取的实体是否覆盖查询中的关键实体？关系是否正确？

Step 4：检查检索路径 — Local Search 种子实体是否找对？Global Search 社区摘要是否包含所需信息？

Step 5：检查上下文拼接 — 最终送给 LLM 的上下文是否包含正确信息？是否太长导致 Lost in the Middle？

⚠️
常见根因

实体链接失败→图碎片化→多跳断链；社区摘要质量差→Global Search 效果差；查询路由错误→简单问题走了 Global，复杂问题走了 Local；chunk 切分不合理→实体关系跨 chunk 丢失。
