# AI 对话生成智能体与工作流底层原理

> 项目：efficiency-agent-service — AI 智能体平台后端服务
>
> 定位：面向面试场景，用通俗语言解释"用户通过对话让 AI 自动生成智能体/工作流"的底层实现
>
> 时间：2026.06

---

## 概述

在平台上，用户除了手动逐项填写智能体配置外，还可以通过与 AI 对话来自动完成两件事：

AI 生成智能体：用户用一句话描述需求（如"帮我创建一个代码审查智能体"），AI 自动生成智能体的名称、使用场景、系统提示词等配置。

AI 生成工作流：用户描述一个自动化流程的需求（如"先搜索网页再填表提交"），AI 在沙箱中自主编排节点和连线，生成一个可执行的工作流。

这两件事底层都依赖大模型的理解和生成能力，但实现方式完全不同——前者是一次同步的 LLM 调用，后者是把 Claude Code 放进沙箱里让它自主"动手"编排。

---

## 一、AI 生成智能体

### 1.1 用户看到什么

用户在创建智能体时，输入一段文字描述（比如"帮我生成一个查询天气的智能体，能够根据用户位置返回天气信息"），系统几秒钟后返回一个完整的智能体配置方案，包括智能体的名称、使用场景描述、系统提示词（人设）。用户可以直接采用或在此基础上修改。

### 1.2 底层怎么工作

整个流程是一个同步的 HTTP 请求——用户提交描述后，后端构造一段精心设计的提示词发给大模型，大模型返回 JSON 格式的配置方案，前端展示给用户确认。

#### 第一步：接收用户描述

用户通过一个 REST 接口提交描述，核心参数就是一段文字（description），还可以可选传入一个已有智能体的 ID（用于在已有配置基础上迭代优化）。

#### 第二步：构造"AI 架构师"提示词

这是最关键的一步。系统不是简单地把用户描述转发给大模型，而是构造了一套精心设计的"架构师指令"，告诉大模型它现在的角色是"精英 AI 智能体架构师"，需要按六个步骤工作：

1. 提取核心意图——从用户描述中提炼出这个智能体要解决什么问题
2. 设计专家人设——为智能体设计一个专业的角色定位和行为风格
3. 构建全面的指令——写出详细的系统提示词，涵盖工作流程、约束条件、输出格式等
4. 优化性能——调整提示词让模型表现更好
5. 创建标识符——生成智能体的英文名称（用于内部标识）
6. 生成使用示例——描述这个智能体适合在什么场景下被调用

同时，如果用户传入了已有智能体的 ID，系统会从数据库中读出该智能体当前的系统提示词，包裹在上下文标签中一起发给大模型。这样大模型就知道"当前已有的人设是什么，需要在此基础上优化"。

还需要注意一个细节：提示词中明确要求输出内容（JSON 的 value）必须使用中文，保证生成的人设是中文的。

#### 第三步：调用大模型

系统通过内部统一的 LLM 调用网关发起同步请求。默认使用 Claude Sonnet 4 模型，温度设为 0.5（在创造性和确定性之间取平衡），最大输出 32000 Token，强制响应格式为 JSON 对象。

#### 第四步：解析返回结果

大模型返回的是一个 JSON 对象，包含三个字段：

- identifier——智能体的英文标识符（如 `weather-query-agent`）
- whenToUse——使用场景描述（如"当用户询问天气相关信息时使用此智能体"）
- systemPrompt——完整的系统提示词（人设的核心内容，可能长达数千字）

有时候大模型会把 JSON 包裹在 Markdown 代码块中返回，系统会自动用正则表达式提取出纯 JSON 再解析。

#### 第五步：返回前端，用户确认后保存

关键点：这个接口本身不直接保存到数据库。 它只返回生成结果给前端。前端展示给用户后，用户可以修改、确认，然后通过另一个保存接口把配置写入数据库。

这个保存接口的逻辑是遍历配置项，逐个写入通用的键值对配置表——如果某项配置已存在则更新，不存在则新增。

### 1.3 多轮对话机制

这个生成链路本身不支持真正的多轮对话——它是一次性的同步请求：用户提交描述 → 大模型生成 → 返回结果。

但系统通过"传入已有智能体 ID"的方式实现了一种"手动多轮"：用户第一次生成配置后保存，第二次如果想优化，可以传入已保存的智能体 ID，系统会把当前的人设作为上下文发给大模型，让大模型在此基础上改进。每次调用都是独立的，但通过传入已有配置来模拟迭代。

### 1.4 配置如何落地到容器

用户确认保存后，配置就存在数据库里了。当用户开始与这个智能体对话时，系统会从数据库加载全部配置，然后做一次"配置到文件的转换"——把人设、技能、知识库、子代理、MCP 配置等全部转换为 Claude Code 容器能识别的文件集：


|          |                                            |                             |
| -------- | ------------------------------------------ | --------------------------- |
| 配置项      | 转换为的文件                                     | 说明                          |
| 人设/系统提示词 | `CLAUDE.md`                                | 智能体的核心身份文件，Claude Code 自动读取 |
| 技能       | `.claude/skills/*.md`                      | 每个技能一个 Markdown 文件          |
| 子代理      | `.claude/agents/*.md`                      | 子代理配置，含 YAML 格式的元数据         |
| 自定义命令    | `.claude/commands/*.md`                    | 斜杠命令定义                      |
| 知识库      | `.claude/skills/knowledge-recall/SKILL.md` | 知识库检索技能                     |
| MCP 配置   | `.claude/mcp.json`                         | 外部工具服务配置                    |
| 全局设置     | `.claude/settings.json`                    | 运行时设置                       |


这些文件部署到容器的工作目录后，Claude Code 进程就会自动读取并"理解"自己是谁、有什么技能、能查什么知识库。

### 1.5 与普通对话的区别


|       |                  |                  |
| ----- | ---------------- | ---------------- |
| 维度    | AI 生成智能体         | 普通使用智能体对话        |
| 入口    | HTTP REST 接口     | WebSocket 长连接    |
| 大模型角色 | 充当"架构师"，生成配置     | 充当"智能体本身"，回答用户问题 |
| 状态    | 无状态，单次请求         | 有状态，支持会话上下文      |
| 流式输出  | 不支持（同步返回）        | 支持（打字机效果）        |
| 配置角色  | 生成的配置由用户确认后写入数据库 | 配置已在数据库中，每次对话时加载 |


### 1.6 设计亮点

AI 生成智能体的设计有两个亮点：

"架构师 Prompt"的设计：系统不是简单地把用户描述转发给大模型，而是构造了一套专业的"六步法"指令，让大模型像一位资深架构师一样思考——先理解意图，再设计人设，然后写提示词，最后优化。这保证了生成质量不会因为用户描述太简单而太差。

"生成与保存分离"：生成接口只负责生成，不负责保存。用户必须确认后才能写入数据库。这是一个重要的安全设计——避免 AI 生成的低质量配置直接覆盖已有配置。

## 二、AI 生成工作流

### 2.1 工作流是什么

在讨论 AI 生成工作流之前，需要先理解这个系统中"工作流"的概念。

工作流不是多个智能体之间的编排，而是单个智能体内部的一种能力——它是一系列"节点"的有向编排图，节点之间通过连线传递数据，最终完成一个自动化任务。比如"搜索网页 → 提取信息 → 填写表单 → 提交"就是一个工作流，包含 4 个节点依次执行。

工作流有两种存在形态：

传统工作流：通过 XML 描述节点和连线，由外部工作流引擎解释执行。XML 中包含开始节点（定义入参）、结束节点以及中间的各种工具节点。

AI 生成工作流：用户通过对话描述需求，AI（Claude Code）在沙箱容器中理解意图并自动编排节点和连线，生成工作流。

### 2.2 用户看到什么

用户描述一个需求（如"帮我创建一个自动化流程，先搜索某个关键词，然后把搜索结果填到表格里"），AI 开始"思考"——用户在前端看到 AI 的思考过程、工具调用过程、以及最终生成的工作流编排图。整个过程是流式的，用户可以实时看到 AI 在做什么。

### 2.3 底层怎么工作

这是一个比"AI 生成智能体"复杂得多的流程。生成智能体只是调一次 LLM API 拿回 JSON 配置，而生成工作流是把 Claude Code 放进一个沙箱容器里，让它自主操作——读文件、写代码、调用工具——最终编排出工作流。

#### 第一步：创建 SSE 连接

用户发起请求，后端创建一个 30 分钟超时的 SSE（Server-Sent Events）连接。SSE 是一种服务器向客户端单向推送数据的技术，适合流式输出场景。整个生成过程会通过 SSE 实时推送给前端。

请求来源有三种类型：AI 工作流、AI RPA 工作流、AI Groovy 工作流，三者的区别在于生成的代码类型不同。

#### 第二步：前置钩子链——准备运行环境

SSE 连接建立后，系统依次执行一组钩子（Hook），其中最关键的是工作空间初始化钩子，它负责：

等待工作空间就绪：Claude Code 需要在一个准备好的工作空间中运行——文件系统要挂载好、目录要创建好。系统轮询检查工作空间是否就绪，最多等待 60 秒。期间通过 WebSocket 向前端推送进度状态（"环境隔离完成"、"文件系统已就绪"、"工作空间初始化完成"等），让用户知道系统在做什么。

检查容器存活：检测 Claude Code 容器的 IP 和端口是否有效。如果容器已失效，从容器池中随机分配一个新容器。

扩展上下文变量：将租户 ID、环境信息、用户查询内容、会话上下文、上传文件等信息放入上下文变量中，供后续传递给 Claude Code。

#### 第三步：构建请求并调用 Claude Code

系统构建一个请求发给 Claude Code 容器，核心内容包括：

- query：用户的原始描述文本（如"帮我创建一个自动化流程，先搜索再填表"）
- projectId：Claude Code 工作空间对应的 Git 仓库名
- 工作目录：路径区分不同来源（AI 工作流 / AI RPA 工作流 / AI Groovy 工作流）
- 权限模式：默认设为"绕过权限检查"，让 AI 自主操作不需要逐个确认

然后通过 HTTP SSE 流式请求发给 Claude Code 容器的对话端点。Claude Code 在容器内运行，它本质上是一个增强版的大模型 Agent——拥有文件读写、代码执行、工具调用等完整能力。

#### 第四步：流式接收 AI 输出并转换为工作流节点

这是最核心的部分。Claude Code 的输出通过 SSE 逐条返回，每条数据包含类型和内容两个字段。系统将每条 SSE 数据转换为工作流节点数据，转换逻辑根据数据类型分多种情况：

状态更新类：如"思考中"、"执行中"、"完成"，更新聊天记录状态，不生成工作流节点。

流式文本类：AI 的文本输出（比如"让我分析一下你的需求..."），生成一个消息类型的节点，状态为"生成中"。这些文本片段会按节点 ID 合并成完整文本。

工具调用类：AI 调用某个工具（如读写文件、执行脚本），生成一个消息节点，记录工具调用的详细信息。如果标记为"待办任务"，则用工具 ID 作为节点 ID，标记为需要后续更新。

工具结果类：工具执行结果返回。如果包含技能调用信息，会解析技能 ID、参数、返回结果，并根据结果类型（直接展示/自定义话术/大模型润色/HTML 模板）生成不同的展示内容。

工作流 JSON 类：这是 AI 实际编排的工作流结构数据，包含项目 ID 和工作流数据。这是最终产物。

文件附件类：AI 生成的文件上传到 S3 后的附件信息。

思维导图类：AI 生成的思维导图。

RPA 操作类：RPA 操作节点，转换为工作流数据。

其他类型（思考过程、系统消息、Git 状态、版本信息等）也各自生成对应类型的消息节点。

#### 第五步：节点合并与快照管理

每收到一条 SSE 数据，系统做三件事：

1. 合并到当前快照：新生成的工作流节点按节点 ID 匹配——如果节点已存在则更新内容，不存在则追加。这实现了流式输出的累积效果。
2. 缓存到 Redis：快照缓存在 Redis 中，防止意外中断丢失数据。
3. 推送前端：合并后的快照通过 SSE 推送给前端，前端据此渲染工作流编排视图。当没有正在生成的节点时，快照也会持久化到数据库。

#### 第六步：生成工作流并持久化

当 AI 完成编排后，会通过工作流 JSON 类型的 SSE 数据返回最终的工作流结构。同时，系统调用外部工作流引擎的创建接口，在工作流引擎中创建工作流记录，包含工作流名称、描述、类型、空间 ID 等信息。

### 2.4 工作流的数据结构

工作流在前端展示为一组有序的节点内容列表，每个节点包含：

- 唯一标识：节点 ID
- 类型：消息节点、大模型调用、RPA 引擎调用、HTTP 请求、事件、业务节点、环境初始化等
- 状态：生成中、完成、错误、成功、暂停、等待问答等
- 内容：文本、JSON、工具调用信息等
- 消息子类型：Markdown 文本、HTML、工具调用、流式文本、思维导图、工作流 JSON、S3 附件等
- 流式标记：是否为流式数据
- 增量数据：用于流式合并

工作流在外部引擎中以两种格式存储：

XML 格式：包含开始节点（定义入参列表）、结束节点以及中间的各种工具节点标签。每个节点有工具 ID、工具描述、输出键、是否发送消息等属性。

JSON 格式：content 字段是一个 JSON 数组，每个元素是一个节点对象，包含类型（如 `startNode`）和节点数据（如入参列表）。

系统负责将这两种格式对齐：当 XML 中的入参为占位符时，从 JSON 中提取实际数据并替换。

### 2.5 工作流的执行

工作流生成后可以通过多种方式执行：

通过工作流引擎执行：传入工作流 ID、执行类型、全局变量、入参列表，由外部工作流引擎解释 XML/JSON 并逐节点执行。执行过程中通过 Redis Stream 消息队列推送执行进度，消费者读取这些消息并推送给前端。

在 Claude Code 对话中触发：当用户的命令以"workflow"开头时，系统构建工作流执行请求并触发执行，执行结果回传到对话流中。

暂停/继续：通过工作流引擎的运行时控制接口实现暂停和恢复，暂停状态缓存在 Redis 中。

### 2.6 节点类型

系统支持的工作流节点类型包括：

- 消息节点：最常见，包括 AI 文本、工具调用、思维导图、工作流 JSON 等子类型
- 大模型调用节点：独立的 LLM 调用
- RPA 引擎调用节点：自动化 UI 操作
- HTTP 请求节点：调用外部 API
- 事件节点：触发或响应事件
- 业务节点：业务逻辑处理
- 环境初始化节点：准备工作环境
- 其他：丢弃任务、暂停任务、调试消息、指令错误等

### 2.7 架构演进：从"LLM 直接编排"到"Claude Code 自主编排"

代码中保留了一套早期的工作流编排设计（在 `aiBuildWorkflow` 目录下），包含完整的任务节点定义、编排请求结构、LLM 对话结果等。这套设计计划让 ChatGPT 直接理解 PRD 并生成工作流节点列表。

但最终采用了"让 Claude Code 在沙箱中自主编排"的方案。原因是 Claude Code 作为全功能的 AI Agent，拥有文件系统访问、代码执行、工具调用等能力，能够更灵活地理解用户意图并生成复杂的工作流——它不只是"翻译"用户描述为 JSON，而是真正地"动手"探索、试错、验证，最终生成可执行的工作流。

这套早期设计的代码目前没有被主流程引用，属于架构演进留下的痕迹。

### 2.8 设计亮点

AI 生成工作流的设计有三个亮点：

"沙箱自主编排"而非"LLM 直接生成"：不是让大模型直接输出一段工作流 JSON，而是把 Claude Code 放进沙箱里让它自主操作。这意味着 AI 可以读文件了解上下文、写代码验证逻辑、调用工具测试效果——生成的工作流质量远高于纯文本生成。

"流式转换"机制：Claude Code 的 SSE 输出有多种类型（文本、工具调用、工具结果、工作流 JSON 等），系统设计了一套统一的转换层，把每种类型的 SSE 数据转换为工作流节点。用户可以实时看到 AI 的思考过程、工具调用过程和最终产物，体验非常好。

"快照合并"机制：流式输出的片段通过节点 ID 匹配进行合并——已存在的节点更新内容，新节点追加。同时缓存到 Redis 防止丢失，没有正在生成的节点时持久化到数据库。这实现了流式输出的"打字机效果"在工作流编排场景下的适配。

## 三、AI 生成智能体 vs AI 生成工作流

两者虽然都是"AI 自动生成"，但底层实现截然不同：


|       |                        |                           |
| ----- | ---------------------- | ------------------------- |
| 维度    | AI 生成智能体               | AI 生成工作流                  |
| 生成方式  | 同步调用 LLM API，一次返回 JSON | Claude Code 在沙箱中自主编排，流式返回 |
| 交互方式  | HTTP 同步请求              | SSE 流式推送                  |
| AI 角色 | "架构师"——生成配置文本          | "工程师"——读文件、写代码、调工具        |
| 复杂度   | 低（一次 API 调用）           | 高（容器管理 + 工作空间初始化 + 流式转换）  |
| 生成产物  | 智能体配置（名称、人设、提示词）       | 工作流编排（节点 + 连线 + 执行逻辑）     |
| 用户确认  | 必须确认后才保存               | 实时可见过程，生成后持久化             |
| 多轮迭代  | 通过传入已有 ID 模拟迭代         | 在同一个沙箱中持续对话               |


两者共享的底层能力包括：Claude Code 容器管理、工作空间初始化、SSE 流式通信、节点数据结构、消息合并逻辑等。AI 生成工作流是更"重"的操作——它需要完整的 Claude Code 沙箱环境，而 AI 生成智能体更多是调用 LLM API。

## 四、面试速答卡片

问：用户通过对话生成智能体，底层是怎么实现的？

答：整个流程是一次同步的 LLM 调用。用户提交文字描述后，后端构造了一套精心设计的"AI 架构师"提示词——告诉大模型它现在是一位精英架构师，需要按六步法工作：提取核心意图、设计专家人设、构建全面指令、优化性能、创建标识符、生成使用示例。提示词中还要求输出内容使用中文。然后通过内部 LLM 网关调用 Claude Sonnet 4 模型（温度 0.5），大模型返回一个 JSON，包含智能体的标识符、使用场景和完整系统提示词。生成结果返回前端，用户确认后通过保存接口写入数据库。生成接口本身不直接保存，这是一个安全设计——避免 AI 生成的低质量配置直接覆盖已有配置。

问：这个生成过程支持多轮对话吗？

答：生成链路本身不支持真正的多轮对话，它是一次性的同步请求。但系统通过"传入已有智能体 ID"的方式实现了一种"手动多轮"——如果用户想优化已有的智能体，可以传入该智能体的 ID，系统会把当前的人设作为上下文发给大模型，让大模型在此基础上改进。每次调用都是独立的，但通过传入已有配置来模拟迭代。

问：AI 生成工作流和 AI 生成智能体有什么区别？

答：最大的区别在于生成方式。生成智能体是同步调一次 LLM API 拿回 JSON 配置，简单直接。生成工作流则复杂得多——系统把 Claude Code 放进一个沙箱容器里，让它自主操作：读文件、写代码、调用工具，最终编排出工作流。整个过程通过 SSE 流式推送，用户可以实时看到 AI 的思考过程和工具调用过程。之所以用 Claude Code 而不是直接让 LLM 生成 JSON，是因为 Claude Code 拥有文件系统访问和代码执行能力，可以真正"动手"探索和验证，生成的工作流质量远高于纯文本生成。

问：AI 生成工作流时，Claude Code 的输出是怎么转换为工作流的？

答：Claude Code 的 SSE 输出有多种类型——流式文本、工具调用、工具结果、工作流 JSON、思维导图、RPA 操作等。系统设计了一套统一的转换层，把每种类型的 SSE 数据转换为工作流节点数据。每收到一条数据，就按节点 ID 合并到当前快照中——已存在的节点更新内容，新节点追加。快照同时缓存到 Redis 防止丢失，并在没有正在生成的节点时持久化到数据库。合并后的快照通过 SSE 推送给前端，用户可以实时看到工作流编排视图的演进。

问：生成的工作流怎么执行？

答：工作流最终在外部工作流引擎中创建记录，以 XML 和 JSON 两种格式存储。XML 包含开始节点（定义入参）、结束节点和中间的工具节点；JSON 包含节点的详细数据。执行时传入工作流 ID、执行类型、全局变量和入参列表，由工作流引擎逐节点解释执行。执行进度通过 Redis Stream 消息队列推送，消费者读取后推送给前端。还支持暂停/继续——通过运行时控制接口实现，暂停状态缓存在 Redis 中。用户也可以在 Claude Code 对话中直接触发工作流执行——当命令以"workflow"开头时自动构建执行请求。

问：代码中有一套早期的工作流编排设计，为什么最终没有使用？

答：早期设计计划让 ChatGPT 直接理解 PRD 并生成工作流节点列表——输入需求描述，输出一段 JSON。但这套设计的代码目前没有被主流程引用。最终采用了"让 Claude Code 在沙箱中自主编排"的方案，原因是 Claude Code 作为全功能的 AI Agent，拥有文件系统访问、代码执行、工具调用等能力，能够更灵活地理解用户意图并生成复杂的工作流。它不只是"翻译"用户描述为 JSON，而是真正地探索、试错、验证，最终生成可执行的工作流。这是从"LLM 作为翻译器"到"LLM 作为自主 Agent"的架构演进。
