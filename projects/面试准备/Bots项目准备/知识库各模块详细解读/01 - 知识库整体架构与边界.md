# 知识库整体架构与边界

> 本篇讲清楚"知识库这个功能在整个系统里到底处于什么位置"、"哪些是我们做的、哪些是别的团队做的"，以及"我们和外部服务之间怎么交互"。

---

## 一、知识库是做什么的

知识库是平台的"企业私有知识大脑"。用户可以把公司文档、操作手册、FAQ、技术规范等内容导入到知识库中，智能体在对话时可以自动检索这些知识，基于私有内容回答用户问题——这就是所谓的 RAG（检索增强生成）。

举个例子：你公司的客服智能体如果不知道退货政策是什么，它就没法回答用户"买了东西怎么退货"。但你把退货政策文档导入知识库后，智能体就能在对话时自动查阅并给出准确回答。

---

## 二、一个关键结论：核心能力不在本仓库

调研代码后最重要的发现是：知识库的核心能力（创建管理、文档解析、向量化存储、向量检索）并不在这个 Java 仓库里，而是在一个完全独立的兄弟服务（知识库专用服务）中。

本仓库（efficiency-agent-service）是知识库的"消费方"，只负责三件事：

1. 绑定管理：记录"哪个智能体绑定了哪些知识库"——就是一张配置表里存一个逗号分隔的 ID 列表
2. 技能化注入：把知识库变成智能体能理解的"技能说明书"文件，放到容器里让 AI 自己去查
3. 对话集成：在对话开始前提醒 AI "你有知识库可以用，遇到不懂的问题先查资料"

真正的文档解析（PDF 怎么拆页、Word 怎么提取文字）、文本分片（把长文档切成适合向量检索的短片段）、向量化计算（用 Embedding 模型把文本转成数学向量）、向量存储和检索引擎（在千万级向量中找到最相似的几条），全部在外部知识库服务中完成。

理解了这个架构边界，才能准确向面试官描述"我做的是什么部分"——你做的是"智能体平台侧的知识库集成"，不是"知识库引擎本身"。

## 三、三种交互方式

本仓库通过三种方式与外部知识库服务交互，每种方式用于不同场景：

### 方式一：SDK 直接调用

本仓库通过 Maven 依赖引入了知识库服务的 SDK 包（`com.waimai.frame.knowledgebase.api`），可以直接调用知识库服务提供的 Java 接口。

用到的 SDK 接口包括：

- `KbOvBaseService.getOvKbDetailById(kbId)` —— 查知识库详情（名称、描述）
- `KbOvSkillConvertService.getBinding(kbId, operator)` —— 查知识库是否已绑定了技能
- `KbOvSkillConvertService.convertToSkill(request, operator)` —— 把知识库转换成平台技能包

这种方式调用最直接，但依赖对方 jar 包版本——如果对方还没发版，新字段就用不了。后面会讲到 `kb_summary` 字段的故事就是一个典型例子。

### 方式二：HTTP 远程调用（Retrofit 客户端）

对于不需要 SDK 依赖的轻量交互，通过 Retrofit 客户端发 HTTP 请求：

- `KnowledgeApi`：基础知识库操作，包括查询（`/base_query`）、保存内容（`/save_content`）、删除内容（`/delete_content_by_ids`）
- `IntelliBaseApi`：智能知识库系统，包括持久化对话上下文（`/open/chat/context/add`）、按关联 ID 查节点等

Retrofit 客户端在配置类中统一注册，baseUrl 从 Apollo 配置中心读取（`knowledgeBase.domain` 和 `intelliBase.domain`），请求时自动注入鉴权 header。

### 方式三：Python 脚本中转

这是最特殊的一种方式，用于长期记忆系统。容器内运行着 Python 脚本（auto_[capture.py](http://capture.py) / auto_[recall.py](http://recall.py)），这些脚本不直接连接向量数据库，而是回调本仓库 Java 侧的开放接口（`/open/ovkb/data/mem/*`），Java 接口再透传给外部 OpenViking 向量服务。

形成了一个"容器 Python 脚本 → Java 中转 → OpenViking 服务"的三段式调用链。为什么不让 Python 直接调 OpenViking？因为鉴权逻辑、连接池管理、异常处理在 Java 侧统一维护更可靠。

## 五、面试怎么说

问：知识库的整体架构是怎样的？

答：知识库采用"消费方 + 引擎方"分离的架构。引擎方是一个独立的知识库服务，负责文档解析、分片、向量化、存储和检索。消费方是我们的智能体平台，只负责三件事：管理"哪个智能体绑定了哪些知识库"的绑定关系、把知识库变成 AI 能理解的"技能说明书"文件、以及在对话时提醒 AI 使用知识库。两个服务通过 SDK 调用、HTTP 接口和 Python 脚本中转三种方式交互，职责边界清晰。

问：为什么不把知识库功能直接做在智能体平台里？

答：两个原因。第一是职责分离——知识库引擎涉及大量专门的技术（文档解析、向量计算、相似度检索），由专门团队维护更专业。第二是独立迭代——引擎方可以优化检索算法而不影响对话流程，消费方可以改变注入方式而不影响底层存储。两个服务可以按各自节奏发版。
