# 知识库技能化原理——三代方案详解

> 本篇讲清楚"怎么把知识库变成 AI 能理解的技能文件"的三代技术方案，以及不同智能体类型分别走哪条路径。

---

## 一、什么是"知识库技能化"

知识库技能化，就是把知识库信息"翻译"成 AI 能读懂的文件，放到智能体容器里，让 AI 知道"自己有哪些知识库可以用、怎么查"。

打个比方：你给一个新员工发了公司的文档管理系统网址，但他不知道怎么用。你得给他一张"使用说明书"——上面写着"系统里有哪些文档库、每个库是关于什么的、怎么搜索"。知识库技能化就是生成这张"使用说明书"。

系统经历了三代方案演进，代码中三代逻辑并存，不同智能体类型走不同路径。

---

## 二、第一代方案：每个知识库一份独立说明书（已下线）

### 2.1 原理

每绑定一个知识库，就生成一个独立的技能文件夹（类似 `kb-知识库ID`），有几个知识库就有几份说明书。

生成的文件包括：

- SKILL.md：技能说明书，包含知识库名称、描述、调用命令（`ov-kb recall --kb-domain-id {kbId} --query "..."`）、安装方法、故障排查
- kb-meta.json：元数据文件，包含 kbId、kbName、description、kbSummary，用于后续识别和清理

### 2.2 代码实现

核心类是 `KbSkillArgsBuilder`，提供三个静态方法：

- `buildItems`：把逗号分隔的 kbId 列表解析为 JSONArray，每项包含 kbId/kbName/description/kbSummary
- `buildSkillMd`：生成 SKILL.md 全文（YAML 头部 + Markdown 正文）
- `buildMetaJson`：生成 kb-meta.json 文件内容

### 2.3 当前状态

已下线，代码保留但不被调用。`KbCcSkillResolver` 的注释明确说明"不再回退到旧的自建 kb-* SKILL.md 逻辑（已下线）"。

## 三、第二代方案：知识库转技能包（部分智能体在用）

### 3.1 原理

把知识库转换成平台统一的"技能包"（CcSkill）格式再安装。不再自己生成 SKILL.md，而是调用外部知识库服务的"转换"接口，由知识库服务生成标准技能包并发布到 S3，然后通过统一的技能安装入口安装到容器。

### 3.2 代码实现

核心类是 `KbCcSkillResolver`，主要方法：

- `installKbSkills(botUuid, knowledgeIndexs, skillsRelativePath)`：容器型 Bot 统一入口
  - 先调用 `resolveSkillUuids` 把 kbId 列表转为 CcSkill skillUuid 列表
  - 再调 `RemoteSkillInstallService.install()` 按 Bot 类型自动选模式安装

- `resolveSkillUuids(knowledgeIndexs, operator)`：kbId 到 skillUuid 的解析
  - 逐个 kbId 调 `resolveOne`
  - 单个解析失败标记 `degraded=true`，但不中断整体

- `resolveOne(kbId, operator)`：单个 kbId 到 skillUuid 的解析
  - 先查已有绑定（`getBinding`），命中且技能未失效（`skillMissing != true`）直接复用
  - 未绑定或已失效则调 `convertToSkill` 转换出新技能（默认发布到 S3）

### 3.3 当前使用者

- CodexBot（Codex 智能体）
- CursorBot（Cursor 智能体）
- GeminiBot（Gemini 智能体，通过 `resolveSkillUuidsForBot` + `installSkillsByIds` 写入数据库）

## 四、第三代方案：统一说明书 + 规则文件（当前主流）

### 4.1 原理

不管绑定几个知识库，统一只生成两份文件：

文件一：技能说明书（`.claude/skills/knowledge-recall/SKILL.md`）

内容来自 Apollo 配置中心的 `knowledge_recall` 模板，把 `{{kb_message}}` 占位符替换为已绑定知识库的 Markdown 表格行：

```Plain
| kb_domain_id | name | abstract |
|-------------|------|----------|
| 4015 | 退货政策文档库 | 包含退货流程、退款规则等 |
| 4023 | 商家入驻规范 | 商家入驻条件和审核流程 |
| 4099 | 技术开发规范 | 代码规范、接口设计规范等 |
```

表格里每行就是一个知识库的"名片"——ID、名称、摘要，让 AI 一眼就知道有哪些库可用。

文件二：使用规则（`.claude/rules/knowledge.md`）

内容来自 Apollo 配置中心的 `knowledge_rule`，原样落盘不做任何替换。提醒 AI 在什么情况下应该主动去查知识库。

### 4.2 代码实现

核心类是 `KbRecallContentBuilder`，主要方法：

- `build(knowledgeIndexs)`：
  - 调用 `buildKbMessageRows(knowledgeIndexs)` 把 kbId 列表渲染成 Markdown 表格数据行
  - 每行格式：`| {kbId} | {kbName} | {kbSummary} |`
  - kbName 来自 `KbOvBaseService.getOvKbDetailById()`
  - kbSummary 来自 `OvKbSummaryQueryMapper.selectKbSummaryByKbId()`（裸 SQL）
  - 表格单元格做转义处理（`sanitizeCell`）：换行替换为空格，竖线转义为 `\|`
  - 把模板中的 `{{kb_message}}` 替换为表格行
  - 返回 Content 对象（含 ruleContent 和 skillContent）

### 4.3 占位符设计的细节

模板使用 `{{kb_message}}` 而不是 `${kb_message}` 作为占位符。原因：`${...}` 会被 Spring 在解析 `@Value` 注入值时当成嵌套属性占位符递归解析，导致启动时报 `Could not resolve placeholder 'kb_message'` 错误。使用双大括号 `{{...}}` 避免了这个问题。

### 4.4 当前使用者

- ClaudeBot（Claude 智能体）：写入容器文件系统
- ClaudeBotBusiness（无状态企业版）：写入 `agent_project_files` 数据库表
- OpenClaw（OpenClaw 智能体）：通过 `install-knowledge-recall` 快捷命令写入

## 五、三代方案对比


|       |                  |                     |                 |
| ----- | ---------------- | ------------------- | --------------- |
| 维度    | 第一代（已下线）         | 第二代（部分在用）           | 第三代（主流）         |

## 七、全量覆盖语义

所有方案的 `installOrUpdateKnowledge` 都遵循先清理再安装的覆盖语义：

1. 清理阶段：删除所有历史知识库技能
  1. 容器型 Bot：调容器侧 `clean-kb-skills` 快捷命令，按 `kb-meta.json` 特征卸载
  2. 无状态 Bot：查 `agent_project_files` 表中含 `kb-meta.json` 的行，整目录删除

1. 安装阶段：按当前列表重建

1. 空列表处理：knowledgeIndexs 为空/null 时，仅清理不安装（清空知识库），同时删除 rule 文件和 knowledge-recall skill

## 八、面试怎么说

问：知识库技能化是什么意思？

答：就是把知识库信息"翻译"成 AI 能读懂的文件放到容器里。具体来说是生成两份文件——一份技能说明书告诉 AI "你有这些知识库可以用，查资料时执行这条命令"，一份规则文件提醒 AI 什么时候该查。AI 在对话时读到这些文件，就知道自己有知识库可用。

问：代码里有三代方案并存，这是怎么回事？

答：这是技术演进的痕迹。第一代是每个知识库生成一份独立的技能说明书，Java 端自己生成 SKILL.md 全文，目前已下线。第二代是调用外部服务把知识库转成标准技能包再安装，Codex/Cursor/Gemini 还在用。第三代是当前主流方案——不管绑多少知识库都只生成一份统一的说明书，文案模板放在 Apollo 配置中心可以热更新，Claude 和 OpenClaw 用这种方式。三代方案按智能体底座类型硬编码分流，新底座用第三代，老底座还在用第二代。这是典型的技术债——理想方案是全部收敛到第三代。

问：为什么用 `{{kb_message}}` 而不是 `${kb_message}` 做占位符？

答：因为 `${...}` 会被 Spring 在解析 `@Value` 注入值时当成属性占位符递归解析，导致启动时报 "Could not resolve placeholder" 错误。用双大括号 `{{...}}` 避免了 Spring 的属性解析机制，是一个实际的工程踩坑经验。

问：知识库说明书的文案能热更新吗？

答：第三代方案可以。说明书的文案模板存在 Apollo 配置中心，key 是 `knowledge_rule` 和 `knowledge_recall`。修改 Apollo 配置后，下次生成说明书时自动使用新文案，不需要重新发版。但第一代和第二代方案的文案是硬编码或由外部服务生成的，改文案需要发版或依赖外部服务更新。
