# 知识库创建与数据源导入

> 本篇讲清楚"知识库怎么创建"、"文档怎么导入"、"学城链接怎么抓取"以及"Cookie 传递机制"的原理。

---

## 一、知识库的创建

### 1.1 创建入口

用户创建知识库的操作不在本仓库，而是由外部知识库服务提供接口。本仓库在需要时（比如删除空间前检查是否有知识库）通过 SDK 调用外部服务来查询知识库列表。

这意味着本仓库的代码里没有"创建知识库"的接口——创建动作的 API 入口在外部知识库服务那边。本仓库只是一个"消费方"，在需要时读取知识库信息。

### 1.2 元数据管理

知识库的摘要信息（`kb_summary`）由外部服务用 AI 自动生成——分析知识库中的文档内容，生成一段概括性的描述文字。

这段摘要非常重要，因为它会被写入技能说明书的表格中，告诉 AI 模型"这个知识库是关于什么的"，帮助模型判断什么时候该检索哪个知识库。比如一个摘要写着"美团外卖商家入驻流程和规范文档库"，AI 看到用户问商家相关问题就会优先查这个库。

## 二、数据源导入方式

从本仓库能看到的入口来看，知识库支持两种数据导入方式。

### 2.1 文本片段导入

直接提交一组文本内容列表，每条文本被向量化后存入知识库。

具体实现是通过 `KnowledgeApi.saveContent` 接口（Retrofit POST `/save_content`），请求体是 `KnowledgeRequest` DTO，核心字段包括：

- `content_list` / `content_str`：文本片段内容
- `custom_ids` / `content_ids`：文本片段的唯一 ID 列表（保存时返回、删除时使用）
- `index_name`：索引名
- `embedding_type`：embedding 模型类型
- `index_media`：索引媒介（默认 es，可选 es/redis/milvus）

服务端收到请求后，对每段文本调用 Embedding 模型转成向量，写入指定的向量存储引擎，返回每段的 `content_id` 供后续删除使用。

### 2.2 学城 Wiki 链接导入

提交一个或多个学城（公司内部 Wiki 平台）的文档链接，系统自动抓取文档内容，解析后导入知识库。

请求体同样是 `KnowledgeRequest`，但用到的字段不同：

- `url` / `url_list`：学城 wiki 链接（单个或列表）
- `cookie`：当前登录人的 Cookie 信息
- `callback_url`：异步导入完成后的回调 URL
- `task_id`：异步任务 ID

### 2.3 Cookie 传递机制

这是一个值得展开讲的设计点。

学城（公司内部 Wiki 平台）的文档页面需要美团 SSO 登录态才能访问。知识库服务本身没有用户登录态（它是一个后端服务，不持有用户的 Session），无法直接读取受权限保护的学城文档。

解决方案是：前端把当前登录用户的 Cookie 透传给知识库服务，让服务端"借用户的身份"去抓取学城文档内容。这样保证了：

- 权限继承：用户只能导入自己有权限看的文档。如果用户没有某篇文档的阅读权限，用他的 Cookie 去请求会返回 403，导入失败
- 审计可追溯：所有导入操作都以特定用户身份执行，有迹可循

### 2.4 异步导入流程

学城 Wiki 链接导入是异步任务——因为爬取文档、解析内容、分片、向量化都需要时间，不能让 HTTP 请求一直阻塞。

流程：

1. 前端提交 wiki 链接 + Cookie + 回调 URL
2. 知识库服务立即返回任务 ID（表示"已接收，正在处理"）
3. 服务端在后台：爬取文档 → 解析内容 → 文本分片 → 向量化 → 写入存储
4. 完成后调用回调 URL 通知前端

### 2.5 实际的文档处理在外部

再次强调：实际的文档解析（PDF 怎么拆页、Word 怎么提取文字、网页怎么清洗 HTML）、文本分片（把长文档按段落或字数切成短片段）、向量化计算（调用 Embedding 模型把文本转成数学向量）全部在外部知识库服务完成。

本仓库的 `KnowledgeApi` 只是"转发"导入请求——把前端的参数组装好发给外部服务，不参与具体的文档处理逻辑。

## 三、数据导入的数据流

```Plain
方式一：文本片段导入

用户输入文本 → 前端组装 content_list
    │
    └──→ POST /save_content (KnowledgeApi)
         │
         └──→ 外部知识库服务:
              1. 对每段文本调用 Embedding 模型 → 得到向量
              2. 向量 + 原文写入存储引擎 (ES/Redis/Milvus)
              3. 返回 content_id 列表


方式二：学城 Wiki 链接导入

用户粘贴学城链接 → 前端带上 Cookie 提交
    │
    └──→ POST /save_content (KnowledgeApi)
         │  body: { url_list, cookie, callback_url, task_id }
         │
         └──→ 外部知识库服务 (异步):
              1. 用 Cookie 以用户身份请求学城页面 → 获取 HTML
              2. 解析 HTML → 提取正文内容
              3. 正文分片 → 切成适合向量检索的短片段
              4. 每个片段调用 Embedding 模型 → 得到向量
              5. 向量 + 原文写入存储引擎
              6. 调用 callback_url 通知前端完成
```

## 四、知识库内容的删除

删除通过 `KnowledgeApi.deleteContent` 接口（POST `/delete_content_by_ids`），传入 `content_ids` 列表，删除指定向量库中对应的内容。

这个接口在"知识库内容更新"场景下使用——先删除旧内容，再导入新内容。但具体的删除逻辑也在外部知识库服务中。

## 五、面试怎么说

问：知识库怎么导入数据？

答：支持两种方式。一种是文本片段导入——直接提交文本列表，服务端做 Embedding 后写入向量库。另一种是学城 Wiki 链接导入——提交文档链接和用户 Cookie，服务端用 Cookie 以用户身份爬取学城文档内容，解析分片后向量化入库。这个 Cookie 传递机制的设计考虑了权限继承——用户只能导入自己有权限看的文档。

问：导入是同步还是异步的？

答：文本片段导入是同步的，直接等结果返回。学城 Wiki 链接导入是异步的——因为爬取文档、解析、分片、向量化都需要时间。提交后立即返回任务 ID，后台处理完成后通过回调 URL 通知前端。

问：文档解析和向量化的代码在你们仓库里吗？

答：不在。文档解析、文本分片、向量化计算全部在外部知识库服务中完成。我们的仓库只是"转发"导入请求，把前端参数组装好发给外部服务。这是"消费方 + 引擎方"分离架构的体现——我们只负责绑定关系管理和对话集成，不负责底层的文档处理。
