# 知识库数据模型与存储

> 本篇讲清楚"知识库的数据存在哪里"、"长什么样"、"怎么读取"，包括绑定关系存储、知识库详情查询、摘要字段读取的技术陷阱。

---

## 一、知识库信息存在哪里

知识库的核心数据（文档内容、向量索引、分片结果）存在外部知识库服务的数据库中，本仓库能直接看到的数据只有两类。

### 1.1 知识库信息表

这张表在外部知识库服务的数据库里，表名是 `ov_knowledge_base_info`。本仓库能看到的字段包括：

- `id`：知识库主键（就是代码里的 kbId）
- `kb_name`：知识库名称
- `description`：知识库描述
- `kb_summary`：知识库摘要（由 AI 自动生成的知识库内容概述）

本仓库通过两种方式读取这张表的数据：

- SDK 方式：调用 `KbOvBaseService.getOvKbDetailById(kbId)` 获取知识库名称和描述，这是正常路径
- 裸 SQL 方式：通过 `OvKbSummaryQueryMapper` 直接查 `kb_summary` 字段，这是绕过 SDK 的特殊路径（原因后面讲）

### 1.2 智能体配置表

记录"哪个智能体绑定了哪些知识库"的核心数据，存储在 `agent_configs` 表中。

- 配置键：`knowledgeIndexs`
- 配置值：逗号分隔的知识库 ID 字符串，例如 `"4015,4023,4099"`

这个值在前端的表现是：用户在智能体配置页面勾选知识库，保存后后端把选中的 ID 拼成逗号分隔的字符串存进去。读取时按逗号拆分，逐个查询知识库详情。

### 1.3 前端展示数据

从前端视角看，知识库列表页展示的信息包括：

- ID 和名称
- 状态（启用/未启用）
- 知识单元数量（文档被切分后的片段数）
- 数据集数量（导入的数据源数）
- 被引用次数（被多少个智能体/工作流使用）
- 创建和更新时间
- 归属空间和租户

这些统计信息大部分由外部知识库服务提供，本仓库在查询详情时会逐个调 `KbOvBaseService.getOvKbDetailById` 查每个知识库的详情，组装成列表返回前端。

## 二、kb_summary 字段读取的技术陷阱

这是一个典型的"跨团队依赖导致的技术债"案例，在面试中讲出来能体现你对工程实践的理解。

### 2.1 问题背景

外部知识库服务新加了一个 `kb_summary` 字段（知识库摘要，由 AI 自动生成），但线上版本的 SDK 实体类 `OvKnowledgeBaseInfo` 还没有同步这个字段——同事的分支还没合并上线。如果直接调实体类的 `getKbSummary()` 方法，线上会报"找不到方法"的错误。

### 2.2 解决方案

本仓库创建了一个独立的 Mapper 接口 `OvKbSummaryQueryMapper`，不依赖实体类，直接用裸 SQL 查询单列：

```Java
@Select("SELECT kb_summary FROM ov_knowledge_base_info WHERE id = #{kbId} LIMIT 1")
String selectKbSummaryByKbId(@Param("kbId") Long kbId);
```

这个方案的本质是"绕过 ORM 实体类，直接走原始 SQL 查一个字段"。因为是单列查询，返回类型直接是 String，不需要实体类映射。

### 2.3 使用场景

`kb_summary` 字段在两个地方被使用：

1. 第一代方案（KbSkillArgsBuilder）：生成每个知识库的独立技能文件时，把摘要写入 [SKILL.md](http://SKILL.md) 的描述部分，帮助 AI 理解这个知识库是关于什么的
2. 第三代方案（KbRecallContentBuilder）：生成统一的知识库表格时，摘要作为表格的 `abstract` 列，告诉 AI 每个知识库的内容概要

两处调用都做了 try-catch 防御：查不到或异常时摘要留空，不影响主流程。这说明开发者知道这个方案不够健壮，做了兜底处理。

### 2.4 技术债的坦诚

这个方案是一个临时绕行手段。等外部知识库服务的 SDK 版本上线后，应该回归到通过实体类 getter 读取。但代码中的注释也坦诚说明了这个情况——这是跨团队协作中常见的技术债：你的功能依赖别人的字段，别人还没上线，你只能先绕过去。

## 三、召回策略类型

本仓库能看到的召回策略有两种，存储在智能体配置中。

### 3.1 默认知识库召回

直接调用知识库的向量检索能力，按语义相似度返回最相关的文档片段。AI 执行 `ov-kb recall --kb-domain-id {知识库ID} --query "问题内容"` 时走的就是这个路径。

### 3.2 自定义召回（走工作流）

不走默认检索，而是触发一个用户自定义的工作流来处理检索逻辑。比如：

- 先做意图识别（用户问的是技术问题还是行政问题）
- 再路由到不同知识库（技术问题查技术文档库，行政问题查行政制度库）
- 最后做结果过滤（只返回评分 > 0.8 的结果）

这给了高级用户自定义检索逻辑的能力，但配置复杂度也更高。

### 3.3 向量存储引擎

向量存储引擎支持三种：

- Elasticsearch：通用搜索引擎，支持全文检索 + 向量检索
- Redis：内存级速度，适合小规模知识库
- Milvus：专门的向量数据库，适合大规模向量检索

选择哪种引擎由知识库服务侧管理，本仓库在导入时通过 `index_media` 字段指定（默认 es）。

## 四、数据流转图

```Plain
用户在前端创建知识库
    │
    ├──→ 外部知识库服务创建记录 (ov_knowledge_base_info 表)
    │    字段: id, kb_name, description, kb_summary(AI生成)
    │
    └──→ 本仓库通过 SDK 可查询到这条记录

用户给智能体绑定知识库
    │
    └──→ 本仓库写入 agent_configs 表
         config_key = "knowledgeIndexs"
         config_value = "4015,4023,4099"

读取知识库列表时
    │
    ├──→ 按逗号拆分 knowledgeIndexs → [4015, 4023, 4099]
    │
    └──→ 逐个调用 KbOvBaseService.getOvKbDetailById(kbId)
         获取每个知识库的名称、描述等信息
         同时调用 OvKbSummaryQueryMapper.selectKbSummaryByKbId(kbId)
         获取摘要（绕过 SDK 实体类的裸 SQL）
```

## 五、面试怎么说

问：知识库的绑定关系怎么存储的？

答：用智能体配置表存储。配置键是 `knowledgeIndexs`，值是逗号分隔的知识库 ID 字符串，比如 `"4015,4023,4099"`。读取时按逗号拆分，逐个调外部知识库服务的 SDK 查详情。这种设计简单直接，但查询效率不是最优——如果有 10 个知识库就要查 10 次 SDK。不过知识库数量通常不多（一般 3-5 个），实际影响可忽略。

问：kb_summary 字段为什么用裸 SQL 查？

答：这是跨团队依赖导致的技术债。知识库服务新加了 `kb_summary` 字段，但线上 SDK 版本还没同步这个字段（同事分支未上线）。如果直接调实体类的 getter 会报方法找不到。所以我写了一个独立的 Mapper 接口，用裸 SQL 直接查这一列，返回 String 类型，完全绕过实体类映射。等对方 SDK 上线后应该回归到实体类 getter。两处调用都做了 try-catch 防御，查不到就留空，不影响主流程。
