# 知识库设计亮点与面试速答

> 本篇总结知识库模块的核心设计亮点，并提供面试高频问题的速答卡片。

---

## 一、五大设计亮点

### 亮点一："知识库技能化"——让 AI 自己查资料

最大的设计亮点是把知识库变成 AI 的"技能"而不是后端的"管道"。

传统 RAG 是后端做检索再拼提示词，这个系统是给 AI 一份说明书让它自己决定什么时候查、查什么、怎么用结果。这降低了后端复杂度，同时提升了检索的智能程度和结果质量。

面试价值：这个设计体现了"把决策权交给更智能的执行者"的架构思维——与其在后端写复杂的检索逻辑，不如让 AI 自己判断。这也是 AI Native 应用设计的典型范式。

### 亮点二："说明书热更新"——配置中心驱动

技能说明书的文案模板不是硬编码在 Java 代码里，而是放在 Apollo 配置中心。

这意味着可以随时优化说明书的措辞、调整使用指南、改变检索策略，而不需要重新发版。发版成本几乎为零。

面试价值：体现了"配置驱动"的工程理念——把可能频繁变化的内容从代码中抽离到配置中心，实现热更新。

### 亮点三："消费方与引擎方分离"——清晰的架构边界

知识库的创建、文档解析、向量化、检索引擎是一个独立服务（引擎方），智能体平台只负责绑定关系管理和对话集成（消费方）。

两个服务通过 SDK + HTTP + 回调三种方式交互，职责边界清晰。这使得两个服务可以独立迭代——引擎方可以优化检索算法而不影响对话流程，消费方可以改变注入方式而不影响底层存储。

面试价值：体现了"关注点分离"的架构原则——每个服务只做自己擅长的事，通过清晰的接口协作。

### 亮点四："双轨并行"——知识库检索 + 长期记忆

知识库解决"查企业预置知识"的问题，长期记忆解决"记住对话中学到的信息"的问题。

两者都用向量检索技术，但场景不同、触发机制不同、存储位置不同。双轨并行让智能体既有"专业知识"又有"个人记忆"。

面试价值：体现了"同一技术不同场景"的分层设计——不是用一个系统解决所有问题，而是根据场景特点分别设计。

### 亮点五：技术债的坦诚——三代方案并存

三代知识库技能化方案并存是一个典型的技术债案例：新方案更好但旧方案没有完全清理。

这在面试中可以坦诚地讲——说明你了解系统的历史演进，知道技术债的成因（不同智能体底座类型的差异），也知道理想方案是什么（统一收敛到第三代）。

面试价值：能坦诚地讨论技术债，说明你有工程判断力——不是所有技术债都需要立即清理，需要权衡投入产出比。

## 二、面试速答卡片

### 问：知识库的整体架构是怎样的？

答：知识库采用"消费方 + 引擎方"分离的架构。引擎方是一个独立的知识库服务，负责文档解析、分片、向量化、存储和检索。消费方是我们的智能体平台，负责三件事：管理绑定关系、把知识库变成技能说明书、在对话时提醒 AI 使用知识库。两个服务通过 SDK 调用、HTTP 接口和 Python 脚本中转三种方式交互。

### 问：知识库检索和传统 RAG 有什么不同？

答：传统 RAG 是"后端检索"——后端调向量数据库查出结果拼到提示词里。我们的系统是"AI 自主检索"——后端只往容器里放一份技能说明书，告诉 AI "你有这些知识库可以用，查资料时执行这条命令"。AI 在对话过程中自己判断是否需要检索、构造什么 query、怎么整合结果。好处是 AI 可以智能判断检索时机、自主构造更精准的 query、多次检索逐步缩小范围。

### 问：知识库变更后怎么同步到已绑定的智能体？

答：知识库服务在变更时会回调通知我们。收到通知后，系统反查所有绑定了这个知识库的智能体，整体重新生成每个智能体的技能说明书文件。如果知识库被删除了，还会把它的 ID 从绑定列表中摘除。这是"整体重建"而非"增量修改"的策略。

### 问：代码里有三代知识库方案并存，这是怎么回事？

答：第一代每个知识库生成独立说明书（已下线）；第二代把知识库转成标准技能包安装（Codex/Cursor/Gemini 在用）；第三代统一生成一份说明书，文案放 Apollo 配置中心可热更新（Claude/OpenClaw 在用）。三代按智能体底座类型硬编码分流。这是典型的技术债——理想方案是全部收敛到第三代。

### 问：知识库检索和长期记忆有什么区别？

答：知识库检索是查"企业预置的知识"——人主动导入的文档、FAQ、手册等，内容相对稳定。长期记忆是记住"对话中学到的信息"——AI 自动从对话中提取用户偏好、重要决定等事实存入向量库，下次对话时自动召回。两者都用向量检索但场景不同，双轨并行让智能体既有"专业知识"又有"个人记忆"。

### 问：知识库的权限怎么控制？

答：知识库依附于"空间"概念，一个知识库只能属于一个空间。用户能否访问取决于他在空间中的角色。不支持跨租户共享，共享粒度是整个知识库而非单篇文档——想让别人用就把人拉进空间。细粒度权限判断在外部知识库服务中。

### 问：kb_summary 字段为什么用裸 SQL 查？

答：跨团队依赖导致的技术债。外部知识库服务新加了 kb_summary 字段，但线上 SDK 版本还没同步（同事分支未上线）。直接调实体类 getter 会报方法找不到。所以写了独立 Mapper 用裸 SQL 直接查这一列，返回 String 类型，绕过实体类映射。两处调用都做了 try-catch 防御。

### 问：知识库技能化的占位符为什么用 `{{kb_message}}` 而不是 `${kb_message}`？

答：因为 `${...}` 会被 Spring 在解析 `@Value` 注入值时当成属性占位符递归解析，导致启动时报 "Could not resolve placeholder" 错误。用双大括号 `{{...}}` 避免了 Spring 的属性解析机制。这是一个实际的工程踩坑经验。

### 问：长期记忆的三路检索是什么？

答：三路并发检索——用户级记忆（跨所有智能体共享的个人偏好）、智能体级记忆（当前智能体专属沉淀）、技能知识（智能体绑定的技能相关知识）。三路结果合并后做两次去重，然后按五个维度加权重排（原始分数、叶子节点加权、事件意图匹配、偏好意图匹配、词面重叠度），取 TopN 注入对话上下文。

### 问：长期记忆怎么保证不影响正常对话？

答：整个设计遵循"失败不阻断"原则——任何异常都走放行逻辑，不注入记忆、不阻断对话。所有关键事件写本地日志。记忆功能失败时用户完全无感知。这是因为记忆是"锦上添花"的功能，不能因为记忆系统出问题就影响用户正常使用智能体。
