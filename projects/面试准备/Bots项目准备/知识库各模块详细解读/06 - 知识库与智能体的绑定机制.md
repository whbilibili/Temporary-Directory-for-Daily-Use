# 知识库与智能体的绑定机制

> 本篇讲清楚"用户绑定知识库后后端做了什么"、"知识库信息变更后怎么同步"、"说明书什么时候刷新"。

---

## 一、绑定操作的全流程

### 1.1 用户操作

用户在前端界面给一个智能体勾选知识库、点保存。这个操作触发后端的完整处理链路。

### 1.2 后端处理

后端做两件事：

第一步：存储绑定关系

把知识库 ID 列表（逗号分隔）作为一条配置记录存进智能体的配置表（`agent_configs`），配置键是 `knowledgeIndexs`，值是类似 `"4015,4023,4099"` 的字符串。

第二步：异步生成说明书文件

异步触发"生成说明书文件"的工作——把最新的知识库列表渲染成技能说明书和规则文件，写入容器（有状态智能体）或数据库（无状态智能体）。

### 1.3 触发入口

当用户保存 Bot 时（`AgentController.saveBot`），会触发 `BotProvider.onBotSaved(uuid, botInfo)`。各 Provider 在 `onBotSaved` 中检查 `botInfo` 是否包含 `knowledgeIndexs` 这个 key，如果包含就触发知识库技能化。

### 1.4 ThreadLocal 传递 botUuid

这里有一个技术细节：`BotProvider.installOrUpdateKnowledge(String knowledgeIndexs)` 接口签名只接收知识库列表，不包含 botUuid（哪个智能体）。但所有 Provider 实现都需要知道操作的是哪个 Bot。

解决方案是使用 ThreadLocal：调用方在调用前通过 `BotKnowledgeContext.with(uuid, () -> { ... })` 注入 botUuid，Provider 内部通过 `BotKnowledgeContext.currentUuid()` 取出。这是一个"用 ThreadLocal 绕过接口签名限制"的实用模式。

### 1.5 异步执行

知识库同步操作在大部分 Provider 中都是异步执行的（通过线程池提交），保证 saveBot 接口秒级返回。用户不需要等说明书生成完成，后台异步处理。

## 二、全量覆盖语义

所有 Provider 的 `installOrUpdateKnowledge` 都遵循先清理再安装的覆盖语义。这意味着每次保存都是"全量覆盖"——不管之前绑定了什么，全部清掉，按当前列表重建。

### 2.1 清理阶段

删除所有历史知识库技能：

- 容器型 Bot（Claude/Codex/Cursor）：调容器侧 `clean-kb-skills` 快捷命令，按 `kb-meta.json` 特征卸载
- 无状态 Bot（ClaudeBotBusiness/Gemini）：查 `agent_project_files` 表中 `.claude/skills/` 或 `.gemini/skills/` 路径下含 `kb-meta.json` 的行，整目录删除

### 2.2 安装阶段

按当前列表重建（走第二代或第三代方案，取决于 Bot 类型）。

### 2.3 空列表处理

`knowledgeIndexs` 为空或 null 时，仅清理不安装——相当于"清空知识库"功能，同时删除 rule 文件和 knowledge-recall skill。

## 三、知识库变更时的同步

### 3.1 回调通知

知识库信息发生变化时（改名、改描述、删除），外部知识库服务会主动回调通知本系统。

### 3.2 处理逻辑

本系统收到通知后：

1. 反查影响范围：查"所有绑定了这个知识库的智能体"——通过搜索 `agent_configs` 表中 `knowledgeIndexs` 值包含该 kbId 的记录
2. 整体重新生成说明书：把每一个相关智能体的说明书文件整体重新生成（不是增量修改）——重新查一遍所有绑定的知识库信息，重新渲染说明书
3. 处理删除场景：如果知识库被删除了，还会把这个 ID 从对应智能体的绑定列表里摘除

### 3.3 为什么用"整体重建"而非"增量修改"

整体重建策略简单可靠——不需要处理"新增一个知识库怎么插入表格"、"删除一个知识库怎么从表格移除"等复杂的增量逻辑。知识库数量通常不多（3-5 个），整体重建的性能开销可接受。

---

## 四、刷新时机

说明书的生成只在两个时机触发：

1. 保存智能体：用户在界面上修改了知识库绑定并保存
2. 知识库变更回调：外部知识库服务通知知识库信息变了

不会触发刷新的场景：

- 智能体的容器重启或创建时不会主动刷新知识库说明书
- 如果是从模板创建的智能体，说明书是模板里自带的，不重新生成

这个设计避免了不必要的刷新——如果知识库信息没变，就不需要重新生成说明书。

## 五、数据流图

```Plain
场景一：用户保存智能体

前端保存 Bot (含 knowledgeIndexs)
    │
    ├──→ AgentController.saveBot
    │      └──→ BotProvider.onBotSaved(uuid, botInfo)
    │             ├──→ 检查 botInfo.containsKey("knowledgeIndexs")
    │             └──→ 异步: BotKnowledgeContext.with(uuid, () -> {
    │                    installOrUpdateKnowledge(kbIdx)
    │                  })
    │
    ├──→ [第三代路径: Claude/OpenClaw]
    │      1. clean-kb-skills 清理旧技能
    │      2. KbRecallContentBuilder.build(kbIdx)
    │         → 渲染 Apollo 模板 + 知识库表格
    │      3. 落盘 rule + skill
    │
    └──→ [第二代路径: Codex/Cursor/Gemini]
           1. clean-kb-skills 清理旧技能
           2. KbCcSkillResolver.resolveSkillUuids(kbIdx)
              → 每个 kbId 转成 CcSkill
           3. RemoteSkillInstall.install 安装


场景二：知识库变更回调

外部知识库服务通知变更
    │
    └──→ 反查所有绑定了该知识库的智能体
         │
         └──→ 对每个智能体整体重新生成说明书
              ├──→ 重新查所有绑定的知识库信息
              ├──→ 重新渲染说明书文件
              └──→ 如果知识库被删除，从绑定列表中摘除
```

## 六、面试怎么说

问：知识库变更后怎么同步到已绑定的智能体？

答：知识库服务在知识库信息变更（改名、改描述、删除）时会回调通知我们的服务。收到通知后，系统反查所有绑定了这个知识库的智能体，然后整体重新生成每个智能体的技能说明书文件——重新查一遍所有绑定的知识库信息、重新渲染说明书。如果知识库被删除了，还会把它的 ID 从绑定列表中摘除。这是"整体重建"而非"增量修改"的策略，简单可靠但效率不是最优。

问：用户绑定知识库后，后端做了什么？

答：两件事。第一，把知识库 ID 列表存到智能体配置表里（逗号分隔的字符串）。第二，异步触发说明书生成——先清理旧的知识库技能文件，再按当前列表重新生成技能说明书和规则文件，写入容器或数据库。整个操作是异步的，保存接口秒级返回。

问：说明书什么时候会刷新？

答：只在两个时机刷新：用户保存智能体时、知识库变更回调时。容器重启或创建时不会主动刷新——如果是从模板创建的智能体，说明书是模板里自带的。这个设计避免了不必要的刷新，因为知识库信息没变就不需要重新生成。
