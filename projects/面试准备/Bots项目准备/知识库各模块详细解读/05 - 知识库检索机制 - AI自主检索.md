# 知识库检索机制——AI 自主检索

> 本篇讲清楚"为什么我们的 RAG 和传统 RAG 不同"、"AI 怎么自己查资料"、"后端在这过程中做了什么"。

---

## 一、核心理念：后端不检索，让 AI 自己检索

### 1.1 传统 RAG 的做法

传统的 RAG（检索增强生成）系统是这样的：

```Plain
用户提问 → 后端调向量数据库检索 → 把检索结果拼到提示词里 → 发给大模型 → 模型回答
```

后端是检索的执行者——后端代码负责调向量数据库、拿到结果、把结果拼接进提示词模板、再把拼好的提示词发给大模型。整个过程中大模型只是"被动地读"检索结果。

### 1.2 我们的做法

本系统的设计完全不同：后端不做检索。

后端做的事情是"教会" AI 怎么查资料——往容器里提前放好两份文件，让 AI 自己判断什么时候查、查什么、怎么用结果。

```Plain
对话开始前 → 后端提前把"说明书"放到容器里
对话进行中 → AI 自己读说明书，自己决定是否查资料，自己执行检索命令，自己理解结果
```

整个"调用命令 → 解析结果 → 组织回答"的过程完全发生在 AI 的推理过程中，后端只是提前把说明书放好，不参与也看不到具体检索过程。

## 二、放到容器的两份文件

### 2.1 技能说明书

路径：`.claude/skills/knowledge-recall/SKILL.md`

这份说明书告诉 AI：

- 你有哪些知识库可以用（一张 Markdown 表格，列出每个知识库的 ID、名称和摘要）
- 要查资料时，执行 `ov-kb recall --kb-domain-id {知识库ID} --query "问题内容"` 这条命令
- `ov-kb` 是一个内部 npm 包，安装方法是 `npm install @waimai/ov-kb-cli`
- 常见报错的排查方法

AI 读完这份说明书后，就"知道"了自己有知识库这个工具可用。

### 2.2 使用规则

路径：`.claude/rules/knowledge.md`

内容来自 Apollo 配置中心（`knowledge_rule` 配置项），提醒 AI 在什么情况下应该主动去查知识库。这个文件是纯文本，原样落盘不做替换，可以随时通过修改 Apollo 配置来更新规则内容。

## 三、对话时的检索流程

当用户与绑定了知识库的智能体对话时，整个流程如下：

### 3.1 对话开始前：后端唯一主动介入的地方

初始化钩子（`KbAppendSystemPromptHook`）在对话发起前检查智能体是否绑定了知识库。如果绑定了，往系统提示词后面悄悄加一句固定提示语：

> "当问题模糊或缺少信息需要提问用户时，优先使用知识库技能。"

这是后端唯一主动介入对话内容的地方——只加一句话提醒，不强制检索。

### 3.2 对话进行中：AI 自主检索

AI 模型在容器的沙箱里运行，它读到了前面的两份文件，知道自己有哪些知识库可以用。当它判断"这个问题需要查资料"时，就自己执行 `ov-kb recall` 命令。

这个命令在容器内调用知识库服务的向量检索 API，返回一段 JSON 格式的结果，包含：

- 相关文档片段内容
- 相似度评分
- 来源信息

### 3.3 结果整合

AI 模型自己读懂 JSON 结果、提取有用信息、组织成自然语言回答。如果第一次检索结果不够好，AI 可以自己决定换个关键词再查一次。

整个过程后端完全不参与。

## 四、为什么这样设计

### 4.1 智能判断

AI 可以根据对话上下文判断是否需要检索——不是每次都检索（浪费资源），也不是从不检索（错过信息）。比如用户说"你好"，AI 知道不需要查知识库；用户问"退货流程是什么"，AI 知道需要查。

### 4.2 自主构造查询

AI 可以构造比用户原始问题更精准的检索 query。比如用户问"那个东西怎么搞"，AI 结合上下文理解到用户问的是"API 部署流程"，就会用"API 部署流程"去检索，而不是用"那个东西怎么搞"。

### 4.3 多次检索

AI 可以先粗检索缩小范围，再细检索精确查找。传统 RAG 通常只检索一次，而 AI 自主检索可以多次迭代。

### 4.4 结果质量

AI 不是机械地把检索结果拼到回答里，而是理解检索结果后用自己的语言组织回答，质量远高于传统 RAG 的"拼接"方式。

### 4.5 架构简洁

后端不需要写复杂的检索逻辑、结果排序逻辑、提示词拼接逻辑，这些全部交给 AI 处理。后端只负责"把说明书放对位置"。

## 五、技术实现细节

### 5.1 Hook 执行链路

```Plain
用户发起对话
  → UnifiedSharedCodeAgentServiceImpl.beforeExecute(paramPassingDTO)
    → 一系列前置 Hook 依次执行:
      → queryReWriteHook (查询改写)
      → claudeAgentRecommendQuestionInitHook (推荐问题)
      → fileEnvCheckHook (文件环境检查)
      → kbAppendSystemPromptHook (知识库提示) ← 这里注入知识库提示语
```

### 5.2 提示语注入

`KbAppendSystemPromptHook` 检查 `agentConfigVO.getKnowledgeIndexs()` 是否非空。如果非空，把固定提示语写入 `dto.vars["kbAppendSystemPrompt"]`。

### 5.3 下游消费

在 `buildAgentRequest` 阶段，取出 vars 中的知识库提示语，通过 `KbPromptBuilder.mergeAppendSystemPrompt` 合并到 `appendSystemPrompt` 上，最终传给 AI 模型。

### 5.4 固定提示语

提示语是硬编码的：

```Plain
当问题模糊或缺少信息需要提问用户时，优先使用知识库技能。
```

## 六、与传统 RAG 的对比


|          |             |           |
| -------- | ----------- | --------- |
| 维度       | 传统 RAG      | 我们的方案     |
| 检索执行者    | 后端代码        | AI 自己     |
| 检索时机     | 每次都检索       | AI 自主判断   |
| 检索 query | 用户原始问题      | AI 自主构造   |
| 检索次数     | 通常一次        | 可多次迭代     |
| 结果使用     | 机械拼接        | AI 理解后组织  |
| 后端复杂度    | 高（检索+排序+拼接） | 低（只放说明书）  |
| 依赖 AI 能力 | 低           | 高（依赖推理能力） |

## 七、面试怎么说

问：知识库检索和传统 RAG 有什么不同？

答：传统 RAG 是"后端检索"——后端代码调向量数据库查出结果，拼到提示词里发给大模型。我们的系统是"AI 自主检索"——后端只往容器里放一份技能说明书，告诉 AI "你有这些知识库可以用，要查资料时执行这条命令"，AI 在对话过程中自己判断是否需要检索、构造什么 query、怎么整合结果。好处是 AI 可以智能判断检索时机、自主构造更精准的 query、多次检索逐步缩小范围，检索质量远高于固定管道。代价是依赖 AI 的推理能力来决定何时检索。

问：后端在检索过程中做了什么？

答：只做一件事——在对话开始前，通过一个 Hook 往系统提示词后面加一句"当问题模糊或缺少信息需要提问用户时，优先使用知识库技能"。这是后端唯一主动介入对话内容的地方。之后的检索、结果解析、回答组织全部由 AI 在容器沙箱中自主完成，后端看不到也不参与。

问：这种设计有什么风险？

答：主要风险是依赖 AI 的推理能力。如果 AI 能力不够强，可能会该检索时不检索，或者构造的 query 不够精准。但随着大模型能力不断提升，这个问题在缓解。另一个风险是检索过程不可观测——后端看不到 AI 具体查了什么、返回了什么，调试和监控比传统 RAG 难。但好处是架构简洁、检索质量高、可扩展性强。
