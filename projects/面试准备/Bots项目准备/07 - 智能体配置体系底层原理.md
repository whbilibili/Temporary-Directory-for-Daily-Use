# 智能体配置体系底层原理

> 项目：AI 智能体平台后端服务
>
> 定位：面向面试场景，用通俗语言解释"用户在前端配置了 XX 之后，底层发生了什么"
>
> 时间：2026.06

---

## 概述

当用户在前端创建一个 Claude 智能体（数字员工）时，会看到一个配置面板，包含 13 项配置，分为三大类：

基本设定：人设、记忆、模型、技能、知识库、Hooks、斜杠命令

扩展能力：对话体验、渠道接入、工作空间

发布与管理：权限管理、使用分析、Trace 追踪

本文档将逐一解释每项配置在底层是如何工作的——用户配置之后，数据存在哪里，对话时怎么生效，以及背后的设计思路。

---

## 一、人设（Persona）

### 用户看到什么

用户在"人设"页面填写智能体的名称、描述，以及一份 CLAUDE.md 文件——这个文件定义了智能助理必须遵守的底线规则、安全框架和核心价值观。本质上就是告诉 AI "你是谁，你应该怎么表现"。

### 底层怎么存储

人设信息分散在两张表中：

智能体基本信息表：存储名称和描述，这是智能体的"身份证"。

智能体配置表（一张通用的键值对表）：存储更复杂的配置。人设相关的两个键是：

- 系统提示词——人设的核心指令文本，告诉模型"你的角色定位、行为规范、回答风格"等
- CLAUDE.md 内容——底线规则和安全框架

为什么要分开存？因为系统提示词是"软指令"（引导 AI 的行为风格），而 CLAUDE.md 是"硬约束"（安全底线），两者在注入方式上有所不同。

### 保存时发生了什么

用户点保存后，后端做两件事：

第一，写数据库：名称和描述写入智能体基本信息表；系统提示词和 CLAUDE.md 内容写入配置表。

第二，同步到容器（仅 Claude Code 类智能体）：调用容器管理接口，把 CLAUDE.md 内容作为一个真实的文件写入容器工作空间的根目录。这一步很关键——Claude Code SDK 有一个内置约定：它会自动读取工作目录下的 CLAUDE.md 文件作为项目级系统指令。所以我们不需要在每次对话时通过 API 传入人设，而是把它写成文件让 Claude Code 自己读取。

### 对话时怎么生效

对话开始前，系统会执行一个"钩子链"（Hook Chain），其中初始化钩子是关键环节：

第一步：加载配置。从数据库读出这个智能体的全部配置，包括系统提示词。

第二步：变量替换。系统提示词中可以写占位符，比如 `${current_time}`（当前时间）、`${end_user_id}`（用户 ID）、`{{knowledge.xxx.description}}`（知识库描述）。钩子会把这些占位符替换成真实值。这样一来，人设就不是静态文本，而是可以根据运行时上下文动态变化的。

第三步：注入到模型，分两种路径：

- 传统工作流智能体：替换后的提示词直接作为系统提示词发给大模型
- Claude Code 智能体：不走 API 的系统提示词字段，而是通过之前写入容器的 CLAUDE.md 文件生效。Claude Code SDK 在每次对话时自动读取这个文件。此外，如果绑定了知识库，还会通过一个额外的 `append_system_prompt` 字段注入一句"优先使用知识库技能"的提示

### 设计亮点

人设配置最巧妙的地方在于文件化注入。传统做法是每次对话时通过 API 传系统提示词，但 Claude Code 的设计理念是"一切皆文件"——把人设写成 CLAUDE.md 文件，让 SDK 自己读取，既符合 Claude Code 的原生约定，又避免了每次对话都传输大量提示词文本。

## 二、记忆（Memory）

### 用户看到什么

用户可以打开或关闭智能体的"记忆"功能。开启后，智能体能够记住跨会话的历史信息，比如用户的偏好、之前讨论过的重要决定等。

### 底层怎么工作

系统中存在两套记忆机制，一套是主力方案，一套是遗留方案。

#### 主力方案：OpenViking 长期记忆

这是真正意义上的"语义记忆"——不是简单地把聊天记录塞回上下文，而是从对话中提取要点，存入向量数据库，下次对话时按相关性召回。

配置存储：在配置表中存两个键值对——开关（布尔值）和配置参数（JSON，如召回条数限制）。

记忆内容本身不在这个 Java 服务里，而是存在外部的向量数据库中（通过知识服务访问）。

开启记忆时发生了什么：当用户打开记忆开关并保存，后端会往智能体的容器中部署两个 Python 钩子脚本：

脚本一：自动召回（绑定到"用户发送消息"事件）

每次用户发消息时触发，执行以下流程：

1. 用用户的消息去向量数据库中搜索相关的历史记忆（同时搜索用户级记忆和智能体级记忆）
2. 对搜索结果做排序去重——按相关度评分、词汇重叠度、时效性等维度综合打分
3. 把最相关的记忆包装成 `<relevant-memories>` 标签，作为额外上下文注入到对话中

这就是记忆在对话中"生效"的方式：在用户消息送给模型之前，先附加上历史记忆作为背景信息。

脚本二：自动捕获（绑定到"智能体回复完毕"事件）

每次智能体回复完毕后触发，执行以下流程：

1. 读取本轮对话内容
2. 把对话文本发送给知识服务，由另一个大模型异步提取出值得记住的事实（如用户偏好、重要决定、关键信息）
3. 提取出的记忆存入向量数据库

整个记忆循环：对话结束 → 自动提取记忆 → 存入向量库 → 下次对话开始 → 自动召回相关记忆 → 注入上下文。这是一个跨会话持久的长期记忆系统。

#### 遗留方案：历史消息回放

这是早期的简单方案，配置包括历史消息条数等。本质上就是每次对话时把最近 N 条原始聊天记录塞回上下文。这个方案没有语义理解能力——它不理解对话内容的含义，只是机械地回放历史。目前主要用于控制上下文窗口中的历史消息数量，语义记忆部分已经完全由 OpenViking 方案接管。

### 设计亮点

记忆系统的设计理念是"记忆即检索"——不试图在模型内部维护状态，而是把记忆外化到向量数据库，每次对话时按需检索注入。这样做的好处是记忆可以跨会话持久、可以精确控制召回数量、可以按相关性排序，而且不影响模型本身的推理能力。

## 三、模型（Model）

### 用户看到什么

用户可以为智能体选择不同的 AI 模型（如 Claude 3.5 Sonnet、GPT-4o 等），并调整参数（温度、最大输出长度等）。还可以选择是否允许终端用户在对话时切换模型。

### 底层怎么存储

模型配置是一个三层结构：

第一层：平台模型目录（全局注册表）

这是一张全局表，记录平台支持的所有模型。每条记录包含丰富的信息：模型名称、最大输出 Token 数、上下文窗口大小、是否支持函数调用、是否支持视觉、是否支持推理、输入输出价格、速率限制等。还有两个关键字段——"是否已降级"和"降级替代模型名称"，用于故障切换。

配套的还有厂商表（如 OpenAI、Anthropic）、用户自配 API Key 表、租户自定义模型表、模型标签表（如"推理能力"、"视觉"）等。

第二层：智能体级模型配置

每个智能体有一个模型配置 JSON 对象，指定用哪个模型、温度、最大输出 Token、TopP、历史消息条数、是否允许用户切换模型等。存在配置表中。

第三层：会话级覆盖

用户在某次对话中临时切换了模型，这个选择存在会话信息中，只影响当前会话。

### 对话时如何选择模型

优先级从高到低：会话级覆盖 > 智能体级配置 > 降级替代

具体流程：

1. 初始化钩子启动时，先加载智能体级配置中的模型配置
2. 检查模型降级：去模型目录表查这个模型是否被标记为"已降级"。如果是，静默替换为管理员指定的替代模型。比如管理员把 GPT-4o 降级为 GPT-4o-mini，所有使用 GPT-4o 的智能体会自动切到 GPT-4o-mini，用户无感知
3. 应用会话级覆盖：如果当前会话有用户临时切换的模型配置，用"非空字段覆盖"的方式合并到智能体级配置上——用户显式设置的字段才覆盖，没设置的保持智能体默认值
4. 最终的模型名称和参数传入引擎，用于实际的 LLM 调用

### 模型降级机制

这是一个管理员手动操作的降级，不是运行时自动降级：

管理员通过后台接口把某个模型标记为降级状态，并指定替代模型。标记后，该模型被设为不可用，所有使用这个模型的智能体在对话时自动被替换为替代模型。管理员也可以取消降级，恢复原模型。

注意：代码中没有运行时自动重试或自动降级的逻辑。如果 LLM 调用失败，不会自动切换到备用模型。降级是一种事前的管理手段，不是事后的容错手段。

### 设计亮点

三层配置的设计让模型管理既有全局一致性（平台目录），又有个体灵活性（智能体级配置），还有临时适应性（会话级覆盖）。降级机制虽然是手动的，但通过"标记 + 加载时替换"的方式实现了对用户完全透明的故障切换。

## 四、技能（Skills）

### 用户看到什么

用户可以为智能体添加各种技能。技能本质上是打包好的能力模块——比如"定时提醒"技能、"知识库检索"技能、"团队协作"技能等。每个技能包含一份给 AI 看的指令文档，还可以包含执行脚本和参考文档。

### 底层怎么存储

平台采用了"外部技能市场 + 本地绑定关系"的双层存储：

技能本体（包括文件内容、发布版本等）存储在外部技能市场微服务中，每个技能有一个唯一 ID 和对应的 S3 下载地址。

智能体与技能的绑定关系存储在本地配置表中，配置键记录了逗号分隔的技能 ID 列表。另外还有一个键记录已安装到容器中的技能信息（从容器刷新回来的实际状态）。

对于无状态智能体（没有常驻容器的类型），技能文件直接存在项目文件表中，路径形如 `.claude/skills/{技能名}/SKILL.md`。

### 安装到容器的流程

用户在前端为智能体配置技能后，保存时触发安装流程：

1. 从配置表读出绑定的技能 ID 列表
2. 调用外部技能市场服务，用 ID 换取每个技能的 S3 下载地址
3. 根据智能体的部署类型选择安装方式：
  1. 有状态容器：通过 HTTP 调用容器上的 shell 脚本，脚本从 S3 下载压缩包，解压到容器的 `.claude/skills/` 目录
  2. 无状态容器：后端直接从 S3 下载，在内存中解压，写入项目文件表
4. 安装完成后，技能文件就存在于容器的文件系统中了

### 对话时技能怎么生效

技能的生效方式取决于技能是"预装"还是"对话时引用"：

预装技能：保存智能体配置时就已安装到容器文件系统的 `.claude/skills/` 目录下。Claude Code 运行时会自动扫描这个目录，把技能内容纳入可用工具集。对话时无需额外注入——技能文件就在磁盘上，Claude Code 自己会发现并使用它们。

对话时 @引用的技能（用户在聊天中输入 `@某技能`）：通过钩子链处理。关键钩子是文件环境检查钩子，它的工作流程是：

1. 从用户消息的上下文中提取被 @引用的技能
2. 根据部署类型路由：无状态容器把技能包信息附加到请求中，运行时在启动对话前临时下载注入；有状态容器直接调用容器的下载解压接口
3. 对话结束后，清理钩子负责卸载那些 @引用但不属于智能体常驻配置的技能，避免技能残留

内置团队协作技能：打包在项目的资源目录下，包含协作通信、任务分解、共享工作区执行等技能。这些技能安装到会话隔离的路径下，在协作会话开始时注入。

### 设计亮点

技能体系的核心设计理念是"后端管配置，容器管执行"。后端只负责绑定关系管理和文件下载分发，技能真正的运行时逻辑完全由 Claude Code 原生处理——它扫描 `.claude/skills/` 目录，读取技能定义，在对话中按需调用。这种设计让技能系统具有极强的扩展性：新增一个技能只需要打包文件、上传到技能市场，不需要改任何后端代码。

## 五、知识库（Knowledge Base）

### 用户看到什么

用户可以为智能体绑定一个或多个知识库。绑定后，智能体在回答用户问题时可以检索知识库中的文档内容，实现基于私有知识的问答。

### 底层怎么工作

这个系统的知识库实现有一个关键设计理念：后端不做 RAG 检索，而是把知识库"技能化"，让 Agent 自己在对话中调用外部检索工具。

### 存储方式

知识库内容存储在外部知识库微服务中，本仓库不存储任何知识库文档内容。

智能体与知识库的绑定存在配置表中，值是逗号分隔的知识库 ID（如 `"4015,4023,4099"`）。

外部知识库平台在知识库变更或删除时，会通过回调通知本服务，触发绑定了该知识库的所有智能体更新技能文件。

### 配置生效流程：把知识库变成技能文件

当用户保存智能体配置时，触发知识库技能文件的生成。核心逻辑分两步：

第一步：清理旧文件。通过清理命令清除标记为知识库技能的旧文件。

第二步：生成新文件。写入两个文件到智能体工作空间：

文件一：规则文档（`.claude/rules/knowledge.md`）——固定的规则文档，告诉 Agent 知识库使用规范。

文件二：知识库检索技能（`.claude/skills/knowledge-recall/SKILL.md`）——一个技能定义文件，其中包含一个动态生成的 Markdown 表格，列出所有绑定的知识库的 ID、名称和摘要。这个文件告诉 Agent："你拥有这些知识库，当用户提问时可以用 `ov-kb recall --kb-domain-id {知识库ID} --query "问题"` 命令去检索。"

### 对话时怎么生效

知识库在对话时的生效分两层：

第一层：系统提示词提醒。在钩子链中，知识库追加钩子检查智能体是否绑定了知识库。如果有，就在上下文中写入一条提示语："当问题模糊或缺少信息需要提问用户时，优先使用知识库技能。" 这条提示附加在系统提示词后面发给大模型。这一层的目的是"提醒"模型主动使用知识库技能——因为模型不一定总是会主动调用技能。

第二层：Agent 自主检索。对话进行中，Claude Code Agent 如果认为需要查知识库，就会执行 `ov-kb recall` 命令（这是一个外部命令行工具），传入知识库 ID 和查询文本。这个命令会调用知识库服务的 API，执行向量相似度检索，返回 JSON 格式的检索结果。Agent 解析这些结果后，将相关内容融入回答。整个检索过程发生在容器的沙箱内，由 Agent 自主决策调用，本 Java 后端不参与。

### 设计亮点

知识库的实现方式很独特：传统做法是后端做 RAG 检索然后把结果拼到提示词里，而这个系统把知识库变成了一个"技能"——生成技能文件告诉 Agent "你有这些知识库可以用"，然后让 Agent 自己决定什么时候检索、检索什么内容。这样做的好处是：Agent 可以根据对话上下文智能判断是否需要检索（不是每次都检索），可以自主构造检索 query（比用户原始问题更精准），还可以多次检索（先粗检索再细检索）。代价是依赖模型的推理能力来判断何时检索。

## 六、Hooks（定时触发器）

### 用户看到什么

用户可以在对话中对智能体说"每天早上 10 点提醒我查看昨日报告"或"3 分钟后再问一次"，系统会自动创建定时触发器，到时间后自动向智能体发送预设的消息。

### 底层怎么工作

这里的"Hook"不是代码层面的钩子链，而是面向用户的定时触发器。它的核心场景是"定时让智能体执行某个任务"。

### 架构：跨服务协作

触发器的数据持久和调度执行由外部工作流服务负责（使用 XXL-Job 调度），本仓库只负责：

- 提供 Agent 侧的执行器（接收触发器调度，把预设消息发给智能体）
- 接收执行引擎的回调，更新运行状态

### 用户怎么配置

用户配置触发器不是通过 REST API，而是通过一个名为 `timer-skills` 的 Claude Code 技能。当用户在对话中说"每天 10 点提醒我"时，Agent 会调用这个技能，技能中的 Python 脚本通过 HTTP 调用外部触发器 API，创建一条触发器记录。

可配置内容包括：

- 名称：触发器显示名称
- 触发时间：支持 Cron 表达式（周期触发）、指定时间点（一次性触发）、延迟触发（"3 分钟后"）、时间窗口内周期触发（"下午 4-5 点每 10 分钟"）
- 执行内容：触发时要发给智能体的提示词文本，相当于用户输入的消息
- 会话模式：是每次触发新建会话，还是在固定会话中继续对话
- 启用/禁用：可以随时开关

### 触发后发生了什么

1. 外部工作流服务的调度器根据 Cron 表达式到时间触发
2. 调度器调用本仓库的任务执行器，读取触发器参数中的预设提示词
3. 解析/创建会话，然后把这条消息像用户输入一样发给智能体
4. 智能体正常走对话流程处理这条消息，产生的聊天记录标记为"定时触发"来源
5. 对话处理完成后，更新触发器运行记录的状态（成功/失败）

### 设计亮点

Hooks 的设计体现了"对话即配置"的理念——用户不需要去配置面板填写 Cron 表达式，而是直接在对话中用自然语言告诉智能体自己的需求，Agent 自动解析意图、生成 Cron 表达式、创建触发器。这大大降低了定时任务的使用门槛。

## 七、斜杠命令（Slash Commands）

### 用户看到什么

用户可以为智能体配置自定义的斜杠命令。比如配置一个 `/review` 命令，内容是一段代码审查的提示词模板。用户在对话中输入 `/review` 时，系统自动加载这个模板，相当于用户输入了那段提示词。

### 底层怎么工作

这个项目有两套"斜杠命令"系统：

第一套：用户自定义命令——用户在前端为智能体配置的命令，是对话中真正使用的斜杠命令。

第二套：平台快捷命令——平台管理的运维脚本，用于备份、恢复、安装技能等操作，不参与对话流程。

#### 用户自定义命令

定义和存储：用户在前端配置的自定义命令存储在配置表中，每个命令包含三个字段——命令名称、Markdown 格式的提示词正文、是否启用。

如何生效：写入文件，交给 Claude Code 原生处理

这是最关键的理解点：后端不解析、不拦截用户在对话中输入的 `/xxx`。 斜杠命令的执行完全由容器内的 Claude Code 原生处理。

后端的角色是"把命令定义推送到容器文件系统"：

1. 用户保存智能体配置时，检测到命令配置变更
2. 遍历所有启用的命令，通过 HTTP 调用容器 API 创建文件：`.claude/commands/{命令名}.md`，文件内容就是用户配置的提示词正文

一旦这些 `.md` 文件存在于容器的 `.claude/commands/` 目录中，Claude Code 就会原生识别它们为斜杠命令。当用户在对话中输入 `/review` 时，Claude Code 自动加载 `.claude/commands/review.md` 的内容作为提示词模板，注入到对话上下文中。整个过程不需要后端 Java 代码参与。

双向同步：系统还实现了从容器到数据库的反向同步。当获取智能体详情时，后端会读取容器中 `.claude/commands/` 目录下的文件内容，如果发现与数据库存储的不一致（比如用户在容器内直接修改了命令文件），就用容器版本更新数据库。这意味着容器文件系统是最终事实来源。

#### 平台快捷命令

这是一套独立的运维脚本系统，和对话流程无关。每个命令包含名称、描述、脚本类型（Python/Shell）、脚本内容、参数定义。内置命令包括备份、恢复、安装技能、卸载技能、系统信息、导出工作区等十余个运维命令。通过 REST API 触发执行，后端通过 HTTP 调用容器的脚本执行接口，在容器内执行脚本并返回结果。

### 设计亮点

斜杠命令的设计体现了 Claude Code 架构的核心哲学："文件即配置"。后端不需要理解命令的含义，不需要解析命令的参数，只需要把命令定义写成文件，Claude Code 自己会识别和使用。这与技能、知识库的设计思路一脉相承——后端是"文件搬运工"，运行时逻辑交给 Claude Code。

## 八、对话体验（Conversation Experience）

### 用户看到什么

用户打开一个智能体后看到的一切"非对话内容"——开场白、预设问题按钮、输入框提示文字、背景样式、快捷操作按钮、以及 AI 自动生成的推荐问题。

### 底层怎么存储

对话体验配置存储在配置表中，每一项一个键值对：

- 开场白：用户进入对话时自动展示的欢迎语
- 预设问题：JSON 数组，展示为可点击的问题按钮
- 输入框提示文字：占位提示
- 开场白展示风格：整数编码控制展示样式
- 背景配置：JSON 格式的对话界面背景设置
- 快捷操作：JSON 数组，每项有图标、描述、触发内容
- 推荐问题策略：控制推荐问题的生成方式

当用户打开对话界面，前端通过 API 获取这些配置渲染界面。开场白和预设问题还支持 AI 自动生成——系统用大模型根据智能体的系统提示词自动撰写。

### 推荐问题（最复杂的部分）

推荐问题有三种模式：AI 自动生成（默认）、自定义提示词、关闭。

当模式为"AI 自动生成"时，每轮对话结束后，一个专门的钩子异步触发：

1. 取最近几轮对话历史
2. 拼一个"请根据对话生成 3 个用户可能接下来要问的问题"的提示词
3. 调用一个轻量级模型（如 gpt-4o-mini）生成推荐问题
4. 结果存到聊天记录表的推荐问题列中缓存起来

前端请求推荐问题时，如果已缓存则直接返回，否则现场生成。这种"异步生成 + 缓存"的设计避免了推荐问题阻塞对话主流程。

### 应用级覆盖

还有一层"应用级"配置，允许在应用维度覆盖欢迎语、占位文字、快捷操作等。同一个智能体在不同应用里可以有不同的对话体验——比如在内部工具中展示完整的开场白，但在嵌入到其他系统时只显示简洁版。

### 设计亮点

对话体验的核心设计是"配置即界面"——所有的 UI 元素都是后端可配置的，前端只是一个通用渲染器。这使得非技术人员也能通过配置面板调整智能体的交互界面，不需要改前端代码。

## 九、渠道接入（Channel Integration）

### 用户看到什么

用户可以让智能体接入大象、飞书、钉钉、Bridge（自定义适配器）等外部 IM 平台，实现"在哪里都能用这个智能体"。

### 底层怎么工作

#### 配置存储

渠道配置同样存储在配置表中，每个渠道一个配置键：

- 大象：存机器人 ID 和应用配置（含 appId、appSecret）
- 飞书：存应用配置（含 appId、appSecret、encryptKey）
- 钉钉：存应用配置（含 appKey、appSecret、cardTemplateId）

#### 用户配置渠道后发生了什么

- 大象：不需要长连接，大象平台收到消息后会回调后端的接口。后端通过机器人 ID 反查配置表找到对应的智能体。
- 飞书/钉钉：应用启动时，长连接管理器扫描所有配置了飞书/钉钉的智能体，为每个建立 WebSocket 长连接。新增配置后需要重启或触发重新扫描。
- Bridge：外部适配器主动连接后端的 Bridge WebSocket 端点，注册时声明自己关联的智能体 ID 和支持的能力（文本、图片、文件、工具调用等）。

#### 消息路由全流程

1. 消息从各渠道进入，被对应的渠道适配器接收
2. 统一转换为标准入站消息格式
3. 中央编排器依次执行：路由解析 → 快捷命令拦截（如 `/new`）→ 转换为对话请求 → 会话查找/创建 → 注入渠道上下文（这一步至关重要，它把渠道信息带进异步处理链路）→ 发起异步对话
4. 智能体处理完后，流式输出的每条消息通过分发器读取上下文中的渠道信息，找到对应的渠道适配器，调用其发送方法
5. 各渠道的发送方式不同：大象更新"独占卡片"实现流式效果，飞书用 CardKit 流式卡片，钉钉用 AI Card，Bridge 通过 WebSocket 发送 JSON 消息

每个渠道+聊天类型（单聊/群聊）在会话表中用不同的类型值区分，同一用户在不同渠道的对话互相独立。

### 设计亮点

渠道接入的核心设计是"统一接口 + 多态实现"。所有渠道实现同一个标准接口，消息进来时统一转换为标准格式，消息出去时由各渠道适配器自行处理展示方式。这种设计让新增渠道只需要实现一个适配器，不需要改动核心对话逻辑。

## 十、工作空间（Workspace）

### 用户看到什么

智能体的"文件系统"——用户可以上传文件、管理文档、配置工作目录。这些文件在对话时可以被智能体使用。

### 底层怎么工作

工作空间包含三个层次：

#### 核心层：智能体项目文件（数据库支撑的虚拟文件系统）

这是一张项目文件表，存储智能体的配置文件和业务文件。文本文件内容直接存在 MySQL 中（避免小文件的网络开销），二进制文件存 S3。文件通过 `scope` 字段分四层：

- 全局配置层：全局 Claude Code 配置（挂载到 `/etc/claude-code/`）
- 用户层：用户级配置（挂载到 `~/.claude/`）
- 项目层：智能体专属文件（挂载到 `~/workspace/`）
- 本地覆盖层：如 `CLAUDE.local.md` 等本地覆盖文件

对话时这些文件怎么生效：当智能体的沙箱容器启动时，系统从项目文件表查出所有文件，打包成压缩流，然后在容器内解压到对应目录。Claude Code 进程启动后，这些文件就在磁盘上了——CLAUDE.md 作为系统提示词、skills 目录下的技能包、.mcp.json 的 MCP 配置等，都原生地被 Claude Code 读取。

对话过程中，Claude Code 进程还能通过文件系统接口实时读写这些文件（增删改查都走数据库/S3），实现"工作空间随对话演进"。

#### 资产中心（用户级文档管理）

这是用户级的文档管理（类似网盘），支持文件夹树、版本管理、分享。文件内容存 S3。它与对话没有直接注入关系，但对话结果可以保存到资产中心。

#### 用户上传的附件怎么进入对话

用户发送带附件的消息时，系统在消息前面加上 `@文件名` 引用，并追加下载命令让沙箱下载文件。同时根据文件类型添加处理提示——比如 Excel 文件会自动追加"使用 openpyxl 库读取"的提示。

### 设计亮点

工作空间的设计理念是"数据库即文件系统"。用数据库表模拟文件系统，文本内容直接存在 MySQL 中，避免了大量小文件的 S3 网络开销。同时通过 `scope` 字段实现了文件分层挂载，让 Claude Code 容器看到的文件结构与原生开发环境完全一致。容器启动时的"物化"操作把数据库中的虚拟文件变成磁盘上的真实文件，是一个优雅的"虚拟到物理"的转换过程。

## 十一、权限管理（Permission Management）

### 用户看到什么

控制谁能创建、编辑、使用、发布智能体，以及多租户隔离。

### 底层怎么工作

权限分四层，从外到内逐级收紧：

#### 第一层：租户（Tenant）

最顶层的组织边界。每个用户操作都在租户范围内。租户有 owner、admin、spaceCreator 等角色，控制谁能创建团队空间。

#### 第二层：空间（Space）

租户内的组织单元。每个用户自动拥有一个"个人空间"。空间有四级角色：

- Owner（所有者）：全权管理空间
- Admin（管理员）：管理成员和资源
- User（使用者）：使用空间内的资源
- Viewer（查看者）：只读访问

角色可以分配给个人，也可以分配给部门/团队（通过部门路径匹配实现批量授权）。

#### 第三层：资源 ACL（访问控制列表）

每个智能体有一套 ACL，记录谁是管理员、编辑者、可用者，支持按部门批量授权。还支持"从空间继承权限"——设置后智能体的 ACL 自动与所在空间同步。

#### 第四层：可见性（permiss 字段）

智能体自身有一个可见性字段，决定访问策略：

- 公开：所有人可用
- 公开且可查看配置：所有人可用且可查看配置
- 私有：仅 ACL 中的管理员和编辑者可用
- 空间保护：ACL 中的管理员、编辑者和查看者都可用

#### 运行时怎么生效

列出智能体时，系统逐个检查当前用户是否为 owner、admin、rd、usableMis 之一，结合可见性字段计算出 `canUse`（能否使用）和 `canEdit`（能否编辑）标记。

平台管理后台的所有接口通过 AOP 切面统一拦截，只有超级管理员（配置中心维护的名单）才能访问。

#### 发布和上架流程

智能体有 debug（草稿）和 normal（发布版）双版本。发布时 debug 版本复制到 normal；上架到市场需要审批，上架后可见性自动变为公开，下架后恢复私有。还支持通过分享码创建独立分享链接，可设置有效期和访问次数限制。

### 设计亮点

权限管理的四层设计实现了"组织 → 空间 → 资源 → 可见性"的逐级收紧。每一层都有自己的管理界面和授权方式，但又通过"继承"机制实现了层间的联动。双版本（草稿/发布）的设计让智能体的迭代不影响线上用户。

## 十二、使用分析（Usage Analytics）

### 用户看到什么

智能体的运营数据仪表盘——谁在用、用了多少、效果如何、花了多少钱。

### 底层怎么工作

#### 数据采集（实时）

- 每条对话消息写入聊天记录表，记录响应耗时、用户反馈（点赞/点踩）、Token 消耗、对话状态
- 每个会话在会话信息表记录会话元数据和累计 Token 用量
- 用户操作（点赞、收藏）写入操作记录表
- 浏览量通过资源属性表的字段实时递增

#### 数据聚合（每日批处理）

外部调度器每天调用统计刷新接口，执行三步聚合：

1. 把前一天的对话记录和会话数据汇总到统计表（每个智能体每天一行），计算：会话数、调用次数、成功次数、总响应时间、点赞/点踩数
2. 把每用户的使用记录写入用户记录表
3. 计算浏览量的日增量

#### Token 和费用数据

通过 HTTP 接口调用外部的 Provider 服务获取——按智能体/按会话/按租户维度的 Token 消耗和费用（人民币），包含输入/输出 Token 分别统计、按模型和工作流的费用明细。

#### 分析仪表盘提供的数据维度

- 关键指标卡片：活跃智能体数、总费用、总 Token、总调用次数、活跃用户数、单次平均费用
- 趋势图：对话轮次趋势、活跃用户趋势、浏览量与活跃用户趋势、点赞/点踩/满意度趋势、性能趋势（平均响应时间、成功率、首 Token 延迟）
- 排行榜：按对话量/活跃用户/费用排序的智能体列表
- 单个智能体详情：分 5 个维度——基本信息、费用指标、使用指标、效率与性能、关键归因（最贵的模型和工作流）
- 会话日志：分页查询每个会话的消息条数
- 用户统计：某智能体的每个用户的会话数、轮次、反馈、最后使用时间

查询层使用 10-20 线程的专用线程池并行执行多个异步任务，多维数据同时查询返回，避免串行等待。

### 设计亮点

使用分析的设计是"实时采集 + 离线聚合 + 并行查询"的三层架构。实时采集保证数据不丢失，离线聚合降低查询压力，并行查询保证仪表盘的响应速度。Token 和费用数据由外部 Provider 服务提供，实现了计费逻辑与业务逻辑的解耦。

## 十三、Trace 追踪（Skill 维度追踪）

### 用户看到什么

不是简单的对话日志，而是从"技能维度"追踪智能体的执行过程——某个技能在某次对话中被调用了几次、成功率多少、平均耗时多少、Token 消耗多少。

### 底层怎么工作

Skill Trace 的核心难点在于：通用 Trace 系统记录的是整段对话的所有事件（模型调用、工具调用、连接事件等），一条对话可能触发多个技能，事件混杂在一起。系统需要从中"切出"属于某个特定技能的那部分。

#### 整个链路分两个阶段

阶段一：关联记录（近实时）

前端在识别到技能工具调用完成时，调用后端 API 上报一条关联记录，写入关联表（"这个会话用了这个技能"）。这一步只做标记，不做任何分析。

阶段二：物化落库（定时批处理）

定时任务周期执行以下流程：

1. 扫描候选：查关联表中尚未物化的记录
2. 拉取原始 Trace：从公司统一的 Trace 服务按会话 ID 拉取该会话的全部事件流
3. 窗口切片：从事件流中找到目标技能的触发点，确定时间窗口的起止点
4. LLM 归因（核心创新）：把窗口内的事件片段发给大模型，让模型判断哪些步骤真正属于当前技能的主执行链（PRIMARY）、哪些只是相关但非核心（SECONDARY）、哪些纯属上下文（CONTEXT）。模型输出经过严格校验——只能引用窗口内真实出现的事件 ID，不允许编造
5. 组装产物：根据 LLM 的归因结果，构建执行时间线和工具调用明细，Token 统计只算主执行链的步骤
6. 落库：结果存入技能追踪表，标记关联表为已物化

如果 LLM 不可用（未配置或调用失败），回退到规则式兜底——只保留匹配到的技能工具调用行。

#### 用户能看到什么

- 技能维度的运行日志列表：每个技能被调用了多少次、成功率、平均耗时、Token 消耗、工具调用数量、触发者、用户当时的问题摘要
- 单条 Trace 详情：完整的执行时间线（每个步骤的类型、归因等级、耗时）和工具调用明细，用于排查问题
- 可观测性指标：系统暴露了关联写入数、物化成功/失败次数、LLM 评测通过率等监控计数

### 设计亮点

Trace 追踪最大的创新是"用 LLM 做 Trace 归因"。传统的 Trace 系统只能按时间顺序展示事件，无法判断哪些事件属于同一个逻辑操作。这个系统用大模型理解事件之间的因果关系，把混杂的事件流切分成清晰的技能执行链，大大提升了可观测性的精度。同时设计了规则式兜底机制，保证 LLM 不可用时系统仍然能工作。

## 总结：13 项配置的共性设计模式

回顾这 13 项配置，可以发现几个贯穿始终的设计理念：

### 1. "文件即配置"——后端是文件搬运工

技能、知识库、斜杠命令、人设（CLAUDE.md）这四项配置的共同特点是：用户在前端配置后，后端把配置内容写成文件放到容器的 `.claude/` 目录下，然后 Claude Code 原生识别和使用这些文件。后端在对话时的参与度很低——它只负责"把文件放对位置"，运行时逻辑完全交给 Claude Code。

### 2. "配置表即存储"——通用的键值对模型

几乎所有配置都存在一张通用的键值对配置表中（agent UUID + config_key → config_value）。这种设计的好处是新增配置项不需要改表结构，缺点是配置值的类型和语义完全由代码层保证，数据库层面无法约束。

### 3. "钩子链即扩展点"——统一的对话增强机制

人设注入、知识库提醒、推荐问题生成、技能临时安装……这些对话时的增强逻辑都通过钩子链实现。每个增强逻辑是一个独立的钩子，按固定顺序执行，通过共享上下文传递数据。这种设计让新增增强逻辑不需要改动核心对话流程。

### 4. "外部服务即能力"——不自建重能力

知识库内容存在外部知识库服务，记忆存在外部向量数据库，技能包存在外部技能市场，Token 计费由外部 Provider 服务提供。本系统专注于"智能体编排"，重能力全部外接。这种设计让系统保持轻量，同时可以灵活替换底层服务。

### 5. "两层版本即安全网"——草稿与发布分离

智能体有草稿版和发布版双版本，所有配置变更先在草稿版上修改，确认无误后发布到正式版。这保证了用户在修改配置时不会影响线上正在使用该智能体的其他用户。

## 面试速答卡片

问：智能体的人设是怎么生效的？

答：用户在前端填写的人设信息分两部分存储——名称和描述存在基本信息表，系统提示词和 CLAUDE.md 内容存在配置表。保存时，CLAUDE.md 内容会被写入容器工作空间的根目录，Claude Code SDK 自动读取这个文件作为项目级系统指令。对话时，初始化钩子会加载系统提示词并做变量替换（如当前时间、用户 ID），然后注入到模型。对于 Claude Code 类智能体，主要通过 CLAUDE.md 文件生效；对于传统工作流智能体，通过 API 的系统提示词字段生效。

问：记忆功能是怎么实现的？

答：系统有两套记忆机制。主力方案是 OpenViking 长期记忆——用户开启后，后端往容器部署两个 Python 钩子脚本：一个在用户发消息时触发，用消息去向量数据库搜索相关历史记忆并注入上下文；另一个在智能体回复完毕后触发，用大模型从对话中提取值得记住的事实存入向量数据库。整个循环是"对话结束→提取记忆→存入向量库→下次对话→召回记忆→注入上下文"。遗留方案是简单的历史消息回放，把最近 N 条消息塞回上下文。

问：模型降级机制怎么工作？

答：模型配置是三层结构：平台模型目录（全局注册表）→ 智能体级配置 → 会话级覆盖。对话时按"会话级 > 智能体级 > 降级替代"的优先级选择模型。降级是管理员手动操作——把某个模型标记为降级并指定替代模型，之后所有使用该模型的智能体在配置加载阶段自动替换为替代模型。注意这是事前管理手段，不是运行时自动容错。

问：技能是怎么安装和生效的？

答：技能本体存在外部技能市场，绑定关系存在本地配置表。用户配置技能后，后端从技能市场获取下载地址，根据智能体类型选择安装方式——有状态容器通过 HTTP 调用容器上的 shell 脚本下载解压到 `.claude/skills/` 目录，无状态容器直接写入项目文件表。对话时，Claude Code 自动扫描 skills 目录发现技能。对话中 @引用的技能通过钩子链临时安装，对话结束后自动清理。

问：知识库和传统的 RAG 有什么不同？

答：传统 RAG 是后端做检索然后把结果拼到提示词里。这个系统把知识库"技能化"——生成一个技能文件告诉 Agent "你有这些知识库可以用"，然后让 Agent 自己决定什么时候检索、检索什么内容。后端只负责绑定关系管理和技能文件生成，真正的向量检索发生在 Agent 运行时调用外部知识库服务的 CLI 工具时。好处是 Agent 可以智能判断是否需要检索、自主构造检索 query，代价是依赖模型的推理能力。

问：斜杠命令是后端解析的吗？

答：不是。后端完全不解析用户在对话中输入的 `/xxx`。后端的角色是把用户配置的命令定义写成 `.claude/commands/{命令名}.md` 文件放到容器中，之后 Claude Code 原生识别这些文件为斜杠命令。用户输入 `/review` 时，Claude Code 自动加载对应的 .md 文件内容作为提示词模板注入对话。后端还实现了双向同步——可以从容器读取命令文件更新数据库，保证容器文件系统是最终事实来源。

问：工作空间是怎么实现的？

答：工作空间是一个数据库支撑的虚拟文件系统。文本文件内容直接存在 MySQL 中（避免小文件的网络开销），二进制文件存 S3。文件通过 scope 字段分四层（全局配置/用户级/项目级/本地覆盖）。容器启动时，系统从数据库查出所有文件打包成压缩流，在容器内解压到对应目录，实现"虚拟到物理"的转换。对话过程中 Claude Code 还能通过文件系统接口实时读写这些文件。

问：Trace 追踪的核心创新是什么？

答：核心创新是"用 LLM 做 Trace 归因"。通用 Trace 系统记录的是整段对话的所有事件，事件混杂在一起。系统分两阶段工作：第一阶段近实时记录"这个会话用了这个技能"的关联关系；第二阶段定时从 Trace 服务拉取原始事件流，用大模型理解事件之间的因果关系，把混杂的事件切分成清晰的技能执行链，并分类为 PRIMARY（主执行链）、SECONDARY（相关但非核心）、CONTEXT（纯上下文）。如果 LLM 不可用则回退到规则式兜底。
