# 01 - 整体架构设计

> **定位**：AI 智能体平台后端服务的整体架构设计详解，面向面试场景

> **关键词**：三层抽象、策略路由、Redis Stream、模板方法、管道过滤器

## 一、平台定位与背景

### 1.1 这个平台是做什么的？

简单来说，这是一个 **AI 智能体的托管和编排平台**。打个比方，它就像「AI Agent 的应用商店 + 运行引擎」：

- **应用商店**：用户可以在平台上创建、配置、发布各种类型的 AI 智能体——有的擅长写代码，有的擅长回答问题，有的擅长做数据分析
- **运行引擎**：用户通过网页、大象、飞书、钉钉等多种渠道与智能体对话，平台负责把消息路由到对应的 AI 引擎，再把结果流式返回

平台底层接入了多种 AI 引擎能力（Claude Code、OpenClaw、Gemini 等），将它们统一封装为上层智能体。同时还支持多个智能体组成「团队」协作完成复杂任务。

### 1.2 技术栈


|       |                      |                      |
| ----- | -------------------- | -------------------- |
| 层面    | 技术选型                 | 选型原因                 |
| 后端框架  | Spring Boot          | 团队熟悉、生态完善            |
| ORM   | MyBatis + XML 映射     | 灵活控制 SQL、复杂查询场景多     |
| 数据库   | MySQL                | 事务一致性保障（协作状态机依赖）     |
| 缓存/消息 | Redis + Redis Stream | 已有基础设施、Stream 支持消费者组 |
| 实时通信  | WebSocket            | 全双工、适合流式输出           |
| 部署    | Docker 容器化           | 引擎隔离、弹性扩缩容           |




### 1.3 规模数据

- 约 40+ 个 Controller（REST + WebSocket 入口）
- 约 100+ 个 Service（业务逻辑层）
- 约 200+ 个数据库实体类
- 支持 7 种智能体类型
- 协作体系基于 8 张核心表构建

## 二、系统模块划分



### 2.1 三个 Maven 模块

项目拆分为三个模块，各司其职：

**核心业务模块（agent-api）**：这是平台的"心脏"，负责所有核心运行时逻辑——智能体对话、Bot 容器管理、渠道适配、消息处理、协作调度。用户发的每一条消息、智能体的每一次回复，都经过这个模块。

**运营管理模块（platform-api）**：这是平台的"后台管理办公室"，提供智能体发布审核、统计分析、租户管理、空间管理、模板管理等运营能力。管理员在这里审核用户提交的智能体、查看使用数据。

**内联服务（frame-inline-service）**：轻量辅助模块，处理内部请求转发和跨域配置。代码量很小，就一个启动入口和一个 CORS 过滤器。

### 2.2 模块间的依赖关系

```Plain
platform-api  ──依赖──▶  agent-api  ──依赖──▶  frame-inline-service
     │                        │
     └──── 共享父 POM ────────┘
```

platform-api 依赖 agent-api 的领域模型和服务接口，但不应该反向依赖（架构红线：禁止跨层调用）。

### 2.3 一个具体场景说明

以"用户创建智能体到发布上线"为例：

1. 用户在**前端页面**填写智能体名称、选择引擎类型（Claude/OpenClaw/Gemini）、配置技能 → 请求发到 **agent-api** 的控制器
2. **agent-api** 的 Service 层创建智能体记录、初始化容器（调用 BotProvider）、安装技能 → 数据写入 **MySQL**
3. 用户测试通过后提交发布审核 → **agent-api** 更新状态为"待审核"
4. 管理员在**管理后台**（platform-api）看到待审核列表 → 审核通过 → 调用 **agent-api** 的接口更新状态为"已发布"
5. 其他用户在应用商店看到这个智能体 → 开始使用

## 三、分层架构



### 3.1 三层架构设计

在核心模块内部，采用经典的 Controller → Service → DAO 三层架构：

**Controller 层**：接收 WebSocket 和 HTTP 请求，做参数校验和路由分发。不写业务逻辑，只做"交通指挥"。

**Service 层**：承载所有业务逻辑编排——对话执行、容器管理、协作调度、消息处理。这里是代码最密集的地方，100+ 个 Service 按功能域划分为 chat/、bot/、channel/、collab/、stream/ 等子包。

**DAO 层**：通过 MyBatis 与 MySQL 交互。200+ 个实体类对应数据库表，100 个 Mapper 接口 + 90 个 XML 映射文件定义 SQL。

### 3.2 一个完整请求链路示例

以"用户在网页上发一条消息给 Claude 智能体"为例：

```Plain
第 1 步：前端通过 WebSocket 发送消息
    → ChatWebsocketTextHandler（Controller 层）
    → 解析消息，判断是哪种智能体

第 2 步：路由分发
    → ChatServiceRouter（Service 层入口）
    → 根据 capacityType 选择对应的 ChatService 实现
    → 比如选择了 UnifiedSharedCodeAgentServiceImpl

第 3 步：前置处理
    → beforeHook 链依次执行
    → 权限检查 → 会话初始化 → 知识库注入 → ...

第 4 步：执行骨架
    → 获取分布式锁 → 构建请求 → 发送给 Claude 容器
    → Claude 容器处理后，流式响应写入 Redis Stream

第 5 步：消费和推送
    → Stream 消费服务读取消息
    → 通过 WebSocket 推送给前端（打字机效果）

第 6 步：后置处理
    → afterHook 链执行
    → 记录日志 → 协作状态检测 → 统计

第 7 步：持久化
    → 聊天记录通过 DAO 层写入 MySQL
```



### 3.3 WebSocket 入口 vs HTTP REST 入口


|       |                          |                                     |
| ----- | ------------------------ | ----------------------------------- |
| 对比维度  | WebSocket                | HTTP REST                           |
| 适用场景  | 实时对话（流式输出）               | 管理操作（CRUD）                          |
| 通信方式  | 全双工持久连接                  | 请求-响应                               |
| 典型接口  | `/chat`（发消息、收回复）         | `/api/v1/agent/session/list`（查会话列表） |
| 入口处理器 | ChatWebsocketTextHandler | 各 XxxController                     |


同一个功能可能同时有两个入口：比如"停止对话"既可以通过 WebSocket 发停止指令，也可以通过 HTTP POST 调用停止接口。

## 四、核心设计：三层抽象统一封装多种 AI 引擎

这是整个平台最核心的架构设计。

### 4.1 问题背景

平台需要支持多种完全不同的 AI 引擎：


|             |                     |                         |              |
| ----------- | ------------------- | ----------------------- | ------------ |
| 引擎          | 运行方式                | 通信方式                    | 状态管理         |
| OpenClaw    | 有状态长驻容器（Node.js 进程） | WebSocket（Bridge 协议）    | 容器内维护对话上下文   |
| Claude Code | Docker 容器里的编码沙箱     | HTTP API + Redis Stream | 无状态，每次传完整上下文 |
| Gemini      | 容器化运行               | HTTP API                | 有状态/无状态两种模式  |
| Cursor Bot  | 共用 Claude 镜像        | HTTP API                | 无状态          |


如果每种引擎都写一套完整的对话逻辑，代码会极其臃肿，而且新增引擎时改动量巨大。因此需要一套统一的封装架构。

### 4.2 第一层：引擎适配层（策略模式 + 注册表）

**设计思路**：定义统一的"Bot 生命周期管理接口"，每种引擎实现自己的版本。

**接口定义的标准操作**：

```Plain
创建容器    createAndInitContainer()
销毁容器    destroyContainer()
探活        keepalive()
重启        restart()
停止        stop()
技能安装    installOrUpdateKnowledge()
详情填充    fillDetailResponse()
模板绑定    onTemplateBound()
```

**Spring 自动注册机制**：Spring 启动时扫描所有实现了该接口的 Bean，调用 `capacityType()` 方法获取类型标识，存入一个 `Map<String, BotProvider>`。运行时根据智能体的类型从 Map 中取出对应的 Provider。

**伪代码展示**：

```Java
// 统一接口
public interface BotProvider {
    String capacityType();  // 策略标识，如 "claudeBot"、"openClawBot"
    void createAndInitContainer(String uuid, String userId, ...);
    void destroyContainer(String uuid, String userId);
    boolean keepalive(String uuid);
    // ... 其他方法
}

// 注册表（Spring 自动注入所有实现）
@Service
public class BotProviderRegistry {
    private final Map<String, BotProvider> providerMap = new HashMap<>();

    @PostConstruct
    public void init() {
        // Spring 注入所有 BotProvider Bean
        for (BotProvider provider : providers) {
            providerMap.put(provider.capacityType(), provider);
        }
    }

    public BotProvider getProvider(String capacityType) {
        return providerMap.get(capacityType);
    }
}
```

**新增一个引擎需要做什么**：

```Plain
1. 实现BotProvider接口，定义 capacityType() 返回新类型标识
2. 实现创建/销毁/探活等生命周期方法
3. 实现ChatService接口（对话执行逻辑）
4. 在路由器中添加新类型的路由规则

不需要改动任何上层代码！
```

**目前已接入的 7 种类型**：


|              |                   |      |                      |
| ------------ | ----------------- | ---- | -------------------- |
| 类型           | 标识                | 有无状态 | 容器镜像                 |
| Claude Bot   | claudeBot         | 容器型  | aigc-claude-code     |
| Codex Bot    | codexBot          | 容器型  | aigc-claude-code（共用） |
| Cursor Bot   | cursorBot         | 容器型  | aigc-claude-code（共用） |
| OpenClaw Bot | openClawBot       | 容器型  | openclaw 镜像          |
| Gemini Bot   | geminiBot         | 容器型  | gemini 镜像            |
| Claude 企业版   | claudeBotBusiness | 无状态  | 无需容器                 |
| Gemini 无状态   | geminiBot(无状态)    | 无状态  | 无需容器                 |




### 4.3 第二层：对话执行骨架（模板方法模式）

**设计思路**：不同引擎的对话流程宏观步骤是一样的，只是细节不同。

**统一骨架的步骤**：

```Plain
1. beforeHook()           → 前置处理链
2. doPrepare()             → 准备工作（配额检查等）
3. checkQuota()            → 权益校验
4. buildTrigger()          → 构建触发器（怎么发起请求）
5. buildHandler()          → 构建处理器（怎么处理响应）
6. acquireStreamLock()     → 获取分布式锁
7. consumeStream()         → Redis Stream 阻塞消费
8. afterHook()             → 后置处理链
```

**每种引擎只需要实现差异化的部分**：

- `buildRequest()` — 怎么构建请求（OpenClaw 构建 JSON 消息，Claude 构建代码执行请求）
- `getServerUrl()` — 发给哪个地址（OpenClaw 发给 Bridge WebSocket，Claude 发给容器 HTTP API）
- `getStreamMessageHandler()` — 怎么处理响应（OpenClaw 解析 assistant_reply，Claude 解析代码执行结果）

**伪代码展示**：

```Java
// 抽象骨架
public abstract class AbstractChatExecutionService implements ChatService {

    public Boolean execute(ChatRequest chatRequest) {
        // 1. 前置处理
        beforeHook(paramPassingDTO);

        // 2. 获取分布式锁（防止同一会话并发消费）
        acquireStreamLock(streamKey);

        try {
            // 3. 构建触发器和处理器（子类实现差异化部分）
            StreamMessageTrigger trigger = buildTrigger(paramPassingDTO);
            StreamMessageHandler handler = buildHandler(paramPassingDTO);

            // 4. 触发请求 + 消费响应
            trigger.trigger();  // 发请求给引擎
            consumeStream(config, handler);  // 阻塞消费 Redis Stream

        } finally {
            // 5. 释放锁
            releaseStreamLock();
            // 6. 后置处理（finally 保证必定执行）
            afterHook(paramPassingDTO);
        }
    }

    // 子类实现差异化部分
    protected abstract StreamMessageTrigger buildTrigger(ParamPassingDTO dto);
    protected abstract StreamMessageHandler buildHandler(ParamPassingDTO dto);
    protected abstract String getStreamConsumeLock();
    protected abstract String getRedisGroupId();
}

// OpenClaw 实现
public class UnifiedOpenClawAgentServiceImpl extends AbstractChatExecutionService {
    @Override
    protected StreamMessageTrigger buildTrigger(ParamPassingDTO dto) {
        // 构建 OpenClaw 用户消息，通过 Bridge WebSocket 发送
        return new OpenClawStreamMessageTrigger(dto);
    }
    // ...
}

// Claude 实现
public class UnifiedSharedCodeAgentServiceImpl extends AbstractChatExecutionService {
    @Override
    protected StreamMessageTrigger buildTrigger(ParamPassingDTO dto) {
        // 构建 Claude 代码执行请求，通过 HTTP 发送
        return new CodeAgentStreamMessageTrigger(dto);
    }
    // ...
}
```

**分布式锁的作用**：同一个会话可能在前一条消息还没处理完时就收到新消息，分布式锁保证同一会话串行处理，避免消息乱序。锁的 key 基于会话 ID 设计。

**心跳续期机制**：AI 引擎处理可能需要几十秒甚至几分钟，分布式锁默认 TTL 可能不够。心跳续期线程会定期延长锁的过期时间，防止锁被其他实例抢占。

### 4.4 第三层：可插拔处理链（管道 + 过滤器模式）

**设计思路**：对话前后有大量通用逻辑，如果硬编码在每个引擎里会非常臃肿。

**Hook 的设计**：每个处理逻辑是一个独立的 Hook，实现统一的 `Hook<T>` 接口，按固定顺序执行，通过共享上下文对象传递数据。

**伪代码展示**：

```Java
// Hook 接口
public interface Hook<T> {
    void execute(T t) throws IOException;
}

// 共享上下文对象（贯穿整个对话生命周期）
public class ParamPassingDTO {
    private ChatRequest chatRequest;
    private String agentUuid;
    private String assistantMessageId;
    private String teamId;          // 协作团队ID
    private String taskId;          // 协作任务ID
    private List<String> skillPackages;  // 技能包
    private Map<String, Object> vars = new HashMap<>();  // 自定义变量
    // ...
}

// 示例：会话归档检查 Hook
@Component
public class SessionArchivedCheckHook implements Hook<ParamPassingDTO> {
    @Override
    public void execute(ParamPassingDTO param) {
        String sessionId = param.getChatRequest().getSessionId();
        if (sessionService.isArchived(sessionId)) {
            throw new BizException("会话已归档，无法继续对话");
        }
    }
}

// 示例：协作初始化 Hook
@Component
public class AgentCollabInitHook implements Hook<ParamPassingDTO> {
    @Override
    public void execute(ParamPassingDTO param) {
        String teamId = param.getChatRequest().getTeamId();
        if (StringUtils.isNotEmpty(teamId)) {
            // 进入协作模式！
            String taskId = UUID.randomUUID().toString();
            collabTaskService.prepareCollaboration(taskId, teamId);
            param.getVars().put("teamId", teamId);
            param.getVars().put("taskId", taskId);
            // 注入协作技能包
            param.setSkillPackages(loadTeamSkills());
        }
    }
}
```

**20+ 个 Hook 及其职责**：


|     |         |     |
| --- | ------- | --- |
| 分类  | Hook 名称 | 职责  |


| **状态检查** | SessionArchivedCheckHook | 检查会话是否已归档 |

| | TeamArchivedCheckHook | 检查团队是否已归档 |

| **初始化** | AgentChatInitHook | 核心初始化：加载配置、注入系统变量、构建 Prompt |

| | AgentCollabInitHook | 协作模式初始化：创建 Task + Session |

| **内容处理** | KbAppendSystemPromptHook | 知识库内容追加到 System Prompt |

| | QueryReWriteHook | 查询重写（改写用户问题提高检索效果） |

| | AgentCollabMessageContentHook | 协作消息内容注入 |

| **引擎特有** | OpenClawBeforeHook | OpenClaw 前置：文件下载到容器 |

| | ClaudeBotBusinessContextInitHook | Claude 企业版上下文初始化 |

| | GeminiContextConfigInitHook | Gemini 上下文配置 |

| **其他** | RegenerateHook | 重新生成场景处理 |

| | FileEnvCheckHook | 文件环境检查 |

| | AIWorkflowGenerateInitHook | AI 工作流生成初始化 |

| **后置处理** | AgentChatEndHook | 对话结束：协作 idle 探测、Task 完成检测 |

| | StreamWorkflowTerminalHook | 流式工作流终止 |

| | CollabTaskStreamWorkflowTerminalHook | 协作 Task 流式终止 |

**协作模式初始化 Hook 的工作流程**（示例）：

```Plain
用户发送消息，携带 teamId="team_123"
    │
    ▼
AgentCollabInitHook 检测到 teamId 不为空
    │
    ├── 1. 生成 taskId（UUID）
    ├── 2. 调用 prepareCollaboration() 幂等创建：
    │       ├── 创建 Task 记录（状态 PENDING）
    │       ├── 为每个团队成员创建独立会话
    │       └── 写入执行快照表（不可变）
    ├── 3. 将 teamId/taskId 写入共享上下文
    └── 4. 从 S3 下载协作技能包，注入到运行时配置
    │
    ▼
后续的 AgentChatInitHook 等正常执行（感知不到协作模式）
    │
    ▼
引擎处理时，发现配置了协作技能包，Agent 就能调用协作技能了
```

## 五、请求路由机制



### 5.1 路由器的作用

当用户发送一条消息时，系统首先通过 `ChatServiceRouter` 判断这条消息应该交给哪个引擎处理。路由依据是智能体的「能力类型」（capacity type）。

**路由规则示例**：

```Plain
capacityType = "claudeBot"     → UnifiedSharedCodeAgentServiceImpl
capacityType = "openClawBot"   → UnifiedOpenClawAgentServiceImpl
capacityType = "geminiBot"     → UnifiedGeminiAgentServiceImpl
capacityType = "codexBot"      → UnifiedCodexAgentServiceImpl
capacityType = "cursorBot"     → UnifiedCursorAgentServiceImpl
capacityType = "claudeBotBusiness" → ClaudeBotBusinessStatelessAgentServiceImpl
```



### 5.2 灰度切流设计

系统重构时不能一次性切换所有流量，需要灰度切流。路由器支持两种切流策略：

**策略一：全局开关**

通过 Apollo 配置中心设置全局开关，比如 `agent.chat.unified.openclaw.enable=true`，开启后所有 OpenClaw 请求走新版实现。

**策略二：白名单灰度**

配置白名单用户列表，只有白名单内的用户走新版实现，其他用户继续走旧版。这样可以先让部分用户试用新版，确认没问题后再全量切换。

**示例：从旧版切到新版的过程**：

```Plain
第 1 天：开启白名单，加入 5 个测试用户
    → 这 5 个用户的 OpenClaw 请求走 UnifiedOpenClawAgentServiceImpl
    → 其他用户继续走 OpenClawAgentServiceImpl

第 3 天：白名单扩大到 50 个用户，观察指标

第 7 天：开启全局开关，所有用户切换到新版

第 10 天：下线旧版代码
```

## 六、异步消息通信架构



### 6.1 为什么需要异步通信

AI 引擎的响应是流式的——不是一次性返回完整回复，而是一个字一个字地"吐"出来（打字机效果）。如果用同步 HTTP 请求，连接会长时间阻塞，容易超时。

而且，多个用户可能同时与智能体对话，需要保证消息不串、不丢、不重复。

### 6.2 Redis Stream 方案

**生产端**（引擎容器产出响应后）：

```Plain
引擎容器处理用户消息
    │
    ├── OpenClaw：通过 Bridge WebSocket 回传 → 平台写入 Redis Stream
    ├── Claude：通过 HTTP 回调 → 平台写入 Redis Stream
    └── Gemini：通过 HTTP 回调 → 平台写入 Redis Stream
    │
    ▼
Redis Stream（key = assistantMessageId）
    └── XADD streamKey {data: messageJson}
```

**消费端**（专门的消费服务从 Stream 读取）：

```Plain
消费服务启动
    │
    ├── 1. 创建 Consumer Group（如果不存在）
    ├── 2. 获取分布式锁（key = streamConsumeLock + assistantMessageId）
    │       → 防止集群中多个实例重复消费同一会话的消息
    ├── 3. 启动心跳续期线程（定期延长锁过期时间）
    │
    ├── 4. 循环读取消息
    │       └── XREADGROUP GROUP groupId consumer COUNT 1 BLOCK 200-1000ms
    │           → 自适应阻塞时间：有消息时短阻塞(200ms)，无消息时长阻塞(1000ms)
    │
    ├── 5. 处理每条消息
    │       ├── handleMessage() → 按消息类型分发
    │       ├── 推送到前端 WebSocket（打字机效果）
    │       └── 推送到外部渠道（大象/飞书/钉钉）
    │
    ├── 6. ACK 确认
    │       └── XACK streamKey groupId messageId
    │
    └── 7. 退出条件
            ├── 收到 done=true → 消费完成，退出
            ├── 空闲超时 5 分钟 → 超时退出
            └── 发生异常 → 错误退出

    8. finally：释放分布式锁 + 清理 Stream
```

**推送端**：

消费到的消息会被构造成工作流数据（WorkFlowData），通过 WebSocket 推送到前端。支持两种推送模式：

- **增量推送**：每收到一个 token 就推一次，实现打字机效果
- **快照合并**：累积增量后与之前的快照合并，避免前端拼接错误

### 6.3 关键设计细节

**自适应阻塞时间**：消费循环中，XREADGROUP 的 BLOCK 参数不是固定的。有消息时用短阻塞（200ms），快速消费；没消息时自动切换到长阻塞（1000ms），减少空转。

**空闲超时退出**：如果连续 5 分钟没有收到任何消息，消费循环自动退出，释放锁。防止引擎异常导致永久阻塞。

**分布式锁的 key 设计**`streamConsumeLock:{assistantMessageId}`，基于消息 ID 而非会话 ID，保证同一条消息只有一个消费者。

**Stream 的过期清理**：消费完成后，Stream 会被清理。同时有一个 ZSet 索引管理 Stream 的生命周期，超过配置的过期时间自动清理。

### 7.3 可能被追问的问题

**Q: 为什么用 Redis Stream 而不是 Kafka？**

> Redis Stream 更轻量，我们已有 Redis 基础设施。Stream 支持消费者组、ACK 确认、消息持久化，满足需求。而且对话消息是会话级隔离的，每个会话一个 Stream，Kafka 的 Topic 模型不太适合这种大量短生命周期 Topic 的场景。

**Q: 分布式锁怎么实现的？**

> 基于 Redis 的 setIfAbsent（即 SETNX）+ 过期时间。获取锁时设置 key 和 TTL，同时启动心跳线程定期续期。释放锁时先验证持有者再删除（防止误删别人的锁）。

**Q: 如果消费端 crash 了消息会丢吗？**

> 不会。Redis Stream 有持久化，消费者组会记录每个消费者消费到哪个位置。crash 后重启，未 ACK 的消息会被重新分配给其他消费者。我们还有空闲超时机制，5 分钟没消费就释放锁，让其他实例接管。

**Q: Hook 链如果某个 Hook 抛异常了怎么办？**

> Before Hook 抛异常会中断对话流程，返回错误给用户。After Hook 在 finally 块中执行，即使前面出错也会执行。每个 After Hook 内部也有 try-catch，一个 After Hook 失败不影响其他 After Hook 执行。

**Q: 新增一种引擎大概需要多少工作量？**

> 主要是实现两个接口：BotProvider（生命周期管理，约 200-300 行）和 ChatService（对话执行，约 500-800 行）。如果引擎的通信方式和现有的类似（比如都是 HTTP），可以复用现有的 Stream 消费逻辑，工作量更小。整体大约 2-3 天。
