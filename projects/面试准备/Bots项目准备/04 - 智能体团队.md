# 04 - 智能体团队（多 Agent 协作）详解

> 本文是 AI 智能体平台中技术含量最高的功能模块——多 Agent 协作的完整技术详解。面向面试场景编写，语言通俗易懂，配合具体示例和流程图。

---

## 一、功能概述

### 1.1 什么是智能体团队

智能体团队是让多个 AI 智能体**组成一个团队**，协作完成一个复杂任务的机制。用户只需要跟"入口 Agent"（团队队长）说一句话，队长就会自动把任务拆解成多个子任务（Todo），分配给不同的队员，队员各自独立工作，产出成果后队长汇总报告。

**举一个具体例子：**

假设你创建了一个"代码审查团队"，包含三个 Agent：


|                |          |                  |
| -------------- | -------- | ---------------- |
| Agent          | 角色       | 职责               |
| 代码分析 Agent（队长） | 入口 Agent | 接收用户请求，拆解任务，汇总报告 |
| 安全审计 Agent     | 成员       | 专门检查代码中的安全漏洞     |
| 性能分析 Agent     | 成员       | 专门分析代码性能问题       |


用户只需发一条消息："帮我审查这个仓库的代码质量"，然后：

1. 队长 Agent 收到消息，创建两个 Todo：一个给安全审计 Agent，一个给性能分析 Agent
2. 系统自动把 Todo 分发给对应 Agent
3. 安全审计 Agent 独立完成安全检查，写报告到共享文件夹
4. 性能分析 Agent 独立完成性能分析，写报告到共享文件夹
5. 两个 Todo 都完成后，系统通知队长
6. 队长读取两份报告，合并成一份完整的代码审查报告返回给用户

**与单 Agent 对话的核心区别：**


|      |             |                      |
| ---- | ----------- | -------------------- |
| 对比维度 | 单 Agent 模式  | 团队协作模式               |
| 参与者  | 1 个 Agent   | N 个 Agent，各有专长       |
| 会话数量 | 1 个 session | N 个独立 session（互不干扰）  |
| 任务管理 | 无           | 有 Task + Todo + 依赖关系 |
| 成果交换 | 不需要         | 通过共享工作区文件交换          |
| 通信方式 | 用户直接对话      | Agent 之间通过 A2A 协议通信  |


### 1.2 核心理念

整个协作系统的核心理念是：**"编排集中在后端，推理留在引擎"**。

**打个比方：** 想象一个软件开发团队。

- **后端**扮演的是**项目经理**的角色：负责建立项目（创建 Task）、招募团队成员（绑定 Agent）、分配任务（派发 Todo）、跟踪进度（状态机推进）、处理异常（超时/失败）、汇总结果。项目经理本身不写代码。

- **各 Agent 容器**扮演的是**工程师**的角色：每个工程师在自己独立的工位（独立 session）上工作，只关心自己被分配的任务，用自己的专业能力（LLM 推理）独立完成工作。

- **推理引擎**（现有的 OpenChat/OpenClaw 等）就是工程师的"大脑"，后端不会插手工程师怎么思考和编码，只负责告诉他该做什么。

这个设计的好处是：后端的协作层完全**复用了现有的对话引擎**，不需要重写推理逻辑，大大降低了复杂度。

### 1.3 三条架构铁律

整个协作系统有三条不可违反的铁律，每一条背后都有深刻的工程原因：

---

**铁律一：任务分派只能通过 Todo + 调度中心（不能绕过状态机）**

- **含义**：Agent 不能直接用 A2A 消息告诉另一个 Agent "你去做 XXX"，必须通过创建 Todo 来分配任务。系统的调度中心会根据 Todo 的依赖关系和目标 Agent 的空闲状态来自动派发。

- **为什么这么设计**：如果允许 Agent 之间直接指派任务，就没有了统一的进度跟踪和状态管理。你不知道哪些任务在执行中、哪些完成了、哪些失败了。就好比一个团队不用项目管理工具，全靠口头传话——一旦有人请假或者掉线，所有人都不知道项目到底什么进度。

- **不这么做会怎样**：Task 的终态判定（是否全部完成）将无法实现，因为没有一个中央的任务列表来检查；超时控制和失败恢复也无从做起。

---

**铁律二：制品交换只能通过共享工作区文件（Agent 的 stdout 对队友不可见）**

- **含义**：Agent A 的工作成果（代码、报告、数据）必须写到团队的共享工作区（一个共享的容器文件系统），然后告诉队友文件路径。不能指望通过 A2A 消息把整个文件内容传过去。

- **为什么这么设计**：每个 Agent 运行在独立的 session 中，Agent A 的控制台输出（stdout）对 Agent B 完全不可见。而且 A2A 消息是走数据库的，不适合传输大体积的文件内容——消息有长度限制，大文件会导致数据库膨胀和网络延迟。

- **不这么做会怎样**：如果用消息传文件，一份 10MB 的代码分析报告就会变成一条巨大的消息，写入 `agent_a2a_message_log` 表，不但浪费存储，而且重试时每次都要重传整个内容。共享文件系统天然适合大文件交换，而且一次写入，任何队友都能读取。

---

**铁律三：A2A 通信仅用于自由沟通（不用于任务分配）**

- **含义**：A2A（Agent-to-Agent）消息用来让 Agent 之间"聊天"——比如问一个问题、通知一个信息、交接一个上下文。但绝不能用 A2A 来分配任务或推进 Todo 状态。

- **为什么这么设计**：A2A 消息没有状态机、没有依赖关系、没有自动调度。如果用 A2A 来分配任务，就相当于发了一条微信说"帮我做个事"——对方可能没看到、可能在忙、可能做完了也没告诉你。而 Todo 有完整的状态机（待分配 → 已分配 → 执行中 → 已完成），调度中心会确保每个环节都有记录和兜底。

- **不这么做会怎样**：A2A 消息如果既承担"聊天"又承担"分配任务"的职责，代码会变得极其复杂——你需要在每条消息里判断"这是一个任务还是一条普通消息"，然后走不同的逻辑分支。职责分离是避免系统腐化的关键。

### 2.2 每一层的职责


|     |     |      |
| --- | --- | ---- |
| 层   | 职责  | 关键组件 |


| **客户端** | 发起协作对话（WebSocket 携带 teamId）、接收推送、查询状态 | Web 前端 |

| **对话运行时** | 拦截协作请求、创建 Task 和 Session、注入协作上下文、复用现有对话引擎 | AgentCollabInitHook、AgentCollabTaskService |

| **技能包层** | Agent 运行时调用的"工具箱"——列队友、管 Todo、A2A 通信、操作共享工作区 | 4 个 Skill（Python 脚本 + SKILL.md） |

| **调度中心** | 协作的"大脑"——DAG 依赖调度、状态机推进、A2A 投递、事件驱动、定时补偿 | TaskDispatcher、CollabEventHandler、A2aDeliveryCoreService |

| **存储层** | 持久化所有协作状态和消息 | MySQL 8 张表 + Redis 分布式锁 |

### 2.3 与非协作模式的区别

在非协作模式下（普通单 Agent 对话），系统只有"客户端 → 对话运行时 → 存储"三层。协作模式多出了：

- **AgentCollabInitHook**：在 beforeHook 链中新增的协作初始化钩子

- **技能包层**：Agent 可调用的协作工具（普通模式下 Agent 没有"列队友""分任务"的能力）

- **调度中心**：完整的任务调度、A2A 通信、事件处理和定时补偿能力

- **8 张新表**：团队、任务、Todo、执行快照、A2A 消息日志、投递队列等

## 三、数据模型（8 张核心表）

### 3.1 团队层面（3 张表）

#### 表 1：agent_collab_team（团队定义表）


|             |                    |                    |
| ----------- | ------------------ | ------------------ |
| 字段          | 类型                 | 说明                 |
| id          | BIGINT, 自增         | 主键                 |
| team_id     | VARCHAR(128), UUID | 团队业务 ID，对外唯一标识     |
| team_name   | VARCHAR(128)       | 团队名称               |
| team_avatar | VARCHAR            | 团队头像               |
| team_desc   | VARCHAR            | 团队描述               |
| time_out    | INT                | 超时时间（分钟），超时后自动终止任务 |
| creator_id  | VARCHAR(128)       | 创建者 MIS ID         |
| space_id    | VARCHAR            | 所属空间               |
| tenant_id   | VARCHAR            | 租户 ID              |
| is_deleted  | TINYINT            | 软删除：0=正常，1=已删除     |


> **设计要点**：团队是**可复用的模板**，一个团队可以被多次用来创建不同的协作任务。就像一个固定的项目组，可以接手不同的项目。

#### 表 2：agent_collab_team_member（团队成员表）


|                 |              |                        |
| --------------- | ------------ | ---------------------- |
| 字段              | 类型           | 说明                     |
| id              | BIGINT, 自增   | 主键                     |
| team_id         | VARCHAR(128) | 关联 team.team_id        |
| agent_id        | VARCHAR(128) | Agent 标识               |
| team_agent_desc | VARCHAR      | 该 Agent 在团队中的角色描述      |
| is_entry        | TINYINT      | 是否入口 Agent（队长）：0=否，1=是 |
| enabled         | TINYINT      | 是否启用：0=禁用，1=启用         |
| member_role     | VARCHAR      | 成员角色                   |


| **唯一键** | (team_id, agent_id) | 同一团队内 Agent 不重复 |

> **设计要点**`is_entry=1` 的 Agent 是"队长"——用户的消息直接发给它，它负责拆解任务和汇总报告。一个团队必须有且只有一个入口 Agent。

#### 表 3：agent_collab_team_user_setting（用户偏好表）


|             |              |       |
| ----------- | ------------ | ----- |
| 字段          | 类型           | 说明    |

### 3.2 任务层面（3 张表）

#### 表 4：agent_collab_task（协作任务主表）


|            |                    |                                        |
| ---------- | ------------------ | -------------------------------------- |
| 字段         | 类型                 | 说明                                     |
| id         | BIGINT, 自增         | 主键                                     |
| task_no    | VARCHAR(128), UUID | 业务唯一编号，对外标识                            |
| team_id    | VARCHAR(128)       | 关联 team.team_id                        |
| title      | VARCHAR(256)       | 任务标题                                   |
| input      | TEXT, JSON         | 任务输入参数                                 |
| status     | TINYINT            | 状态：0=待执行，1=执行中，2=已完成，3=失败，4=已终止，5=超时失败 |
| timeout_at | DATETIME           | 超时截止时间（创建时 = now + team.time_out 分钟）   |
| creator_id | VARCHAR(128)       | 发起人 ID                                 |
| tenant_id  | VARCHAR(128)       | 租户 ID                                  |


> **设计要点**`task_no` 是 UUID，与自增 `id` 分离。所有协作域的表都通过 `task_no` 关联（而不是自增 ID），因为 `task_no` 可以在创建 Task 之前就由客户端生成，实现幂等重试。

#### 表 5：agent_collab_record（执行快照表）


|             |              |                                             |
| ----------- | ------------ | ------------------------------------------- |
| 字段          | 类型           | 说明                                          |
| id          | BIGINT, 自增   | 主键                                          |
| task_id     | VARCHAR(128) | 关联 task.task_no（注意字段名是 task_id 但值是 task_no） |
| agent_id    | VARCHAR(128) | Agent 标识                                    |
| session_id  | VARCHAR(128) | 该 Agent 在本次任务中的会话 ID                        |
| is_entry    | TINYINT      | 本次任务中是否为入口 Agent                            |
| member_role | VARCHAR      | 成员角色                                        |


| **唯一键** | (task_id, agent_id) | 同一任务中 Agent 不重复 |

> **设计要点**：这是一张**不可变的历史快照表**。团队成员可能在两次任务之间发生变化（加人/减人），但每次任务的参与者名单一旦创建就不再改变。这保证了"发生过什么"的审计可追溯性。它也是 A2A 通信的路由表——当 Agent A 要给 Agent B 发消息时，系统通过这张表找到 B 的 session_id。

#### 表 6：agent_collab_todo（工作项表）


|                  |                    |                                |
| ---------------- | ------------------ | ------------------------------ |
| 字段               | 类型                 | 说明                             |
| id               | BIGINT, 自增         | 主键                             |
| todo_id          | VARCHAR(128), UUID | Todo 业务 ID                     |
| task_id          | VARCHAR(128)       | 关联 task.task_no                |
| agent_id         | VARCHAR(128)       | 执行者 Agent ID（被分配者）             |
| creator_agent_id | VARCHAR(128)       | 创建者 Agent ID                   |
| title            | VARCHAR(256)       | 任务标题                           |
| content          | TEXT               | 任务内容描述                         |
| status           | TINYINT            | 状态（见下方状态机）                     |
| blocks           | TEXT, JSON 数组      | 本 Todo 完成后可以解锁的 Todo ID 列表     |
| blocked_by       | TEXT, JSON 数组      | 本 Todo 被哪些 Todo 阻塞（依赖的前置 Todo） |
| assigned_at      | DATETIME           | 分配时间                           |
| blocked_reason   | VARCHAR            | 阻塞原因                           |


> **设计要点**`blocks` 和 `blocked_by` 构成一个 **DAG（有向无环图）** 依赖关系。这是整个调度引擎的核心——它决定了哪些 Todo 可以并行执行，哪些必须等前置完成后才能开始。

**具体示例：一个包含 3 个 Todo 的任务数据（带依赖关系）**

场景：代码审查任务。安全审计和性能分析可以并行，但报告生成必须等它们都完成。

```Plain
agent_collab_task:
┌────────────────┬──────────────┬────────┐
│ task_no        │ title        │ status │
├────────────────┼──────────────┼────────┤
│ task-uuid-001  │ 代码审查任务  │ 1      │  ← RUNNING
└────────────────┴──────────────┴────────┘

agent_collab_todo (3 条):
┌──────────────┬──────────────────┬────────────────┬────────┬──────────────────┬──────────────────┐
│ todo_id      │ title            │ agent_id       │ status │ blocks           │ blocked_by       │
├──────────────┼──────────────────┼────────────────┼────────┼──────────────────┼──────────────────┤
│ todo-001     │ 安全漏洞扫描     │ agent-security │ 0      │ ["todo-003"]     │ []               │
│ todo-002     │ 性能瓶颈分析     │ agent-perf     │ 0      │ ["todo-003"]     │ []               │
│ todo-003     │ 汇总审查报告     │ agent-leader   │ 0      │ []               │ ["todo-001",     │
│              │                  │                │        │                  │  "todo-002"]     │
└──────────────┴──────────────────┴────────────────┴────────┴──────────────────┴──────────────────┘
```

**依赖关系图：**

```Plain
  todo-001 (安全扫描) ──┐
                        ├──▶ todo-003 (汇总报告)
  todo-002 (性能分析) ──┘

  todo-001 和 todo-002 无依赖，可并行执行
  todo-003 被 todo-001 和 todo-002 阻塞，必须等它们都完成
```

## 四、协作初始化流程

### 4.1 入口：AgentCollabInitHook

当用户发送消息携带 `teamId` 时，在对话引擎的 `beforeHook` 链中，`AgentCollabInitHook` 会在 `AgentChatInitHook` **之前**执行，完成协作的初始化。

**流程图：**

```Plain
用户发送消息 (WebSocket /chat, 携带 teamId)
    │
    ▼
AgentCollabInitHook.execute()
    │
    ├── 1. 检查 chatRequest 是否携带 teamId
    │      │
    │      ├── 无 teamId 且无 taskId → 直接返回（非协作模式）
    │      └── 无 teamId 但有 taskId → 仅注入技能包，返回
    │
    ├── 2. 解析租户 ID (tenantId)
    │      chatRequest.tenantId → 系统参数 system.tenantId
    │
    ├── 3. 解析创建者 (operator)
    │      chatRequest.userId → system.userId → system.creatorId
    │
    ├── 4. 生成或复用 taskId
    │      若 chatRequest.taskId 为空 → UUID.randomUUID()
    │
    ├── 5. 调用 AgentCollabTaskService.prepareCollaboration()
    │      (详见 4.2 节)
    │
    ├── 6. 向 ParamPassingDTO.vars 写入协作上下文
    │      vars.put("teamId", teamId)
    │      vars.put("taskId", taskId)
    │      vars.put("tenantId", tenantId)
    │      vars.put("botsSessionId", sessionId)
    │
    └── 7. 注入团队技能包
           读取 Apollo 配置 team.skills (逗号分隔的 Skill ID)
           → 查询 CcSkillService 获取 S3 包地址
           → 合并到 paramPassingDTO.ccSkillPackages
```

**幂等设计**：如果 `taskId` 已存在`prepareCollaboration()` 会检测到已有任务，不会重复创建——只会补齐缺失的成员 Session。这保证了网络重连或客户端重试不会导致重复的 Task。

### 4.2 会话创建（prepareCollaboration 详解）

`AgentCollabTaskService.prepareCollaboration()` 是一个 `@Transactional` 方法，完成所有协作准备工作：

```Plain
prepareCollaboration(chatRequest, tenantId)
    │
    ├── 1. 校验团队
    │      loadTeam(teamId) → 团队不存在或已删除 → 抛异常
    │
    ├── 2. 加载团队成员
    │      loadMembers(teamId) → 只加载 enabled=1 的成员
    │      validateMembers() → 至少有一个 is_entry=1 → 否则抛异常
    │
    ├── 3. 检查任务是否已存在
    │      findTaskByTaskNo(taskNo)
    │      │
    │      ├── 已存在:
    │      │   ├── 校验 teamId 是否匹配（不匹配则抛异常）
    │      │   ├── 确保状态为 RUNNING（如果不是则 CAS 更新）
    │      │   └── 补齐缺失的 Record（新加入的成员）
    │      │
    │      └── 不存在（新任务）:
    │          ├── 创建 AgentCollabTask (status=RUNNING)
    │          ├── 计算 timeout_at = now + team.timeOut 分钟
    │          └── 进入步骤 4
    │
    ├── 4. 为每个成员创建会话
    │      for each member in team_members:
    │         │
    │         ├── 检查是否已有 Record 且 sessionId 非空 → 跳过
    │         │
    │         ├── 是否可复用当前会话？
    │         │   (入口 Agent + chatRequest 已有匹配的 sessionId)
    │         │   ├── 是 → 复用现有 session
    │         │   └── 否 → humanMachineService.newSession()
    │         │          创建一个全新的独立 session
    │         │
    │         └── upsert AgentCollabRecord
    │              (task_id, agent_id, session_id, is_entry)
    │
    └── 5. 事务提交
           Task + 所有 Record 在同一事务中写入
```

> **为什么每个成员需要独立的 session？** 因为每个 Agent 的对话上下文必须独立——安全审计 Agent 和性能分析 Agent 的对话历史不能混在一起，否则 LLM 的上下文窗口会被无关信息占满，影响推理质量。独立 session 保证了每个 Agent 只看到与自己相关的对话。

## 五、任务调度引擎（核心）

调度引擎是整个协作系统最核心的部分，它解决的核心问题是：**怎样在多个 Agent 之间自动分配和推进任务，同时处理好依赖关系和并发冲突。**

### 5.1 DAG 依赖设计

每个 Todo 有两个 JSON 数组字段来描述依赖关系：

- `blocked_by`：本 Todo 被哪些 Todo 阻塞（前置条件）
- `blocks`：本 Todo 完成后可以解锁哪些 Todo（后续步骤）

**JSON 格式示例：**

```JSON
// todo-003 的 blocked_by：等 todo-001 和 todo-002 都完成
["todo-001", "todo-002"]

// todo-001 的 blocks：完成后可以解锁 todo-003
["todo-003"]
```

**依赖验证逻辑（TodoDependencyValidator）：**

`allDependenciesMet()` 方法的判断规则：

1. 如果 `blocked_by` 为空 → 返回 true（没有前置条件，可以直接执行）
2. 根据 `blocked_by` 中的 todoId 列表，查询这些 Todo 的当前状态

3. **Fail-closed 安全设计**：如果查出来的 Todo 数量少于 `blocked_by` 列表长度（说明有些 Todo 在数据库中不存在），返回 false。宁可不派发，也不能因为数据不一致而错误地解锁任务

1. 只有当所有前置 Todo 都是 COMPLETED(1) 或 CANCELLED(2) 时，才返回 true

5. **FAILED(4) 和 BLOCKED(6) 不算"满足"**——虽然它们是终态，但说明前置任务出了问题，下游任务不应该在有问题的基础上继续执行

> **打个比方**：假设你在做一个蛋糕。"打蛋"和"筛面粉"可以并行（没有依赖），但"混合面糊"依赖前两步。如果打蛋失败了（鸡蛋坏了），你不应该继续混合面糊——应该先解决鸡蛋的问题。

### 5.2 调度流程详解

`TaskDispatcher.dispatchIfReady()` 是调度的入口方法：

```Plain
dispatchIfReady(taskNo, todo)
    │
    ├── 1. 解析 blocked_by 列表
    │      dependencyValidator.parseBlockedBy(todo.blockedBy)
    │      → 如果 JSON 格式损坏 → 直接抛异常（Fail-closed）
    │
    ├── 2. 检查所有依赖是否满足
    │      dependencyValidator.allDependenciesMet(taskNo, blockedByIds)
    │      │
    │      └── 不满足 → 日志记录，返回（Todo 保持 PENDING）
    │
    ├── 3. CAS 更新状态：PENDING(0) → ASSIGNED(5)
    │      todoMapper.casUpdateStatus(id, PENDING, ASSIGNED, now, null)
    │      │
    │      └── CAS 失败（affected=0）→ 已被其他线程抢先调度，返回
    │
    ├── 4. 解析目标 session_id
    │      resolveSessionId(taskNo, todo.agentId)
    │      │
    │      └── 未找到 session → 回滚 CAS (ASSIGNED → PENDING)
    │          日志："agent还未建立session，等待outbox重试"
    │
    └── 5. 执行派发
           doDispatch(taskNo, todo, sessionId)
               │
               ├── 5a. 检查 Todo 是否已 RUNNING → 跳过
               │
               ├── 5b. 写入 Outbox
               │       dispatchQueueMapper.insertIfAbsent(outbox)
               │       → 返回 0 表示已存在（幂等去重）
               │
               └── 5c. 投递消息
                       deliverAssignFromOutbox(outbox, todo)
                       → 构建 CollabDeliverMessage (forTaskAssign)
                       → 调用 deliveryCoreService.deliver()
                       → 成功：删除 Outbox 行
                       → 失败：Outbox 保留，等定时任务重试
```

**具体示例：4 个 Todo 的调度过程**

假设有一个"写技术方案"的协作任务，包含 4 个 Todo：

```Plain
Todo A: 收集需求文档       → 无依赖
Todo B: 分析技术选型       → 依赖 A
Todo C: 设计数据库 schema  → 依赖 A
Todo D: 编写方案文档       → 依赖 B 和 C
```

**DAG 图：**

```Plain
  Todo A (收集需求) ──┬──▶ Todo B (技术选型) ──┐
                      │                        ├──▶ Todo D (编写方案)
                      └──▶ Todo C (数据库设计) ──┘
```

**调度过程逐步演示：**

```Plain
时刻 T1: Todo 全部创建完成
  A: PENDING (blocked_by=[])          ← 无依赖
  B: PENDING (blocked_by=["A"])       ← 依赖 A
  C: PENDING (blocked_by=["A"])       ← 依赖 A
  D: PENDING (blocked_by=["B","C"])   ← 依赖 B 和 C

  → onTodosCreated 触发，对每个 Todo 调用 dispatchIfReady()
  → A 无依赖，满足条件 → CAS: PENDING→ASSIGNED → 派发给目标 Agent
  → B 依赖 A（A 还是 PENDING），不满足 → 跳过
  → C 依赖 A（A 还是 PENDING），不满足 → 跳过
  → D 依赖 B 和 C（都是 PENDING），不满足 → 跳过

时刻 T2: A 的目标 Agent 认领并开始执行
  A: RUNNING
  B/C/D: 不变

时刻 T3: A 完成
  A: COMPLETED

  → onTodoCompleted 触发 cascadeDispatch("A")
  → 扫描所有 PENDING 的 Todo，找到 blocked_by 包含 "A" 的：B 和 C
  → B: 检查依赖 ["A"]，A 已 COMPLETED → 满足！CAS: PENDING→ASSIGNED → 派发
  → C: 检查依赖 ["A"]，A 已 COMPLETED → 满足！CAS: PENDING→ASSIGNED → 派发
  → B 和 C 被并行派发给不同的 Agent

时刻 T4: B 完成
  B: COMPLETED

  → cascadeDispatch("B")
  → D: 检查依赖 ["B","C"]，B 已完成但 C 还在 RUNNING → 不满足 → 跳过

时刻 T5: C 完成
  C: COMPLETED

  → cascadeDispatch("C")
  → D: 检查依赖 ["B","C"]，B 已完成，C 已完成 → 满足！→ 派发 D

时刻 T6: D 完成
  → checkAndCloseTask：所有 Todo 都是终态 → Task = COMPLETED
```

### 5.4 CAS 乐观锁

**为什么用 CAS 而不是分布式锁？**

CAS（Compare-And-Swap）是乐观锁的一种实现方式。在协作场景中，用 CAS 比分布式锁更合适，原因是：

1. **性能更好**：分布式锁（如 Redis 锁）有网络开销，而 CAS 只是在 SQL 的 WHERE 子句中多加一个条件判断，几乎零额外开销

2. **不会死锁**：CAS 操作要么成功要么失败，不会出现"持锁线程挂了导致锁无法释放"的问题

3. **天然幂等**：重复执行 CAS 操作，最多只有一个能成功，天然防止重复操作

**casUpdateStatus 的工作原理：**

```SQL
-- CAS 更新 Todo 状态
UPDATE agent_collab_todo
SET status = #{newStatus},
    assigned_at = #{now}
WHERE id = #{todoId}
  AND status = #{expectedOldStatus}   -- ← 这就是 CAS 的核心
```

执行结果：

- `affected rows = 1`：CAS 成功，状态从 `expectedOldStatus` 更新到了 `newStatus`
- `affected rows = 0`：CAS 失败，说明别人已经改过了，当前线程放弃操作

**示例：两个线程同时尝试调度同一个 Todo**

```Plain
线程 1                              线程 2
   │                                   │
   ├── 检查依赖：满足                    ├── 检查依赖：满足
   │                                   │
   ├── CAS: PENDING→ASSIGNED           ├── CAS: PENDING→ASSIGNED
   │   WHERE status=0 AND id=42        │   WHERE status=0 AND id=42
   │                                   │
   │   UPDATE 执行...                   │   UPDATE 执行...
   │   ┌──────────────┐                │
   │   │ affected = 1 │ ← 先到先得      │
   │   └──────────────┘                │   ┌──────────────┐
   │                                   │   │ affected = 0 │ ← 晚了一步
   │   → 继续派发                       │   └──────────────┘
   │                                   │   → 放弃，日志记录
   ▼                                   ▼
```

这个设计保证了：**不管有多少个线程（或多少个服务节点）同时触发调度，同一个 Todo 只会被派发一次。**

## 六、事件驱动状态收敛

### 6.1 事件编排中枢

`CollabEventHandler` 是协作系统的事件编排中枢，处理 5 种核心事件：


|                     |                            |                                                                                          |
| ------------------- | -------------------------- | ---------------------------------------------------------------------------------------- |
| 事件                  | 触发时机                       | 处理逻辑                                                                                     |
| `onTodosCreated`    | Agent 通过技能创建了新的 Todo       | 遍历每个新 Todo，调用 `dispatchIfReady()` 尝试立即派发（如果没有依赖就直接派发）                                    |
| `onTodoCompleted`   | Agent 通过技能标记 Todo 完成       | 1. 调用 `cascadeDispatch()` 解锁下游 Todo；2. 调用 `checkAndCloseTask()` 判断任务是否可以关闭               |
| `onTaskTimeout`     | 定时处理器检测到任务超时               | 1. CAS: RUNNING→TIMEOUT_FAILED；2. 停止所有成员 session；3. 终止所有待投递消息；4. 推送 TaskEnded；5. 通知队长做总结 |
| `onAgentFailed`     | 消息重试耗尽 / 工作流执行失败           | 1. 将该 Agent 的 RUNNING/ASSIGNED Todo 标记为 BLOCKED(6)；2. 调用 `checkAndCloseTask()`           |
| `onAgentBecomeIdle` | Agent 的对话结束（WorkflowEnded） | 1. 重放该 Agent 的待处理 Outbox 条目；2. 重试该 Agent 的待投递 A2A 消息；3. 尝试关闭无 Todo 的纯聊天任务                |


> **打个比方**：事件编排中枢就像交通指挥中心。它不直接开车（不做推理），但每当路况变化（事件发生）时，它就调整信号灯（状态）、指挥新车辆上路（派发 Todo）、处理事故（Agent 失败）。

### 6.2 Task 终态判定

`checkAndCloseTask()` 是判断任务是否可以关闭的核心方法：

```Plain
checkAndCloseTask(taskNo, parentEvent)
    │
    ├── 1. 加载该任务的所有 Todo
    │      │
    │      └── 没有 Todo → 跳过（纯聊天场景由另一个方法处理）
    │
    ├── 2. 检查是否所有 Todo 都是终态
    │      终态 = COMPLETED(1) / CANCELLED(2) / FAILED(4) / BLOCKED(6)
    │      │
    │      └── 存在非终态 Todo → 不关闭，返回
    │
    ├── 3. 确定 Task 的终态
    │      │
    │      ├── 存在 FAILED(4) 或 BLOCKED(6) → Task 状态 = FAILED(3)
    │      │
    │      └── 全部 COMPLETED 或 CANCELLED → Task 状态 = COMPLETED(2)
    │
    └── 4. 关闭任务
           closeRunningTask(taskNo, newTaskStatus)
           ├── CAS: RUNNING(1) → newTaskStatus
           │   (CAS 失败说明已关闭，跳过)
           ├── 推送 TaskEnded 给前端
           └── 通知队长做总结汇报
```

### 6.3 异常场景处理


|      |      |      |
| ---- | ---- | ---- |
| 异常场景 | 处理方式 | 恢复机制 |


| **Agent 繁忙** | 消息标记为 QUEUED(3)，不阻塞调用方立即返回 | `onAgentBecomeIdle` 事件触发重放 + 定时处理器每 2 分钟轮询 |

| **Agent 失败（重试耗尽）** | Todo 标记为 BLOCKED(6)，checkAndCloseTask → Task=FAILED | 需要人工介入。BLOCKED 不会自动恢复，因为问题的根因没解决 |

| **任务超时** | CAS: RUNNING→TIMEOUT_FAILED，停止所有 session，终止所有待投递消息 | 队长收到超时通知，可以生成当前进度的总结报告 |

| **进程 crash（服务器宕机）** | 各种状态可能卡在中间状态 | `CollabScheduledProcessor` 的 `detectStuckTodos()` 和 `detectStuckDispatches()` 兜底恢复 |

| **CAS 竞争失败** | 操作被安全跳过，不会重复执行 | 只有一个线程能成功执行状态转换，其他线程自动放弃 |

**进程 crash 恢复的详细说明：**

想象一个最坏的情况：系统在 Todo A 完成、cascadeDispatch 刚要触发 B 的派发时宕机了。此时：

- A 的状态已经是 COMPLETED（持久化在 DB 中）
- B 仍然是 PENDING（还没来得及派发）
- Task 仍然是 RUNNING

`detectStuckDispatches()` 定时扫描 Outbox 中卡住的记录，重新尝试派发。即使 Outbox 中也没有记录（因为还没来得及写入），`detectStuckTodos()` 会发现"Task 是 RUNNING，但所有 Todo 都是终态"，从而正确关闭 Task。如果 B 确实应该被派发但没有，入口 Agent 可以通过查看 Todo 列表发现问题并重新创建。

## 七、A2A 通信协议

### 7.1 协议设计

A2A 通信使用 **Protocol Envelope v2** 结构，将每条消息分为"人可读的展示内容"和"机器可解析的协议信封"：

```JSON
{
  "version": "2",
  "channel": "task 或 a2a",
  "action": "具体动作类型",
  "payload": {
    // 动作相关的数据
  }
}
```

**channel 的两种取值：**

- `task`：系统级消息通道，用于任务分配和完成通知。**Agent 不能通过技能发送 task 通道的消息**，只有调度中心才能发。
- `a2a`：Agent 间自由通信通道，Agent 通过技能发送。

**不同类型消息的 JSON 示例：**

**1. 任务分配消息（task/assign）— 调度中心 → Agent：**

```JSON
{
  "version": "2",
  "channel": "task",
  "action": "assign",
  "payload": {
    "todoId": "todo-uuid-001",
    "title": "安全漏洞扫描",
    "content": "扫描仓库中的安全漏洞，重点关注 SQL 注入和 XSS",
    "blockedBy": [],
    "creatorAgentId": "agent-leader"
  }
}
```

**2. 任务完成通知（task/notify_complete）— 调度中心 → 队长：**

```JSON
{
  "version": "2",
  "channel": "task",
  "action": "notify_complete",
  "payload": {
    "taskNo": "task-uuid-001",
    "status": 2,
    "message": "所有协作子任务已完成。请根据各成员的产出，对本次协作任务进行总结汇报。"
  }
}
```

**3. Agent 间自由通信（a2a/handoff）— Agent A → Agent B：**

```JSON
{
  "version": "2",
  "channel": "a2a",
  "action": "handoff",
  "payload": {
    "body": "我已经完成安全扫描，报告在 /workspace/reports/security-report.md，发现了 3 个高危漏洞，请在你的性能报告中也关注这几个文件。"
  }
}
```

**4. Agent 间查询（a2a/query）— Agent A → Agent B：**

```JSON
{
  "version": "2",
  "channel": "a2a",
  "action": "query",
  "payload": {
    "body": "你分析的性能瓶颈中，有没有涉及数据库连接池的问题？"
  }
}
```

**5. Agent 间结果返回（a2a/result）— Agent B → Agent A：**

```JSON
{
  "version": "2",
  "channel": "a2a",
  "action": "result",
  "payload": {
    "body": "是的，连接池配置最大 10 个连接，但高峰期有 50 个并发查询，建议调到 30。详见 /workspace/reports/perf-report.md 第 42 行。"
  }
}
```

### 7.3 消息工厂

`CollabDeliverMessageFactory` 使用**工厂 + Builder 模式**来构建结构化消息：

```Plain
CollabDeliverMessageFactory (静态工厂类, final, 私有构造函数)
    │
    ├── forTaskAssign(todo, extraContext)
    │   → 构建任务分配消息
    │   → channel=task, action=assign
    │   → displayContent: "你收到一个协作任务：{title}\n任务ID：{todoId}..."
    │
    ├── forNotifyComplete(taskNo, taskStatus, summaryPrompt)
    │   → 构建任务完成通知
    │   → channel=task, action=notify_complete
    │   → displayContent: 根据状态生成不同的中文提示
    │
    ├── forA2a(messageType, fromAgentId, messageContent)
    │   → 构建 Agent 间自由消息
    │   → channel=a2a, action=handoff/query/result
    │   → displayContent: 原始消息内容
    │
    └── fromMessageLog(message)
        → 从数据库消息记录中重建消息（用于重试）
        → 解析 context 中的 collabProtocol
        → 如果解析失败返回 null（消息将被标记为失败）
```

**展示层与协议层分离的设计：**

每条消息都有两个层面的内容：

- **displayContent**（展示层）：人可读的自然语言文本，作为 OpenChat 的 `message.content` 发送给目标 Agent。Agent 的 LLM 看到的就是这段文字。

- **protocolEnvelope**（协议层）：结构化的 JSON 信封，作为 `system` 参数中的 `collabProtocol` 注入到 OpenChat 请求中。Agent 的技能脚本可以解析这个结构化数据。

这种分离的好处是：LLM 看到的是自然语言（易于理解），而程序逻辑需要的是结构化数据（易于解析），两者互不干扰。

### 7.4 安全设计


|      |      |       |
| ---- | ---- | ----- |
| 安全措施 | 实现方式 | 防范的风险 |


| **taskNo 环境变量注入** | `EFFICIENCY_AGENT_COLLAB_TASK_ID` 由系统注入，Agent 不能伪造 | 防止 Agent 操作其他任务的数据 |

| **fromAgentId 服务端解析** | `A2aContextEnricher` 根据 `sessionId + taskNo` 在 `agent_collab_record` 中查询 `agent_id`，**不信任客户端传入的 fromAgentId** | 防止 Agent 冒充其他 Agent 发送消息 |

| **toAgentId 合法性校验** | `toAgentId` 必须是当前 Task 的成员（在 `agent_collab_record` 中存在） | 防止向非团队成员发送消息 |

| **消息类型路由校验** | `MessageProtocolRouter` 只允许 Agent 发送 `a2a` 通道的消息（handoff/query/result/artifact_shared），禁止发送 `task` 通道消息（task_assign/notify_complete） | 防止 Agent 越权操作任务分配 |

| **共享工作区路径安全** | 工作区操作限制在团队容器内，禁止 `../` 路径穿越 | 防止文件系统攻击 |

## 八、定时处理器

### 8.1 四项核心任务

`CollabScheduledProcessor` 是一个统一的定时处理器，每 **2 分钟**执行一次，包含四项核心任务：

```Plain
CollabScheduledProcessor.execute() — @Scheduled(fixedDelay = 120_000)
    │
    ├── 1. 获取 Redis 分布式锁
    │      key: "agent_collab:collab_scheduled_processor:lock"
    │      TTL: 110 秒
    │      │
    │      └── 获取失败 → 说明其他节点在执行，本次跳过
    │
    ├── 2. retryPendingMessages()    — 重试失败/排队中的 A2A 消息
    │
    ├── 3. detectTaskTimeouts()      — 检测超时的协作任务
    │
    ├── 4. detectStuckTodos()        — 恢复因 crash 卡死的任务
    │
    ├── 5. detectStuckDispatches()   — 重试 Outbox 中卡住的派发
    │
    └── finally: 释放分布式锁
```

**各任务详解：**


|                         |                     |                                                           |                                           |
| ----------------------- | ------------------- | --------------------------------------------------------- | ----------------------------------------- |
| 任务                      | 职责                  | 查询条件                                                      | 处理逻辑                                      |
| `retryPendingMessages`  | 重试未成功投递的 A2A 消息     | status IN (SENDING, FAILED, QUEUED) 且 send_time < now-30s | 按目标 Agent 分组，逐条重试投递；遇 busy 跳过该 Agent 剩余消息 |
| `detectTaskTimeouts`    | 检测超过 timeout_at 的任务 | timeout_at < now 且 status=RUNNING                         | 触发 `onTaskTimeout` 事件                     |
| `detectStuckTodos`      | 恢复 crash 后卡住的任务     | status=RUNNING 但所有 Todo 已是终态                              | 根据 Todo 状态判定 Task 终态，CAS 关闭               |
| `detectStuckDispatches` | 重试 Outbox 中卡住的派发记录  | 创建时间 > 5 分钟且仍未成功投递                                        | 行级锁 tryLock → 重试投递 → 成功则删除 Outbox 行       |


### 8.2 重试策略

`retryPendingMessages()` 的重试策略设计得很精细：

```Plain
重试策略详解:

1. 分批处理
   - 每批最多 100 条消息
   - 最多循环 10 轮
   - 优先处理更早发送的消息 (ORDER BY send_time ASC)

2. 按目标 Agent 分组
   - 将待重试消息按 toAgentId 分组
   - 同一 Agent 的消息顺序处理
   - 一旦某 Agent 返回 "Agent繁忙"，跳过该 Agent 的所有剩余消息
     (因为 Agent 正在处理中，继续发也是浪费)

3. 重试上限
   - 最多 20 次重试 (maxRetryCount=20)
   - 超过 20 次 → 标记为 RETRY_FAILED
   - 触发 onAgentFailed(RETRY_EXHAUSTED)
   - 该 Agent 的 Todo 被标记为 BLOCKED(6)

4. 早期终止
   - 如果一批处理中成功 0 条且失败 0 条 → 停止循环
   - 如果批次大小 < batchSize → 没有更多消息 → 停止
```

### 8.3 分布式锁

```Plain
锁的实现:

获取锁:
  redisTemplate.opsForValue()
    .setIfAbsent(LOCK_KEY, lockToken, ttl, MILLISECONDS)
  - lockToken = UUID (每次执行生成新 token)
  - TTL = 110 秒 (略小于 120 秒执行间隔，避免锁永久占用)

释放锁 (安全删除):
  1. 先 GET 当前锁的值
  2. 如果值 == 自己的 lockToken → 才 DELETE
  3. 如果值 != 自己的 lockToken → 不删 (避免删除别人的锁)

为什么这样设计?
  - setIfAbsent 保证同一时刻只有一个实例获取锁
  - TTL 保证即使持锁实例宕机，锁也会自动过期
  - Token 校验保证不会误删其他实例的锁 (防 ABA 问题)
```

## 九、团队技能包

### 9.1 四个核心技能

团队技能包是 Agent 在协作过程中可以调用的"工具箱"。每个技能都是一个独立的目录，包含 `SKILL.md`（技能描述）、`run.py`（执行脚本）和参考文档。


|     |     |      |     |
| --- | --- | ---- | --- |
| 技能  | 目录名 | 核心命令 | 职责  |


| **协作路由技能** | using-team-collab | — | 元技能/路由入口，定义生命周期、角色、技能路由表。Agent 首先读这个技能，了解该调用哪个子技能 |

| **协作通信技能** | collab-communication | `agents list` / `a2a send` | 列出队友信息 + 发送自由通信消息（handoff/query/result） |

| **Todo 管理技能** | collab-todo | `create` / `list` / `update` / `claim` / `complete` / `cancel` | 创建、查询、认领、完成、取消 Todo |

| **共享工作区技能** | shared-workspace-exec | `exec --script "<bash>"` | 在团队共享容器中执行脚本、读写文件、构建测试 |

**技能间的调用关系：**

```Plain
using-team-collab (路由入口)
    │
    ├── 需要知道队友是谁？    → collab-communication: agents list
    ├── 需要分配/管理任务？   → collab-todo: create/claim/complete...
    ├── 需要和队友沟通？      → collab-communication: a2a send
    └── 需要读写文件/跑脚本？ → shared-workspace-exec: exec

禁止：
  ✗ 用 A2A 消息分配任务（必须用 Todo）
  ✗ 用 A2A 消息传输大文件（必须用共享工作区）
  ✗ 用本地 Read/Write/Bash 操作共享文件（必须用 shared-workspace-exec）
```

### 9.2 技能注入机制

技能注入有三种路径，形成一个完整的链路：

```Plain
路径 1: Apollo 配置
  team.skills = "skill-id-1,skill-id-2,skill-id-3,skill-id-4"
      │
      ▼
路径 2: CcSkillService 查询
  查询每个 Skill ID 的元数据，获取 S3 压缩包 URL
  CcSkillPackageInfo(name, s3PackageUrl, releaseVersion)
      │
      ▼
路径 3: 合并到运行时配置
  paramPassingDTO.ccSkillPackages.merge(newPackages)
  → 同名技能会被覆盖（新版本替换旧版本）
  → Agent 容器启动时自动从 S3 下载并安装
```

### 9.3 共享工作区

共享工作区是团队协作的"共享文件服务器"——所有团队成员的工作产出都放在这里，任何成员都可以读取。

**关键设计：**


|     |      |     |
| --- | ---- | --- |
| 设计点 | 实现方式 | 原因  |


| **一个团队一个容器** | 每个团队有一个专属的容器作为共享工作区 | 隔离不同团队的数据 |

| **防重复创建** | Redis 分布式锁 + Double-Check 模式 | 多个成员同时请求创建时，只创建一次 |

| **健康探测** | 定期检查容器是否存活 | 容器挂了要能自动感知 |

| **路径安全** | 禁止 `../` 路径穿越，只允许相对路径 | 防止文件系统攻击 |

## 十一、任务停止方案

### 11.1 用户主动停止

用户可以在前端点击"停止"按钮来终止一个正在进行的协作任务。

**端点：** `POST /api/v1/agent/session/stopCollabTask`

**请求体：**

```JSON
{
  "taskNo": "task-uuid-001",
  "sessionId": "session-001"
}
```

### 11.2 停止流程

```Plain
stopCollabTask(taskNo, sessionId)
    │
    ├── 1. 校验 taskNo 和 sessionId
    │      sessionId 必须在 agent_collab_record 中存在
    │
    ├── 2. 检查 Task 是否已终态
    │      │
    │      ├── 已终态 (COMPLETED/FAILED/TERMINATED/TIMEOUT_FAILED)
    │      │   → 不操作数据库，直接推送 collab_task_stop（幂等兜底前端）
    │      │
    │      └── 非终态 (PENDING/RUNNING)
    │          → 继续步骤 3
    │
    ├── 3. 停止所有成员 session
    │      for each record in agent_collab_record:
    │          if !collabSessionIdleProbe.isIdle(sid):
    │              stopChat(sid, null)  // 只停还在运行的 session
    │
    ├── 4. 更新任务状态
    │      updateTaskStatusCancelled(taskNo)
    │      → Task: RUNNING → TERMINATED(4)
    │      → 取消所有 inflight A2A 消息
    │        (SENDING/QUEUED/FAILED → TASK_TIMEOUT_TERMINATED)
    │
    └── 5. 推送通知
           pushCollabTaskStop(sessionId, taskNo, TERMINATED)
           → WebSocket: type=collab_task_stop
           → data: { sessionId, taskNo, status: 4, timestamp }
```

### 11.3 空闲检测逻辑

`CollabSessionIdleProbe` 判断一个 session 是否空闲：

```Plain
isIdle(sessionId)
    │
    ├── 查询 agent_session_info.session_status
    │
    ├── 以下状态视为空闲:
    │   - ChatRecordStatusEnum.isEnd() 返回 true 的状态
    │     (WorkflowEnded, Ended, WorkflowFailed, ManualStop)
    │   - CodeAgent 工作区就绪/失败
    │
    └── 以下状态视为非空闲:
        - 初始化中
        - 运行中
        - 未知字符串
```

### 11.4 幂等设计

- **重复调用安全**：如果 Task 已经是终态，只推送 WebSocket 通知，不修改数据库

- **并发安全**`updateTaskStatusCancelled` 内部使用 CAS，多个请求同时到达只有一个能成功修改状态

- **消息取消安全**`cancelInflightA2aMessagesForTask` 使用批量 UPDATE，将所有待投递消息标记为终止

### 12.4 可能被追问的深度问题

**Q1：为什么不用消息队列（Kafka/RabbitMQ）而用数据库 + 定时任务来做消息投递？**

A：因为协作消息的特点是"条件投递"——只有目标 Agent 空闲时才能投递。消息队列是"发了就消费"，无法做到"消费前先检查目标状态"的语义。而且消息量不大（一次协作通常几十条消息），用数据库 + 定时扫描完全够用，不需要引入额外的中间件复杂度。

**Q2：CAS 失败后怎么处理？会不会一直失败？**

A：CAS 失败说明有另一个线程已经成功了，当前线程直接放弃即可——不需要重试，因为工作已经被完成了。这不是"竞争失败需要重试"的场景，而是"幂等操作只需一个成功"的场景。所以不会出现活锁。

**Q3：Todo 的依赖关系会不会成环？怎么检测？**

A：目前依赖关系由 Agent（LLM）自行规划，系统层面没有做显式的环检测。但因为调度是被动触发的（Todo 完成时才触发下游），如果存在环，相关 Todo 会永远停留在 PENDING 状态，最终被任务超时机制兜底终止。在实际使用中，LLM 规划的任务通常是树形或 DAG 结构，不太会出现环。如果要加强健壮性，可以在 Todo 创建时做 DFS 环检测。

**Q4：如果队长 Agent 自己挂了怎么办？**

A：如果队长 Agent 的 session 出了问题，投递给它的任务（包括 notify_complete 总结通知）会进入重试机制。如果重试 20 次都失败，`onAgentFailed` 会将队长的 Todo 标记为 BLOCKED，最终 Task 标记为 FAILED。用户可以看到 Task 状态为失败，并查看各队员已完成的 Todo 和产出。这也是为什么所有产出都要写到共享工作区——即使队长挂了，队员的工作成果不会丢失。

**Q5：这个系统的瓶颈在哪里？如何扩展？**

A：当前的定时处理器是全局单点（通过 Redis 锁保证只有一个实例执行），当任务量大时可能成为瓶颈。扩展方案：按 taskNo 分片，不同实例处理不同分片的任务。另外 A2A 消息的空闲检测是通过查 `agent_chat_record` 表实现的，高并发下可能有数据库压力。可以考虑用 Redis 缓存 Agent 的空闲状态，减少数据库查询。

**Q6：Outbox 模式相比直接投递有什么好处？**

A：Outbox 模式解决的是"写库和投递不是一个原子操作"的问题。如果先投递再写库，投递成功但写库失败就会导致状态不一致。如果先写库再投递，写库成功但投递失败，消息就丢了。Outbox 模式是：先写一条 Outbox 记录（和业务数据在同一个事务中），然后异步投递，投递成功后删除 Outbox 记录。如果投递失败，Outbox 记录还在，定时任务会兜底重试，保证 at-least-once 投递语义。

**Q7：A2A 协议为什么要区分 task 通道和 a2a 通道？**

A：这是安全和职责分离的考虑。task 通道的消息（task_assign、notify_complete）代表的是"系统行为"——系统分配任务、系统通知完成，这些行为必须由调度中心控制，Agent 不能自己伪造。如果让 Agent 能发 task_assign 消息，就等于让"工程师"自己给自己签署工单——绕过了项目经理的管控。a2a 通道是"工程师之间的讨论"，这个是自由的，但不能用来下达命令。
