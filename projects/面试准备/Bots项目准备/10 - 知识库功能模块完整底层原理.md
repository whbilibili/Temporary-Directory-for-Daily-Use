# 知识库功能模块完整底层原理

> 项目：efficiency-agent-service — AI 智能体平台后端服务
>
> 定位：面向面试场景，用通俗语言解释知识库模块的完整功能和底层实现
>
> 时间：2026.07

---

## 概述

### 知识库是做什么的

知识库是平台的"企业私有知识大脑"。用户可以把公司文档、操作手册、FAQ、技术规范等内容导入到知识库中，智能体在对话时可以自动检索这些知识，基于私有内容回答用户问题——这就是所谓的 RAG（检索增强生成）。

### 一个反直觉的关键结论

调研最重要的发现是：知识库的核心能力（创建管理、文档解析、向量化存储、向量检索）并不在这个 Java 仓库里，而是在一个完全独立的兄弟服务（知识库专用服务）中。

本仓库（efficiency-agent-service）是知识库的"消费方"，只负责三件事：

1. 绑定管理：记录"哪个智能体绑定了哪些知识库"
2. 技能化注入：把知识库变成智能体能理解的"技能说明书"
3. 对话集成：在对话时提醒 AI 使用知识库

真正的文档解析、分片、向量化、存储、检索引擎都在外部服务。本仓库通过三种方式与外部知识库服务交互：SDK 直接调用（同数据源的 jar 包依赖）、HTTP 远程调用（Retrofit 客户端）、Python 脚本中转（容器内的 Hook 脚本回调 Java 接口再透传）。

理解了这个架构边界，才能准确向面试官描述"我做的是什么部分"。

## 一、知识库的数据模型

### 1.1 存在哪里

知识库的核心数据存在外部知识库服务的数据库中，本仓库能看到的表主要是：

知识库信息表：存储每个知识库的基本信息——ID、名称、描述、摘要（由 AI 自动生成的知识库内容概述）。本仓库通过一个专用的查询映射器直接读取摘要字段，用于生成技能说明书。

智能体配置表：记录"哪个智能体绑定了哪些知识库"——配置键为 `knowledgeIndexs`，值是逗号分隔的知识库 ID（如 `"4015,4023,4099"`）。每个知识库还可以单独配置召回策略。

### 1.2 知识库的前端展示数据

从前端视角看，知识库列表页展示的信息包括：ID、名称、状态（启用/未启用）、知识单元数量（文档被切分后的片段数）、数据集数量（导入的数据源数）、被引用次数（被多少个智能体/工作流使用）、创建和更新时间、归属空间和租户。

### 1.3 召回策略类型

本仓库能看到的召回策略有两种：

默认知识库召回：直接调用知识库的向量检索能力，按语义相似度返回最相关的文档片段。

自定义召回（走工作流）：不走默认检索，而是触发一个用户自定义的工作流来处理检索逻辑——比如先做意图识别、再路由到不同知识库、最后做结果过滤。这给了高级用户自定义检索逻辑的能力。

向量存储引擎支持三种：Elasticsearch、Redis、Milvus。

## 二、知识库的创建和管理

### 2.1 创建流程

用户创建知识库的操作不在本仓库，而是由外部知识库服务提供接口。本仓库在需要时（比如删除空间前检查是否有知识库）通过 SDK 调用外部服务来查询知识库列表。

### 2.2 数据源导入

从本仓库能看到的入口来看，知识库支持两种数据导入方式：

文本片段导入：直接提交一组文本内容列表，每条文本被向量化后存入知识库。

学城 Wiki 链接导入：提交一个或多个学城（公司内部 Wiki 平台）的文档链接，系统自动抓取文档内容（需要携带用户 Cookie 做身份验证），解析后导入知识库。

实际的文档解析（PDF 解析、Word 解析、网页抓取等）、文本分片（把长文档切成适合向量检索的短片段）、向量化计算（用 Embedding 模型把文本转成向量）全部在外部服务完成，本仓库只是"转发"导入请求。

### 2.3 元数据管理

知识库的摘要信息（`kb_summary`）由外部服务用 AI 自动生成——分析知识库中的文档内容，生成一段概括性的描述文字。本仓库在生成技能说明书时会读取这个摘要，告诉 AI 模型"这个知识库是关于什么的"，帮助模型判断什么时候该检索哪个知识库。

值得一提的是，这里有一个技术陷阱：外部知识库服务的 SDK 线上版本的实体类还没同步 `kb_summary` 字段（依赖的分支还未合并上线），所以本仓库特地写了一个绕过实体类、直接查单列的原始 SQL 映射器来读取摘要。这是一个典型的"跨团队依赖导致的技术债"。

## 三、知识库的检索机制——"教 AI 自己查资料"

这是知识库模块最核心也是最独特的设计。

### 3.1 核心理念：后端不检索，让 AI 自己检索

传统的 RAG 系统是这样的：用户提问 → 后端调向量数据库检索 → 把检索结果拼到提示词里 → 发给大模型 → 模型回答。后端是检索的执行者。

本系统的设计完全不同：后端不做检索。后端做的事情是"教会" AI 怎么查资料——往容器里塞两份文件：

文件一：技能说明书（`.claude/skills/knowledge-recall/SKILL.md`）

这份说明书的内容是：

- 一张 Markdown 表格，列出了这个智能体绑定的所有知识库的 ID、名称和摘要
- 一段使用指南："要查资料时，执行 `ov-kb recall --kb-domain-id {知识库ID} --query "问题内容"` 这条命令"
- 安装工具的方法（`ov-kb` 是一个内部 npm 包）
- 常见报错的排查方法

文件二：使用规则（`.claude/rules/knowledge.md`）

内容来自公司配置中心（Apollo），提醒 AI 在什么情况下应该主动去查知识库。

### 3.2 对话时的检索流程

当用户与绑定了知识库的智能体对话时：

1. 对话开始前：初始化钩子往系统提示词后面悄悄加一句——"当问题模糊或缺少信息时，优先使用知识库技能"。这是后端唯一主动介入对话内容的地方。

1. 对话进行中：AI 模型在容器的沙箱里运行，它读到了前面说的两份文件，知道自己有哪些知识库可以用。当它判断"这个问题需要查资料"时，就自己执行 `ov-kb recall` 命令——这个命令在容器内调用知识库服务的向量检索 API，返回一段 JSON 格式的结果（包含相关文档片段、相似度评分等）。

1. 结果整合：AI 模型自己读懂 JSON 结果、提取有用信息、组织成自然语言回答。

整个"调用命令 → 解析结果 → 组织回答"的过程完全发生在 AI 的推理过程中，后端只是提前把说明书放好，不参与也看不到具体检索过程。

### 3.3 为什么这样设计

这种"让 AI 自己检索"的设计有三个好处：

智能判断：AI 可以根据对话上下文判断是否需要检索（不是每次都检索），可以自主决定检索什么 query（比用户原始问题更精准），还可以多次检索（先粗检索缩小范围再细检索）。

结果质量：AI 不是机械地把检索结果拼到回答里，而是理解检索结果后用自己的语言组织回答，质量远高于传统 RAG 的"拼接"方式。

架构简洁：后端不需要写复杂的检索逻辑、结果排序逻辑、提示词拼接逻辑，这些全部交给 AI 处理。后端只负责"把说明书放对位置"。

## 四、知识库与智能体的绑定机制

### 4.1 绑定操作

用户在界面上给一个智能体勾选知识库、点保存后，后端做两件事：

第一步：把知识库 ID 列表（逗号分隔）作为一条配置记录存进智能体的配置表。

第二步：异步触发"生成说明书文件"的工作——把最新的知识库列表渲染成技能说明书和规则文件，写入容器（有状态智能体）或数据库（无状态智能体）。

### 4.2 知识库变更时的同步

知识库信息发生变化时（改名、改描述、删除），知识库服务会主动回调通知本系统。本系统收到通知后：

1. 反查"所有绑定了这个知识库的智能体"
2. 把每一个相关智能体的说明书文件整体重新生成（不是增量修改）——重新查一遍所有绑定的知识库信息，重新渲染说明书
3. 如果知识库被删除了，还会把这个 ID 从对应智能体的绑定列表里摘除

### 4.3 刷新时机

说明书的生成只在两个时机触发："保存智能体"和"知识库变更回调"。智能体的容器重启或创建时不会主动刷新知识库说明书——如果是从模板创建的智能体，说明书是模板里自带的。

## 五、技术演进：三代方案并存

代码中能看到明显的三代知识库技能化方案：

### 第一代（旧方案，部分智能体类型仍在用）

每绑定一个知识库，就生成一个独立的技能文件夹（类似 `kb-知识库ID`），有几个知识库就有几份说明书。目前 Codex、Cursor、Gemini 类型的智能体还在用这种方式。

### 第二代（中间态，基本废弃）

把知识库转换成平台统一的"技能包"格式再安装。代码还在但主流程已经不走它了。

### 第三代（当前主流方案）

不管绑定几个知识库，统一只生成一份技能说明书 + 一份规则文件。所有知识库列成一张表格放在说明书里，文案模板放在 Apollo 配置中心可以热更新。Claude Code、无状态 Claude Bot、OpenClaw 类型的智能体用这种方式。

新旧方案的切换没有统一开关，而是按智能体的底座类型（Claude/Codex/Cursor/Gemini/OpenClaw）硬编码分流的——不同底座走不同路径。这是历史包袱没有完全清理干净的体现。

## 六、长期记忆系统（与知识库检索不同的另一套机制）

除了知识库检索，系统还有一套独立的"长期记忆"机制，基于 OpenViking 向量数据库实现。虽然它和知识库都涉及向量检索，但解决的是不同问题：

知识库检索：查企业预置的文档（FAQ、手册、规范），内容由人主动导入，是"已知知识"。

长期记忆：自动从对话中提取值得记住的信息（用户偏好、重要决定），是"对话中学到的知识"。

### 长期记忆的工作方式

系统往容器中部署两个 Python 钩子脚本：

自动捕获脚本（对话结束后触发）：读取本轮对话内容，发送给知识服务，由另一个 AI 模型异步提取出值得记住的事实，存入 OpenViking 向量数据库。

自动召回脚本（用户发消息时触发）：并发搜索三路——用户级记忆、智能体级记忆、智能体技能知识。对搜索结果做去重、重排（综合考虑语义相关度、时间新鲜度、词汇重叠度等因素），挑选 Top N 条结果，包装成 `<relevant-memories>` 标签注入到对话上下文中。

这些 Python 脚本不直接调用 OpenViking，而是回调本仓库的 Java 接口，Java 接口再透传给外部 OpenViking 服务——形成一个"容器 Python 脚本 → Java 中转 → OpenViking"的调用链。

## 七、知识库的权限与共享

### 7.1 权限模型

知识库依附于"空间"这个概念。一个知识库只能属于一个空间，进而只属于这个空间所在的一个租户。用户能不能看到/编辑某个知识库，取决于他在这个空间里的角色。

当空间的成员或权限发生变化时，本系统会主动通知外部知识库服务重新计算权限缓存。细粒度的"谁能编辑谁能删除"判断逻辑在外部知识库服务中。

### 7.2 共享机制

知识库不支持跨租户共享。共享的粒度是"整个知识库"而不是单篇文档——想让别人用某个知识库，本质上是把人拉进知识库所在的空间。没有文档级别的精细共享。

### 7.3 统计能力

知识库列表页展示的统计信息包括：文档数量、数据集数量、被引用次数（被多少个智能体/工作流使用）、创建更新时间等。这些数据通过每天定时扫描智能体和工作流的配置、统计"引用次数"后写入统计表。

当前的统计空白：没有发现"检索调用次数"、"召回命中率"、"检索成功率"这类真正反映知识库使用效果的统计数据，也没有文档占用存储空间大小的统计。这是当前系统的一个明显不足。

## 八、CLI 接入功能

知识库页面上的"CLI 接入"实际上是平台的通用开放 API 令牌系统（详见 [09-知识库CLI接入与开放API底层原理.md](./09-知识库CLI接入与开放API底层原理.md)）。简要来说：

用户在前端填写名称标识、选择要绑定的知识库/智能体/工作流/能力，点击生成后，系统创建一个 32 位随机令牌和一组权限记录，经管理员审批后，外部系统（如 CI/CD 管道、命令行工具）可以在 HTTP 请求头中携带这个令牌来调用平台的智能体 API，智能体在对话中自主检索绑定的知识库。

## 九、与知识库同页面的其他功能

从界面左侧菜单看到的其他功能，它们与知识库的关系如下：

### Prompt 模板

这不是一个知识库的子功能，而是"验证规则"体系下的一个模块。本质是给自动化质检/校验流程配置用的提示词模板（区分系统提示词和用户提示词），支持分类管理和变量占位符。它和知识库没有直接绑定关系，主要服务于"校验智能体回复质量"这类场景。

### AI 专家 / 专家模板

代码里没有"AI 专家"这个独立概念，它其实是"Bot 模板"功能在前端的叫法。可以理解为：专家模板是蓝图，AI 专家是运行实例。用户拿一个专家模板（预置了配置文件、技能、规则等一整套东西）创建出一个真实可用的智能体，这个智能体就是"AI 专家"。

模板系统支持完整的商业化功能：发布到市场、付费购买、创作者分成、导出导入、分组管理、版本管理等。

### Skill 技能 / API 工具 / MCP 服务

技能的创建和发布在另一个独立服务中，本仓库只负责技能的安装、调用和鉴权。API 工具可能是前端对某类工作流节点的包装。MCP 服务不是独立管理页面，而是嵌在智能体配置中的一个字段——用户编辑智能体时配置 MCP 服务器信息，随智能体配置一起保存。

## 十、设计亮点

### 1. "知识库技能化"——让 AI 自己查资料

最大的设计亮点是把知识库变成 AI 的"技能"而不是后端的"管道"。传统 RAG 是后端做检索再拼提示词，这个系统是给 AI 一份说明书让它自己决定什么时候查、查什么、怎么用结果。这降低了后端复杂度，同时提升了检索的智能程度和结果质量。

### 2. "说明书热更新"——配置中心驱动

技能说明书的文案模板不是硬编码在 Java 代码里，而是放在 Apollo 配置中心。这意味着可以随时优化说明书的措辞、调整使用指南、改变检索策略，而不需要重新发版。发版成本几乎为零。

### 3. "消费方与引擎方分离"——清晰的架构边界

知识库的创建、文档解析、向量化、检索引擎是一个独立服务（引擎方），智能体平台只负责绑定关系管理和对话集成（消费方）。两个服务通过 SDK + HTTP + 回调三种方式交互，职责边界清晰。这使得两个服务可以独立迭代——引擎方可以优化检索算法而不影响对话流程，消费方可以改变注入方式而不影响底层存储。

### 4. "双轨并行"——知识库检索 + 长期记忆

知识库解决"查企业预置知识"的问题，长期记忆解决"记住对话中学到的信息"的问题。两者都用向量检索技术，但场景不同、触发机制不同、存储位置不同。双轨并行让智能体既有"专业知识"又有"个人记忆"。

### 5. 技术债的坦诚——三代方案并存

三代知识库技能化方案并存是一个典型的技术债案例：新方案更好但旧方案没有完全清理。这在面试中可以坦诚地讲——说明你了解系统的历史演进，知道技术债的成因（不同智能体底座类型的差异），也知道理想方案是什么（统一收敛到第三代）。

## 十一、面试速答卡片

问：知识库的整体架构是怎样的？

答：知识库采用"消费方 + 引擎方"分离的架构。引擎方是一个独立的知识库服务，负责文档解析、分片、向量化、存储和检索。消费方是本仓库的智能体平台，负责三件事：管理"哪个智能体绑定了哪些知识库"的绑定关系、把知识库变成 AI 能理解的"技能说明书"文件、以及在对话时提醒 AI 使用知识库。两个服务通过 SDK 调用、HTTP 接口和回调通知三种方式交互，职责边界清晰。

问：知识库检索和传统 RAG 有什么不同？

答：传统 RAG 是"后端检索"——后端代码调向量数据库查出结果，拼到提示词里发给大模型。这个系统是"AI 自主检索"——后端只往容器里放一份技能说明书，告诉 AI "你有这些知识库可以用，要查资料时执行这条命令"，AI 在对话过程中自己判断是否需要检索、构造什么 query、怎么整合结果。好处是 AI 可以智能判断检索时机、自主构造更精准的 query、多次检索逐步缩小范围，检索质量远高于固定管道。代价是依赖 AI 的推理能力来决定何时检索。

问：知识库变更后怎么同步到已绑定的智能体？

答：知识库服务在知识库信息变更（改名、改描述、删除）时会回调通知我们的服务。收到通知后，系统反查所有绑定了这个知识库的智能体，然后整体重新生成每个智能体的技能说明书文件——重新查一遍所有绑定的知识库信息、重新渲染说明书。如果知识库被删除了，还会把它的 ID 从绑定列表中摘除。这是"整体重建"而非"增量修改"的策略，简单可靠但效率不是最优。

问：代码里有三代知识库方案并存，这是怎么回事？

答：这是技术演进的痕迹。第一代是每个知识库一份独立说明书；第二代尝试用统一的技能包格式但已基本废弃；第三代是当前主流方案，不管绑多少知识库都只生成一份统一的说明书，文案放在配置中心可以热更新。三代方案按智能体底座类型（Claude/Codex/Cursor/Gemini/OpenClaw）分流，新底座用第三代，老底座还在用第一代。这是典型的技术债——理想方案是全部收敛到第三代，但因为不同底座的差异还没有完全清理。

问：知识库检索和长期记忆有什么区别？

答：两者都用向量检索技术，但解决不同问题。知识库检索是查"企业预置的知识"——由人主动导入的文档、FAQ、手册等。长期记忆是记住"对话中学到的信息"——AI 自动从对话中提取用户偏好、重要决定等事实，存入向量库，下次对话时自动召回。知识库的内容相对稳定，长期记忆随对话不断积累。两者并行让智能体既有"专业知识"又有"个人记忆"。

问：知识库的权限怎么控制？

答：知识库依附于"空间"这个概念，一个知识库只能属于一个空间。用户能否访问知识库取决于他在空间中的角色。不支持跨租户共享，共享粒度是整个知识库而非单篇文档——想让别人用，就把人拉进知识库所在的空间。细粒度的权限判断在外部知识库服务中。
