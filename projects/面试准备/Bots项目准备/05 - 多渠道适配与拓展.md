# 05 - 多渠道适配与扩展功能详解

> 本文档面向面试准备场景，用通俗易懂的语言讲解 AI 智能体平台中多渠道适配、Skill 追踪、模型管理等核心功能模块的设计与实现。

---

## 一、多渠道适配框架

### 1.1 问题背景

用户和智能体对话可能来自完全不同的入口：

- **网页端**：通过 WebSocket 实时双向通信

- **大象（内部 IM）**：通过 HTTP Webhook 接收消息推送

- **飞书**：通过 Lark SDK 建立长连接

- **钉钉**：通过 DingTalk Stream SDK 建立长连接

- **第三方系统**：通过自定义 WebSocket 协议（Bridge）接入

每种渠道的消息格式、传输协议、鉴权方式都不一样。如果每来一个新渠道就在业务逻辑里加一堆 `if-else`，代码很快就会变成一团乱麻。

**打个比方**：就像你家里有 Type-C、Lightning、Micro-USB 三种数据线，每次充电都要翻找对应的线。我们需要的是一个「万能充电转接头」——不管什么接口进来，内部统一转成一种标准格式来处理。

### 1.2 统一渠道接口设计

系统定义了一个统一的 `ChannelProvider` 接口，所有渠道都必须实现它。核心方法如下：

```Plain
ChannelProvider 接口
├── getChannelId()                → 返回渠道唯一标识，如 "daXiang"、"feishu"
├── resolveRoute(inbound)         → 路由解析：从消息中提取 agentId、sessionId 等
├── transform(inbound, route)     → 消息转换：将渠道原始消息转为统一 ChatRequest
├── beforeExecute(request, ...)   → 前置处理：调用前的准备工作
├── afterInvokeSetup(request, ...)→ 中置回调：拿到 messageId 后的处理（如创建卡片）
├── afterExecute(request, ...)    → 后置处理：调用完成后的清理或通知
├── sendMessage(outbound)         → 消息发送：将回复推送给用户（必须实现）
├── sendErrorMessage(outbound)    → 错误消息发送：默认走 sendMessage
├── replyText(context, text)      → 快捷指令回复
├── getCapabilities()             → 能力声明：如 {"text","image","file"}
└── invalidateCurrentSession()    → 会话重置（"/new" 指令）
```

**设计要点**：

- 大部分方法提供了 `default` 默认实现，新增渠道只需实现 `getChannelId()` 和 `sendMessage()` 两个方法即可最小化接入
- `getCapabilities()` 让每个渠道声明自己支持什么内容类型（纯文本？图片？文件？），系统会自动过滤掉渠道不支持的内容

### 1.3 四种渠道实现详解


|     |            |           |             |            |
| --- | ---------- | --------- | ----------- | ---------- |
| 特性  | 大象 DaXiang | 飞书 Feishu | 钉钉 DingTalk | Bridge 自定义 |


| **channelId** | `"daXiang"` | `"feishu"` | `"dingtalk"` | `"bridge"` |

| **传输方式** | HTTP Webhook | Lark SDK 长连接 | Stream SDK 长连接 | WebSocket |

| **消息接收** | 被动推送到回调接口 | SDK 内部事件分发 | SDK 内部事件分发 | 主动 WS 连接 |

| **流式回复** | 大象卡片（带超时处理器） | CardKit 流式卡片 | AI Card 流式卡片 | WS reply_stream 帧 |

| **防重复** | Redis setNx 去重 | SDK 内置 | SDK 内置 | messageId 异常拦截 |

| **能力声明** | text, image, file | text, image, file | text, image, file | 每个 adapter 动态声明 |

| **代码行数** | ~1115 行 | ~1112 行 | ~827 行 | ~644 行 |

**各渠道的特色机制**：

- **大象**：收到消息后先用 Redis `setNx` 做幂等去重（Webhook 可能重推）。回复时先创建一个"处理中"卡片，AI 回答完后再更新卡片内容。如果超时还注册了超时处理器自动标记失败。

- **飞书**：用 `EventDispatcher` + 独立线程池（4-8 线程）处理消息，避免阻塞 SDK 的 3 秒回调窗口。流式回复用 CardKit 的 `streaming_mode`，需要维护严格递增的序列号。

- **钉钉**：流式回复用 AI Card，有 300ms 的消息节流。如果卡片发送失败，自动降级为纯 Markdown 消息。

- **Bridge**：能力不是固定的，而是在连接时由 adapter 动态声明（比如一个 adapter 可能只支持 text，另一个支持 text + image）。

### 1.4 渠道编排引擎

渠道编排引擎 `ChannelServiceImpl` 是整个框架的"调度中心"。它在启动时通过 Spring 自动发现所有 `ChannelProvider` Bean，建立 `channelId → provider` 的映射表。

#### 入站处理链（消息进来）

```Plain
用户发送消息
    │
    ▼
inboundMessage.validate()          ← 校验必填字段（channelId, agentId, senderId...）
    │
    ▼
providerMap.get(channelId)         ← 根据 channelId 找到对应的 Provider
    │
    ▼
provider.resolveRoute(inbound)     ← 路由解析（确定 sessionId、accountId 等）
    │
    ▼
commandDispatcher.tryDispatch()    ← 快捷指令拦截（如 "/new" 重置会话）
    │                                 如果命中指令 → 直接回复，流程结束
    ▼
provider.transform(inbound, route) ← 消息格式转换：渠道格式 → 统一 ChatRequest
    │
    ▼
provider.beforeExecute(request)    ← 前置处理（如准备上下文信息）
    │
    ▼
injectChannelContext(request)      ← 注入渠道上下文到 request.extra
    │
    ▼
validateChatRequest(request)       ← 最终校验
    │
    ▼
httpChatService.asyncInvokeChat()  ← 异步发起对话
    │
    ▼
provider.afterInvokeSetup()        ← 中置回调（如创建"处理中"卡片）
    │
    ▼ (finally)
provider.afterExecute(success)     ← 后置处理（无论成功失败都执行）
```

#### 出站处理链（消息出去）

消息出站经过 Redis Stream，由 `AbstractStreamMessageHandlerService` 统一处理：

```Plain
Redis Stream 消息到达
    │
    ▼
dispatchToChannel(parsedMsg, result, dto)
    │
    ├── 读取 chatRequest.extra.channelId
    │   如果为空 → 不是渠道消息，跳过
    │
    ├── 判断消息状态（成功/失败/继续）
    │
    ├── adaptOutboundContents()        ← 子类转换内容格式
    │
    ├── filterContentsByCapabilities() ← 按渠道能力过滤内容类型
    │   （Bridge 跳过此步，因为能力是动态的）
    │
    ├── 构建 ChannelOutboundMessage
    │
    └── channelService.dispatchOutboundMessage()
        └── provider.sendMessage(outbound)  ← 最终发送
```

**打个比方**：入站链就像机场的入境通道——先检查护照（validate），再查签证类型（resolveRoute），过海关安检（transform + beforeExecute），最后放行入境（invokeChat）。出站链就像快递分拣——根据收件地址（channelId）找到对应的快递公司（provider），过滤掉不支持的物品类型（filterCapabilities），最后投递（sendMessage）。

### 1.5 统一消息模型

系统定义了一套统一的消息 DTO，所有渠道都使用同一套数据结构：

**入站消息** `ChannelInboundMessage`：

- 必填：channelId, agentId, agentType, messageId, senderId, chatType(PRIVATE/GROUP), text
- 可选：images, files, accountId, senderName, senderMis, chatId, threadId, rawMetadata

**出站消息** `ChannelOutboundMessage`：

- sessionId, channelId, targetChatId, threadId
- contents（内容列表，每项是 `MessageContent`）
- chatRecordStatusEnum（消息状态）
- metadata（上下文快照）

**消息内容** `MessageContent`：

- type：TEXT / IMAGE / FILE / AUDIO / VIDEO / CARD / TOOL_CALL / TOOL_RESULT
- text / mediaUrl / mediaKey / fileName / mimeType / toolCallId / toolName 等字段

## 二、Bridge 自定义渠道（重点）

### 2.1 设计动机

大象、飞书、钉钉都是内置的 IM 渠道，但实际业务中还有大量第三方系统需要接入智能体平台：

- 内部工具系统（用 Python/Go 写的）
- 合作伙伴的系统
- 自研的移动端 App

这些系统用什么语言开发、什么协议通信都不确定。我们需要一种**语言无关、协议简单**的接入方式。

**Bridge 的定位**：就像酒店的"万能转接插座"，不管你是欧标、美标还是英标插头，插上去都能用。第三方只需要会 WebSocket + JSON，就能接入平台。

### 2.2 接入流程

```Plain
第三方系统（Adapter）                          平台（Bridge Server）
    │                                              │
    │ ①  WebSocket 连接                             │
    │ ─────────────────────────────────────────→    │
    │    wss://platform/bridge/ws                   │
    │    Header: Authorization: Bearer <token>      │
    │                                              │
    │ ② 发送 register 消息                           │
    │ ─────────────────────────────────────────→    │
    │ { "type": "register",                        │
    │   "adapterId": "my-tool-system",             │
    │   "capabilities": ["text","image","file"] }  │
    │                                              │
    │ ③ 收到 register_ack                            │
    │ ←─────────────────────────────────────────    │
    │ { "type": "register_ack",                    │
    │   "adapterId": "my-tool-system",             │
    │   "status": "ok" }                           │
    │                                              │
    │ ④ 发送用户消息                                  │
    │ ─────────────────────────────────────────→    │
    │ { "type": "message",                         │
    │   "messageId": "msg-001",                    │
    │   "agentId": "agent-123",                    │
    │   "senderId": "user@corp.com",               │
    │   "text": "帮我查一下今天的数据" }              │
    │                                              │
    │ ⑤ 收到流式回复                                  │
    │ ←─────────────────────────────────────────    │
    │ { "type": "reply_stream",                    │
    │   "messageId": "msg-001",                    │
    │   "content": "正在查询..." }                   │
    │                                              │
    │ ⑥ 收到最终回复                                  │
    │ ←─────────────────────────────────────────    │
    │ { "type": "reply",                           │
    │   "messageId": "msg-001",                    │
    │   "content": "今天的数据是..." }               │
    │                                              │
    │ ⑦ 定期心跳                                     │
    │ ─────────────────────────────────────────→    │
    │ { "type": "ping" }                           │
    │ ←─────────────────────────────────────────    │
    │ { "type": "pong" }                           │
```

### 2.3 连接管理

**BridgeConnectionManager** 负责管理所有活跃的 adapter 连接：

```Plain
连接注册表（ConcurrentHashMap）
┌──────────────┬───────────────────────────────┐
│  adapterId   │  ConnectionInfo               │
├──────────────┼───────────────────────────────┤
│ "my-tool"    │ { session, capabilities,      │
│              │   lastHeartbeat, adapterId }   │
│ "crm-bot"   │ { session, capabilities,      │
│              │   lastHeartbeat, adapterId }   │
└──────────────┴───────────────────────────────┘
```

**三个关键机制**：

1. **心跳超时清理**`@Scheduled` 定时任务每隔一段时间扫描注册表，90 秒无心跳的连接自动断开并清理`evictStaleConnections()`）

2. **线程安全发送**`sendSafe()` 方法用 `synchronized` 保证同一个 WebSocket session 不会被并发写入导致消息错乱

3. **断连感知**：当 adapter 断连时触发回调，自动清理该 adapter 的所有消息上下文

### 2.4 会话映射与流式输出

**会话映射**：Bridge 渠道使用独立的 `bridge_session_mapping` 表，用四维唯一键定位会话：

```Plain
唯一键 = (agentId, mis, platform, chatId)
```

这和其他三个渠道用的 `(sessionType, mis, agentId)` 不同，因为 Bridge 需要支持同一个用户在不同平台、不同聊天窗口同时和同一个 Agent 对话。

**流式输出控制**：

- **消息节流**：300ms 间隔，避免频繁推送导致客户端闪烁

- **能力门控**：只有声明了 `preview` 能力的 adapter 才会收到流式预览；只有声明了 `typing` 的才会收到"正在输入"提示

- **特殊内容分发**：tool_call、tool_result、file 等"特殊内容"以 OpenAI 兼容格式推送，方便第三方系统解析

**一个完整的 Bridge 对话示例**：

```Plain
1. CRM 系统通过 WS 连接平台，注册 adapterId="crm-bot"，声明能力 ["text","preview"]
2. 用户在 CRM 系统内发消息："帮我查一下客户张三的最近订单"
3. CRM 发送 message 消息到平台
4. 平台 BridgeWebSocketHandler 收到消息：
   - 验证 adapterId 已注册
   - 构建 ChannelInboundMessage
   - 异步提交到 channelService.handleInboundMessage()
5. ChannelService 执行入站处理链：
   - BridgeChannelProvider.resolveRoute() → 查 bridge_session_mapping 表
   - BridgeChannelProvider.transform() → 构建 ChatRequest
   - 发起异步对话
6. AI 生成回复，通过 Redis Stream 传递
7. 出站处理：
   - 跳过全局能力过滤（Bridge 是动态能力）
   - BridgeChannelProvider.sendMessage() → filterContentsByCapability()
   - 因为 CRM 声明了 preview，所以会收到流式预览帧
   - 最终回复通过 WS 推送回 CRM 系统
```

## 三、Skill 追踪与评测

### 3.1 问题背景

智能体可以配置各种技能（Skill），比如"代码审查"、"数据库查询"、"文档生成"等。但一个关键问题是：**这些技能到底有没有发挥作用？效果如何？**

**打个比方**：就像你给员工配了各种办公软件，但你不知道他们实际用了哪些、用得好不好。Skill 追踪系统就是给每个技能装了一个"使用记录仪 + 效果评估器"。

### 3.2 两阶段方案

整个系统分为两个阶段，各司其职：

```Plain
╔══════════════════════════════════════════════════════════════╗
║                    第一阶段：实时关联                         ║
║                                                              ║
║  用户对话过程中                                                ║
║  ┌────────┐    PUT /associations     ┌────────────────────┐  ║
║  │ 前端   │ ──────────────────────→  │ association 表     │  ║
║  │ (aie)  │   上报 sessionId+skillId │ (实时写入/更新)     │  ║
║  └────────┘                          └────────────────────┘  ║
║                                                              ║
║  关键：ON DUPLICATE KEY UPDATE 保证幂等                        ║
╚══════════════════════════════════════════════════════════════╝
                            │
                      每小时触发一次
                            │
                            ▼
╔══════════════════════════════════════════════════════════════╗
║                    第二阶段：定时物化                         ║
║                                                              ║
║  XXL-Job 定时任务 (每小时)                                     ║
║                                                              ║
║  ① 扫描 association 表，找到最近 65 分钟内更新的记录            ║
║      │                                                       ║
║      ▼                                                       ║
║  ② 按 sessionId 分组，批量拉取 trace-server 的 Trace 数据     ║
║      │                                                       ║
║      ▼                                                       ║
║  ③ 调用 gpt-4.1 评估每个 Skill 的影响窗口和归因               ║
║      │                                                       ║
║      ▼                                                       ║
║  ④ 生成 timeline_json 和 tool_calls_json                     ║
║      │                                                       ║
║      ▼                                                       ║
║  ⑤ 结果写入 agent_skill_trace 表（upsert）                    ║
║      │                                                       ║
║      ▼                                                       ║
║  ⑥ 更新 association 的 materialize_status 为 MATERIALIZED     ║
╚══════════════════════════════════════════════════════════════╝
```

**为什么分两阶段？**

- **第一阶段要快**：用户在对话，不能让上报操作卡住体验。所以只做一个简单的 upsert（插入或更新），毫秒级完成。

- **第二阶段要准**：评估效果需要完整的 Trace 数据和 LLM 分析，这是 CPU/网络密集型操作，放在后台定时做。

### 3.3 评估细节

#### LLM 评估流程

物化任务对每个 `(sessionId, skillId)` 组合执行以下评估：

```Plain
① 从 trace-server 拉取该 session 的全部 Trace 记录
    │
    ▼
② 按时间升序排列所有 Trace
    │
    ▼
③ 计算"工程窗口"（Engineering Window）
   │  找到 action="server_cc_tool_post_use" 且 toolName="Skill" 且 skill 名称匹配的 Trace
   │  窗口起点 = 该 Skill 的 post-use 记录
   │  窗口终点 = 下一个 status_changed 事件，或同一 assistantMessageId 的最后一条
    │
    ▼
④ 截断窗口内的 Trace（最多 80 条，总字符 ≤ 120,000）
   │  优先保留尾部（最新的更重要）
    │
    ▼
⑤ 构建 LLM Prompt，发送给 gpt-4.1
   │  temperature = 0.1（低随机性，追求稳定输出）
   │  maxTokens = 12,000
    │
    ▼
⑥ 解析 LLM 返回的 JSON，校验 schema
   │  检查所有引用的 traceId 是否在窗口内（防止幻觉）
    │
    ▼
⑦ 根据 LLM 的归因结果，构建 timeline 和 tool_calls
```

#### LLM 的评估任务

系统给 gpt-4.1 的角色是"Skill Trace 归因助手"，要求它输出一个结构化 JSON：

```JSON
{
  "summary": "该 Skill 执行了代码审查，发现了 3 个问题并提供了修复建议",
  "confidence": 0.85,
  "timelineRefs": [
    { "traceId": "trace-001", "attribution": "PRIMARY" },
    { "traceId": "trace-002", "attribution": "SECONDARY" }
  ],
  "toolCallRefs": [
    { "toolName": "Bash", "traceId": "trace-003", "attribution": "PRIMARY" }
  ],
  "modelCallRefs": [
    { "modelCallId": "call-001", "traceId": "trace-004", "attribution": "PRIMARY" }
  ],
  "risks": ["部分 Trace 数据缺失，影响归因准确性"]
}
```

**归因等级**：

- **PRIMARY**：明确属于当前 Skill 主执行链的步骤（只有 PRIMARY 的 token 消耗才计入统计）

- **SECONDARY**：相关但非核心的步骤

- **CONTEXT**：环境上下文，不直接相关

#### Timeline 和 ToolCalls 数据结构

**timeline_json** 记录了 Skill 执行的完整时间线：

```JSON
[
  {
    "stepPath": "1",
    "stepType": "MODEL",
    "attribution": "PRIMARY",
    "label": "gpt-4.1",
    "status": "SUCCESS",
    "startedAtMs": 1710000000000,
    "endedAtMs": 1710000001200,
    "durationMs": 1200,
    "data": {
      "usage": { "promptTokens": 1500, "completionTokens": 800 },
      "modelName": "gpt-4.1"
    }
  },
  {
    "stepPath": "2",
    "stepType": "TOOL",
    "attribution": "PRIMARY",
    "toolName": "Bash",
    "status": "SUCCESS",
    "startedAtMs": 1710000001200,
    "endedAtMs": 1710000002000,
    "durationMs": 800,
    "data": {
      "toolInput": "git diff HEAD~1",
      "toolOutput": "... diff output ..."
    }
  }
]
```

**tool_calls_json** 是 timeline 中 TOOL 类型步骤的提取汇总。

### 3.4 数据表设计

#### 表1：agent_skill_session_association（技能-会话关联表）


|                        |              |                                      |
| ---------------------- | ------------ | ------------------------------------ |
| 字段                     | 类型           | 说明                                   |
| `id`                   | BIGINT       | 主键，自增                                |
| `code_session_id`      | VARCHAR(64)  | 产品侧会话 ID                             |
| `skill_id`             | VARCHAR(64)  | 技能 UUID                              |
| `assistant_message_id` | VARCHAR      | 助手消息 ID（唯一键组成部分）                     |
| `skill_name`           | VARCHAR(256) | 技能显示名称                               |
| `environment`          | VARCHAR      | 环境标识（production/staging/test）        |
| `first_seen_at`        | DATETIME(3)  | 首次关联时间                               |
| `last_associated_at`   | DATETIME(3)  | 最近一次关联时间（定时任务扫描依据）                   |
| `materialize_status`   | VARCHAR(16)  | 物化状态：PENDING / MATERIALIZED / FAILED |

**唯一键**`(code_session_id, skill_id)` — 用于 `ON DUPLICATE KEY UPDATE` 实现幂等。

### 3.5 容错与降级

```Plain
正常路径：
  LLM 评估成功 → 构建完整 timeline（含 MODEL + TOOL 步骤）→ status = SUCCESS

降级路径1（LLM 未配置）：
  tenantId/userId/xcToken 为空 → model_version = "NOT_CONFIGURED"
  → 回退到 fallback timeline（仅包含 server_cc_tool_post_use 记录）

降级路径2（LLM 调用失败）：
  网络超时、模型报错 → status = MODEL_FAILED
  → 回退到 fallback timeline

降级路径3（LLM 输出格式错误）：
  JSON 解析失败、schema 不合法、引用了窗口外的 traceId
  → 错误码 EVAL_JSON_SYNTAX / EVAL_SCHEMA / EVAL_TRACE_NOT_IN_WINDOW
  → 回退到 fallback timeline

错误隔离：
  每个 (sessionId, skillId) 独立 try-catch
  一个失败不影响同批次其他记录的处理
```

#### SSE 流式接口

- **LLM 输出解析**`LlmJsonUtil` 先尝试直接 JSON 解析，失败则尝试从 Markdown 代码块中提取 JSON（因为 LLM 有时会用 `\`\`json 包裹输出）

## 六、ChatHook 链详解

### 6.1 设计思路

ChatHook 链采用经典的 **管道 + 过滤器模式**（Pipeline & Filter Pattern）。每一次对话请求在执行前后都会经过一系列 Hook 的处理，就像工厂流水线上的一道道工序。

**打个比方**：就像你去银行办业务——先取号（SessionCheck），再验身份（AuthInit），填表格（ContentProcess），查余额（QuotaCheck），最后办业务（Execute）。每一步都可能拦截你（比如验证不通过就直接拒绝），也可能往你的材料上盖个章（往共享上下文里写数据）。

**共享上下文** `ParamPassingDTO`：所有 Hook 共享同一个 DTO 对象，每个 Hook 都可以读取前序 Hook 写入的数据，也可以往里追加新数据：

```Plain
ParamPassingDTO（Hook 链的"传送带"）
├── request: ChatRequest          ← 原始对话请求
├── agentConfigVO                 ← 智能体配置
├── user                          ← 当前用户信息
├── tenantId                      ← 租户 ID
├── state                         ← 会话状态
├── vars: Map                     ← 自定义变量（工作区路径、环境变量等）
├── assistantMessageId            ← 助手消息 ID
├── debugInfo                     ← 调试信息
├── ccSkillPackages               ← Skill 包列表
├── claudeCodeContextInfo         ← Claude Code 上下文
├── toolChoice                    ← 工具选择策略
├── fileNameMap                   ← 文件映射
├── resultCallback                ← 结果回调
└── ...
```

### 6.2 Before Hooks（前置处理链）

Before Hooks 在对话执行前按**固定顺序**依次调用。不同引擎类型的 Hook 链组合不同，但基本遵循以下分类：

#### 第一梯队：权限与状态检查


|                            |           |          |
| -------------------------- | --------- | -------- |
| Hook                       | 职责        | 失败行为     |
| `SessionArchivedCheckHook` | 检查会话是否已归档 | 抛异常，阻止对话 |
| `TeamArchivedCheckHook`    | 检查团队是否已归档 | 抛异常，阻止对话 |


#### 第二梯队：上下文初始化


|                       |                                  |
| --------------------- | -------------------------------- |
| Hook                  | 职责                               |
| `AgentCollabInitHook` | 多智能体协作初始化（taskId、teamId、skill 包） |


| `AgentChatInitHook` | **核心初始化**：用户查找、会话信息、Agent 配置、变量注入、消息 ID 生成、WebSocket 状态通知 |

| `AgentCollabMessageContentHook` | 协作模式下追加 `[collab_task_id=...]` 到消息内容 |

#### 第三梯队：特殊处理


|                              |                             |
| ---------------------------- | --------------------------- |
| Hook                         | 职责                          |
| `RegenerateHook`             | 处理"重新生成"场景，作废旧记录            |
| `AIWorkflowGenerateInitHook` | 等待工作区初始化、容器检查、变量展开          |
| `QueryReWriteHook`           | 查询重写（iBase 上下文引用、Skill @提及） |


#### 第四梯队：引擎特有


|                                        |                 |                    |
| -------------------------------------- | --------------- | ------------------ |
| Hook                                   | 适用引擎            | 职责                 |
| `ClaudeBotBusinessContextInitHook`     | Claude Bot（无状态） | 上下文变量设置            |
| `GeminiContextConfigInitHook`          | Gemini          | Gemini 容器和上下文初始化   |
| `OpenClawBeforeHook`                   | OpenClaw        | 下载文件到 OpenClaw 工作区 |
| `ClaudeAgentRecommendQuestionInitHook` | SharedCode      | 推荐问题初始化            |
| `ClaudeAgentAskUserQuestionHandleHook` | SharedCode      | 处理"向用户提问"交互        |


#### 第五梯队：内容增强


|                            |                          |
| -------------------------- | ------------------------ |
| Hook                       | 职责                       |
| `FileEnvCheckHook`         | 文件环境设置、Skill 包 S3 URL 准备 |
| `KbAppendSystemPromptHook` | 知识库内容追加到 System Prompt   |


#### SharedCode (Claude Code) 引擎的完整 Hook 执行顺序

```Plain
① SessionArchivedCheckHook     ← 会话归档检查
② TeamArchivedCheckHook        ← 团队归档检查
③ AgentCollabInitHook          ← 协作初始化
④ AgentChatInitHook            ← 核心初始化（最重要的 Hook）
⑤ AgentCollabMessageContentHook ← 协作消息内容处理
⑥ RegenerateHook               ← 重新生成处理
⑦ AIWorkflowGenerateInitHook   ← 工作流初始化
⑧ QueryReWriteHook             ← 查询重写
⑨ ClaudeAgentRecommendQuestionInitHook ← 推荐问题
⑩ ClaudeAgentAskUserQuestionHandleHook ← 用户提问处理
⑪ FileEnvCheckHook             ← 文件环境检查
⑫ KbAppendSystemPromptHook     ← 知识库 Prompt 追加
```

### 6.3 After Hooks（后置处理链）

After Hooks 在对话执行完成后调用，分两类：

**AgentChatEndHook**（在 `finally` 块中调用）：

- 协作 idle 探测：检测 Agent 是否空闲，触发协作调度
- Task 完成检测：检查对话是否完成了协作任务
- 工作流失败上报：如果 Agent 执行失败，向协作系统上报

**StreamWorkflowTerminalHook 链**（流结束时调用）：

- 由 `StreamWorkflowTerminalHookRunner` 管理
- 只在 `WorkflowEnded`（成功）或 `WorkflowFailed`（失败）时触发
- 每个 Hook 独立 try-catch，互不影响

```Plain
StreamWorkflowTerminalHookRunner
├── StreamWorkflowTerminalHook (接口)
│   ├── afterChatWorkflowTerminal(dto, status)
│   │   ├── 实现1: 某些统计/日志 Hook
│   │   └── 实现2: CollabTaskStreamWorkflowTerminalHook（当前 no-op）
│   └── 触发条件: status == WorkflowEnded || status == WorkflowFailed
│
└── 执行方式: for-each + try-catch（一个失败不影响其他）
```

### 6.4 执行骨架与错误处理

整个 Hook 链嵌入在 `AbstractChatExecutionService.execute()` 模板方法中：

```Plain
execute(chatRequest)
│
├── try {
│   │
│   ├── ① beforeHook(dto)          ← 执行所有 Before Hooks
│   │   └── 任意 Hook 抛异常 → 跳到 catch
│   │
│   ├── ② doPrepare(dto)           ← 子类特定准备
│   │
│   ├── ③ checkQuota()              ← 订阅/额度检查
│   │
│   ├── ④ preHandleMessage()        ← 前置消息处理
│   │
│   ├── ⑤ buildTrigger + buildHandler ← 构建流触发器和处理器
│   │
│   ├── ⑥ acquireDistributedLock()  ← Redis 分布式锁（5分钟 TTL）
│   │
│   ├── ⑦ startHeartbeat()          ← 60秒心跳续锁
│   │
│   └── ⑧ consumeStream()           ← Redis Stream 消费
│       └── 内部会调用 StreamWorkflowTerminalHookRunner
│
├── } catch (Exception e) {
│   │
│   ├── handleBeforeHookException()
│   │   ├── 更新聊天记录状态 → WorkflowFailed
│   │   ├── 更新 A2A 消息日志
│   │   └── 发送 WebSocket 错误消息
│   │
│   └── return false
│
└── } finally {
    │
    ├── stopHeartbeat()              ← 停止心跳
    ├── releaseLock()                ← 释放分布式锁
    └── runChatEndHookSafely()       ← AgentChatEndHook（try-catch 包裹）
        └── 保证即使 Hook 抛异常也不影响锁释放
```

**一次对话中 Hook 的完整执行示例**：

```Plain
用户发送消息："帮我审查一下 main 分支最近的代码变更"

① SessionArchivedCheckHook  → 检查会话未归档 ✓ 通过
② TeamArchivedCheckHook     → 检查团队未归档 ✓ 通过
③ AgentCollabInitHook       → 非协作模式，跳过
④ AgentChatInitHook         → 查到用户 zhangsan，加载 Agent 配置，生成 msgId=msg-001
⑤ AgentCollabMessageContentHook → 非协作模式，跳过
⑥ RegenerateHook            → 非重新生成，跳过
⑦ AIWorkflowGenerateInitHook → 等待容器就绪，确认工作区路径
⑧ QueryReWriteHook          → 检查无 @技能引用，原样通过
⑨ RecommendQuestionInitHook → 初始化推荐问题
⑩ AskUserQuestionHandleHook → 无待处理的用户提问
⑪ FileEnvCheckHook          → 设置文件环境变量
⑫ KbAppendSystemPromptHook  → Agent 配了知识库，追加 System Prompt

→ 获取 Redis 锁
→ 开始 AI 对话执行
→ AI 返回代码审查结果
→ StreamWorkflowTerminalHookRunner 触发（status=WorkflowEnded）
→ 释放 Redis 锁
→ AgentChatEndHook 执行（检测协作状态）
```

## 七、面试建议

### 7.1 多渠道适配的讲述要点

**推荐回答结构**（STAR 法则 + 技术深度）：

1. **背景**（30 秒）：平台需要对接多种 IM 渠道，每种渠道协议不同，如果硬编码会导致维护困难。

2. **方案**（1 分钟）：设计了统一的 ChannelProvider 接口，核心方法包括路由解析、消息转换、前后置处理、消息发送。入站由 ChannelServiceImpl 统一编排，出站通过 Redis Stream 异步分发。

3. **亮点**（30 秒）：

 - **Bridge 机制**：支持任意第三方通过 WebSocket + JSON 接入，能力可动态声明

 - **能力过滤**：自动根据渠道声明的能力过滤不支持的内容类型

 - **防重复处理**：不同渠道用不同的去重策略（Redis setNx / SDK 内置 / messageId 异常拦截）

**高频问题**：

- Q：如果新增一个渠道，需要改多少代码？
- A：只需实现 ChannelProvider 接口（最少 2 个方法），在 Spring 注册为 Bean，系统自动发现。零改动核心代码。

### 7.2 ChatHook 设计模式的高频面试问题

**Q：这个设计模式叫什么？有什么优势？**

A：管道 + 过滤器模式（Pipeline & Filter）。优势是每个 Hook 职责单一、可插拔、可复用。不同引擎可以自由组合不同的 Hook 链。

**Q：Hook 之间怎么传递数据？**

A：通过共享的 ParamPassingDTO 对象。前序 Hook 写入的数据，后续 Hook 可以直接读取。类似于 Servlet 的 HttpServletRequest 中的 setAttribute/getAttribute。

**Q：某个 Hook 抛异常了怎么办？**

A：Before Hook 链中任何一个 Hook 抛异常，整个对话流程中止，返回错误消息给用户。After Hook 中每个 Hook 独立 try-catch，一个失败不影响其他。AgentChatEndHook 在 finally 块中执行，保证一定会跑到。

**Q：为什么不用 Spring 的 AOP 或拦截器来实现？**

A：因为 Hook 的执行顺序、组合方式需要根据不同的引擎类型（SharedCode / Gemini / OpenClaw）动态调整。纯 AOP 做不到这种灵活的编排。

### 7.3 Skill 追踪系统的创新点

**面试中值得强调的亮点**：

1. **两阶段分离设计**：实时关联 + 异步物化，兼顾了用户体验（快速上报）和分析精度（LLM 评估）

2. **LLM 归因评估**：不是简单地统计"技能被调用了几次"，而是用 gpt-4.1 分析每个执行步骤到底属于哪个技能，给出 PRIMARY/SECONDARY/CONTEXT 三级归因

3. **工程窗口算法**：巧妙地通过 skill slug 匹配 + 时间锚点定位 + 状态变更事件截断，精确圈定每个 Skill 的影响范围

4. **多层容错**：LLM 未配置 → fallback；LLM 调用失败 → fallback；LLM 输出格式错 → fallback；单条失败 → 不影响批次

5. **幂等设计**：确定性 traceId `SKILLTRACE:{session}|{skill}|{msgId}`) + upsert，重复执行不会产生脏数据

**Q：为什么用 gpt-4.1 做评估而不是规则引擎？**

A：因为一个 session 中可能同时运行多个 Skill，它们的 Trace 交织在一起。简单的规则（如时间范围匹配）无法准确区分哪些 MODEL/TOOL 步骤属于哪个 Skill。LLM 可以理解上下文语义，根据 toolName、toolInput、phase、requestId 等多维信息做精准归因。
