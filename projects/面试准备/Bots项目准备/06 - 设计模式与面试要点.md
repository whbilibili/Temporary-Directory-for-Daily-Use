## 一、设计模式应用总览

平台后端是一个典型的"多引擎 + 多渠道 + 多协作"系统，涉及 7 种 AI 引擎、4 种 IM 渠道、多 Agent 协作任务调度等复杂场景。为了让代码可维护、可扩展，系统大量运用了经典设计模式和分布式系统模式。下面对 10 种核心模式逐一拆解。

### 1.1 策略模式 + 注册表

#### 应用场景

- **Bot 生命周期管理**：6 种 Bot 引擎（Claude Bot、OpenClaw Bot、Gemini Bot、Codex Bot、Cursor Bot、Claude Bot Business）各有不同的容器创建、销毁、保活逻辑

- **渠道适配**：4 种 IM 渠道（大象、飞书、钉钉、Bridge）各有不同的消息格式、路由解析、会话管理

- **对话路由**：不同引擎的对话请求需要路由到对应的执行服务

#### 解决的问题

每接入一个新引擎或新渠道，不希望修改已有代码。理想状态是：写一个新的实现类，加个注解，系统自动识别并注册，运行时按类型动态分发。这就是策略模式 + 注册表的核心价值——**开闭原则**：对扩展开放，对修改关闭。

#### 具体实现说明

利用 Spring 的依赖注入机制，在注册表类中注入 `List<接口>`（Spring 会自动收集所有实现类），然后在 `@PostConstruct` 方法中遍历构建 `Map<类型Key, 实现类>`，运行时根据请求中的类型字段从 Map 中取出对应策略执行。

#### 伪代码展示

```Java
// ========== 策略接口 ==========
public interface BotProvider {
    String capacityType();  // 返回引擎类型标识，作为注册表的 Key
    void createAndInitContainer(String agentId);
    void destroyContainer(String agentId);
    void keepalive(String agentId);
    // default 方法提供可选行为，子类按需覆写
    default boolean enforceSingleRunning() { return false; }
}

// ========== 注册表 ==========
@Component
public class BotProviderRegistry {
    @Autowired(required = false)
    private List<BotProvider> providers;  // Spring 自动注入所有实现

    private Map<String, BotProvider> providerMap;

    @PostConstruct
    public void init() {
        Map<String, BotProvider> map = new HashMap<>();
        for (BotProvider p : providers) {
            map.put(p.capacityType(), p);  // 以类型为 Key 注册
        }
        this.providerMap = Collections.unmodifiableMap(map);
    }

    public BotProvider getProvider(String capacityType) {
        return providerMap.get(capacityType);
    }
}

// ========== 具体策略（6 个实现类）==========
@Service
public class ClaudeBotProvider implements BotProvider {
    @Override
    public String capacityType() { return "claudeBot"; }

    @Override
    public void createAndInitContainer(String agentId) {
        // Claude 特有的容器创建逻辑
    }
    // ... 其他方法
}

// 调用方
botProviderRegistry.getProvider("claudeBot").createAndInitContainer(agentId);
```

> **实际文件**`BotProviderRegistry.javaBotProvider.javaservice/bot/impl/` 下 6 个实现类

> 渠道适配同理：`ChannelServiceImpl` 在构造函数中注入 `List<ChannelProvider>`，`@PostConstruct` 构建 `providerMap`

#### 面试怎么讲

"我们平台有 7 种 AI 引擎，每种引擎的容器创建、销毁、保活逻辑完全不同。如果用 if-else 分支，代码会变成几百行的条件判断，而且每加一个引擎就要改这个方法。我用了策略模式 + Spring 自动注册：定义一个 `BotProvider` 接口，每个引擎实现一个 Provider 类，注册表在启动时自动收集所有实现类并构建 Map。运行时根据引擎类型从 Map 中取策略执行。**新增引擎只需要写一个类加个注解，零修改已有代码**——这就是开闭原则的落地。"

### 1.2 模板方法模式

#### 应用场景

统一对话执行骨架。7 种引擎的对话流程有 80% 相同（加锁、心跳、消费 Stream、释放锁），只有 20% 不同（构建请求参数、调用 API、解析消息）。

#### 解决的问题

如果每个引擎独立实现完整对话流程，7 套代码会有大量重复的锁管理、心跳续期、异常处理逻辑。一旦锁逻辑需要调整，就要改 7 个地方。模板方法模式把不变的部分固化在父类，把变化的部分延迟到子类实现。

#### 具体实现说明

抽象类 `AbstractChatExecutionService` 定义了一个 7 步执行骨架（模板方法），其中：

- 固定步骤（加锁、心跳、消费 Stream、释放锁）直接在父类实现
- 差异化步骤（构建请求、调用 API、解析消息）声明为抽象方法，由子类实现
- 可选步骤（预处理、消息前置处理）提供默认空实现，子类按需覆写

#### 伪代码展示

```Java
// ========== 模板方法（父类）==========
public abstract class AbstractChatExecutionService {

    // 模板方法：定义固定执行骨架，子类不能修改
    public final void execute(ChatRequest req) {
        // Step 1: 前置 Hook（固定）
        beforeHook(req);

        // Step 2: 子类定制化准备（抽象方法，子类必须实现）
        if (!doPrepare(req)) return;

        // Step 3: 配额检查（固定）
        checkQuota(req);

        // Step 4: 构建触发器和处理器（抽象方法）
        StreamMessageTrigger trigger = buildTrigger(req);
        AbstractStreamMessageHandlerService handler = getStreamMessageHandlerService();

        // Step 5: 获取分布式锁（固定）
        String lockKey = getStreamConsumeLock(req);
        acquireLock(lockKey);

        // Step 6: 启动心跳 + 消费 Stream（固定）
        startHeartbeat(lockKey);
        consumeStream(trigger, handler);

        // Step 7: 释放锁 + 执行后置 Hook（固定）
        releaseLock(lockKey);
        runChatEndHookSafely(req);
    }

    // ===== 抽象方法：子类必须实现 =====
    protected abstract String getStreamConsumeLock(ChatRequest req);
    protected abstract Object buildAgentRequest(ChatRequest req);
    protected abstract Response executeApiCall(String url, Object request);

    // ===== 钩子方法：子类可选覆写 =====
    protected boolean doPrepare(ChatRequest req) { return true; }
    protected void preHandleMessage(Object msg) { /* 默认空实现 */ }
}

// ========== 具体子类（7 个）==========
@Service
public class UnifiedOpenClawAgentServiceImpl extends AbstractChatExecutionService {
    @Override
    protected String getStreamConsumeLock(ChatRequest req) {
        return "openclaw:stream:lock:" + req.getSessionId();
    }

    @Override
    protected Object buildAgentRequest(ChatRequest req) {
        // OpenClaw 特有的请求参数构建
        return OpenClawRequest.builder()
            .prompt(req.getMessage())
            .model(req.getModel())
            .build();
    }
    // ...
}
```

> **实际文件**`AbstractChatExecutionService.java`（7 步骨架）+ 7 个子类在 `service/chat/unified/` 目录

> 另有 `AbstractStreamMessageHandlerService` 也是模板方法：定义消息处理骨架（前置处理 -> 解析 -> 分发 -> 后置处理），5 个子类实现差异化解析和分发逻辑

#### 面试怎么讲

"7 种引擎的对话流程有 80% 是相同的——都需要加分布式锁、启心跳、消费 Redis Stream、释放锁。如果每个引擎各写一套，锁逻辑改一次就要同步改 7 处。我用模板方法模式把公共骨架抽到 `AbstractChatExecutionService` 中，定义了 7 步执行流程。子类只需要实现几个抽象方法：构建请求参数、调用 API、解析消息。可选的钩子方法默认空实现，子类需要时才覆写。**这样公共逻辑只维护一份，子类平均只有 100 行左右的差异化代码**，新增引擎只需要继承父类填空。"

### 1.3 管道 + 过滤器模式

#### 应用场景

ChatHook 前后置处理链。一次对话从开始到结束，需要经过 20+ 个处理逻辑：查询重写、知识库注入、文件环境检查、会话归档检查、协作初始化、Gemini 上下文配置等。

#### 解决的问题

如果把这些处理逻辑全部写在一个方法里，会变成一个上千行的巨型方法，修改任何一个逻辑都可能影响其他逻辑。管道模式让每个处理逻辑成为独立的 Hook，互不影响，可插拔。

#### 具体实现说明

定义一个泛型 `Hook<T>` 接口，每个 Hook 接收一个共享上下文对象 `T`（通常是 `ParamPassingDTO`），对其进行修改或检查。管道运行器（Runner）在 `@PostConstruct` 时收集所有 Hook 实现，按顺序执行，每个 Hook 用 try-catch 隔离——一个 Hook 失败不会中断整个管道。

#### 伪代码展示

```Java
// ========== 过滤器接口 ==========
public interface Hook<T> {
    void execute(T context) throws IOException;
}

// ========== 管道运行器 ==========
@Component
public class StreamWorkflowTerminalHookRunner {
    @Resource
    private List<StreamWorkflowTerminalHook> hooks;  // Spring 自动收集

    public void run(ParamPassingDTO dto, ChatRecordStatusEnum status) {
        for (StreamWorkflowTerminalHook hook : hooks) {
            try {
                hook.afterChatWorkflowTerminal(dto, status);
            } catch (Exception e) {
                // 单个 Hook 失败不影响其他 Hook
                log.error("Hook {} failed", hook.getClass().getName(), e);
            }
        }
    }
}

// ========== 具体过滤器（20+ 个）==========
@Component
public class QueryReWriteHook implements Hook<ParamPassingDTO> {
    @Override
    public void execute(ParamPassingDTO dto) {
        // 查询重写：将用户原始问题改写为更利于检索的形式
        dto.setRewrittenQuery(rewriteQuery(dto.getOriginalQuery()));
    }
}

@Component
public class KbAppendSystemPromptHook implements Hook<ParamPassingDTO> {
    @Override
    public void execute(ParamPassingDTO dto) {
        // 知识库注入：将相关知识追加到系统提示词
        dto.setSystemPrompt(dto.getSystemPrompt() + fetchKbContext(dto));
    }
}

@Component
public class FileEnvCheckHook implements Hook<ParamPassingDTO> {
    @Override
    public void execute(ParamPassingDTO dto) {
        // 文件环境检查：确认容器内文件环境就绪
        if (!checkFileEnv(dto.getSessionId())) {
            throw new RuntimeException("File env not ready");
        }
    }
}

// 调用方
hookRunner.run(dto, ChatRecordStatusEnum.WorkflowEnded);
```

> **实际文件**`Hook.java`（接口）`StreamWorkflowTerminalHookRunner.java`（管道运行器）`service/chatHook/` 目录下 15+ 个 Hook 实现类

#### 面试怎么讲

"一次对话要经过 20 多个处理步骤：查询重写、知识库注入、文件检查、会话状态校验等。如果全写在一个方法里，会变成上千行的面条代码。我用了管道+过滤器模式：每个处理逻辑封装为独立的 Hook，实现统一的 `Hook<T>` 接口，通过 Spring 自动收集后顺序执行。关键是**每个 Hook 用 try-catch 隔离**，一个 Hook 出异常不会影响其他 Hook，也不会中断主流程。这就像工厂流水线——每个工位只做自己的事，一个工位出问题不会让整条线停摆。"

### 1.4 装饰器模式

#### 应用场景

Bridge 消息聚合。当对话通过 Bridge 渠道（桥接外部 IM 系统）进行时，AI 的流式回复是碎片化的——一段完整回复被拆成几十个小片段陆续到达。但 Bridge 渠道需要把完整回复聚合成一条消息再转发给 IM 系统。

#### 解决的问题

不修改原有消息发送逻辑的前提下，透明地为 Bridge 会话增加"消息聚合"能力。非 Bridge 会话不受影响，直接透传。

#### 伪代码展示

```Java
// ========== 被装饰的原始服务 ==========
@Service("frameSessionServiceImpl")
public class FrameSessionServiceImpl implements FrameSessionService {
    @Override
    public boolean sendText(String sessionId, WebSocketData data) {
        // 原始发送逻辑：直接通过 WebSocket 推送
        return webSocketSession.sendMessage(data.toJson());
    }
}

// ========== 装饰器 ==========
@Service
@Primary  // 关键：优先注入装饰器而非原始实现
public class BridgeAwareFrameSessionService implements FrameSessionService {

    @Resource
    @Qualifier("frameSessionServiceImpl")
    private FrameSessionService delegate;  // 被装饰的对象

    // 按会话维度的消息累积缓冲区
    private final ConcurrentHashMap<String, StringBuilder> bridgeBuffer = new ConcurrentHashMap<>();

    @Override
    public boolean sendText(String sessionId, WebSocketData data) {
        // 非 Bridge 会话：直接透传，不做任何修改
        if (!sessionId.startsWith("bridge-")) {
            return delegate.sendText(sessionId, data);
        }

        // Bridge 会话：拦截并累积
        String type = data.getType();
        if ("Llm".equals(type)) {
            // 流式片段：累积到缓冲区
            bridgeBuffer.computeIfAbsent(sessionId, k -> new StringBuilder())
                        .append(data.getContent());
            return true;
        }
        if ("End".equals(type)) {
            // 结束信号：刷出聚合后的完整消息
            String fullContent = bridgeBuffer.getOrDefault(sessionId, new StringBuilder()).toString();
            WebSocketData aggregated = new WebSocketData();
            aggregated.setType("BridgeAssistantReply");
            aggregated.setContent(fullContent);
            bridgeBuffer.remove(sessionId);
            return delegate.sendText(sessionId, aggregated);
        }
        return delegate.sendText(sessionId, data);
    }
}
```

> **实际文件**`BridgeAwareFrameSessionService.java`（装饰器）`FrameSessionServiceImpl`（被装饰对象）

#### 面试怎么讲

"Bridge 渠道需要把 AI 的流式碎片聚合为完整消息再转发。我不希望改原有发送逻辑，因为这会影响所有其他渠道。用了装饰器模式：`BridgeAwareFrameSessionService` 实现了和原始服务相同的接口，通过 `@Primary` 注解让 Spring 优先注入它。内部判断如果是 Bridge 会话（sessionId 以 `bridge-` 开头），就拦截 LLM 类型消息做累积，收到 End 信号时刷出完整消息。非 Bridge 会话直接委托给原始服务透传。**对调用方完全透明——调用方不知道自己用的是装饰器还是原始服务**。"

### 1.5 工厂方法模式

#### 应用场景

- **Git 平台服务**：不同 Git 平台（美团 DevTools、GitHub）的仓库操作接口统一

- **协作消息构建**：不同类型的协作消息（任务分配、完成通知、A2A 传递）有不同的协议结构

#### 伪代码展示

```Java
// ========== Git 平台工厂 ==========
@Component
public class GitPlatformServiceFactory {

    @Autowired
    private DevtoolsGitService devtoolsGitService;
    @Autowired
    private GitHubGitService gitHubGitService;

    public IGitPlatformService getService(String gitType) {
        if (StringUtils.isBlank(gitType)) return devtoolsGitService;  // 默认
        GitTypeEnum type = GitTypeEnum.getByCode(gitType);
        return switch (type) {
            case GITHUB -> gitHubGitService;
            default -> devtoolsGitService;
        };
    }
}

// ========== 协作消息工厂（静态工厂）==========
public final class CollabDeliverMessageFactory {
    private CollabDeliverMessageFactory() {}  // 不可实例化

    // 任务分配消息
    public static CollabDeliverMessage forTaskAssign(Todo todo, Map<String, Object> extra) {
        return CollabDeliverMessage.builder()
            .version("1.0")
            .channel("collab")

            .payload(buildAssignPayload(todo))
            .context(extra)
```

#### 面试怎么讲

> "Git 平台适配用了工厂方法：根据 `gitType` 字段返回对应的实现，调用方不需要知道具体是 DevTools 还是 GitHub。协作消息构建用了静态工厂：不同类型消息（任务分配、完成通知、A2A 传递）的协议结构不同，工厂方法封装了构建细节，调用方只需传入业务参数。静态工厂还有一个巧妙的用法——`fromMessageLog` 方法从历史日志重建消息对象，用于消息重试场景。"

### 1.6 CAS 乐观锁

#### 应用场景

多 Agent 协作中的并发状态转换：Todo 状态流转（待完成 -> 已完成）、Task 状态流转（执行中 -> 已完成）、Outbox 行锁定（待投递 -> 投递中）。

#### 为什么用 CAS 而不是分布式锁


|     |                   |         |
| --- | ----------------- | ------- |
| 维度  | 分布式锁（Redis SETNX） | CAS 乐观锁 |


| **性能** | 每次操作都要获取/释放锁，有网络开销 | 一条 SQL 搞定，无额外网络调用 |

| **竞争程度** | 适合高竞争场景 | 适合低竞争场景（协作任务冲突概率低） |

| **实现复杂度** | 需要处理锁续期、锁超时、死锁 | 一条 UPDATE WHERE 语句 |

| **失败处理** | 获取锁失败需要重试/等待 | 更新 0 行表示已被其他线程处理，直接跳过 |

协作场景中，两个 Agent 同时完成同一个 Todo 的概率很低，用 CAS 更轻量。

#### SQL 示例

```SQL
-- Todo 状态 CAS：只有当前状态 = 期望状态时才更新
UPDATE agent_collab_todo
SET status = #{newStatus}, updated_at = NOW()
WHERE id = #{id}
  AND status = #{expectedStatus};

-- 返回影响行数：1 = 成功，0 = 状态已被其他线程修改（CAS 失败）

-- Task 状态 CAS：同理
UPDATE agent_collab_task
SET status = #{newStatus}, updated_at = NOW()
WHERE task_no = #{taskNo}
  AND status = #{expectedStatus};

-- Outbox 行锁定 CAS：抢锁投递
UPDATE agent_collab_dispatch_queue
SET status = 1,                    -- 0=待投递 -> 1=投递中
    locked_until = #{lockedUntil},
    last_attempt_at = NOW()
WHERE id = #{id}
  AND status = 0;                  -- 只有待投递状态才能抢锁
```

```Java
// Java 调用示例
int updated = todoMapper.casUpdateStatus(
    todo.getId(),
    CollabTodoStatusEnum.PENDING.getCode(),   // 期望状态
    CollabTodoStatusEnum.ASSIGNED.getCode(),  // 目标状态
    new Date(), null);

if (updated == 0) {
    // CAS 失败：说明这个 Todo 已经被其他线程处理了，直接跳过
    log.warn("[TaskDispatcher] CAS failed for todoId={}, skipped", todo.getTodoId());
    return;
}
// CAS 成功：继续后续逻辑
```

> **实际文件**`AgentCollabTodoMapper.xml`（casUpdateStatus）`AgentCollabTaskMapper.xml`（casUpdateTaskStatus）`TaskDispatcherImpl.java`（调用方）

#### 面试怎么讲

"多 Agent 协作中，Todo 和 Task 的状态转换是并发的。比如两个 Agent 可能同时尝试完成同一个 Todo。我用 CAS 乐观锁而不是分布式锁，因为协作场景竞争概率低，CAS 更轻量——一条 `UPDATE ... WHERE status = 期望值` 就搞定。如果返回 0 行，说明状态已被其他线程改了，直接跳过。这比分布式锁少了获取锁、续期、释放锁的网络开销。**关键设计是 fail-fast**：CAS 失败不重试，而是跳过，因为说明已经有其他线程在处理了。"

### 1.7 Outbox 模式

#### 应用场景

A2A（Agent-to-Agent）消息投递。入口 Agent 通过 `collab-a2a-send` Skill 给子 Agent 下发任务时，需要保证消息至少投递一次——即使目标 Agent 正在忙、即使系统 crash 了，消息也不能丢。

#### 解决的问题

分布式系统中的"至少一次投递"问题。如果直接调用目标 Agent 的执行接口，可能遇到：目标 Agent 正在处理其他任务（busy）、网络超时、系统 crash。Outbox 模式通过"先落库再投递 + 定时补偿重试"保证消息不丢。

#### 具体实现

1. **INSERT IGNORE 幂等写入**：消息先写入 `agent_collab_dispatch_queue` 表（Outbox 表），利用唯一索引 `(task_no, todo_db_id)` + `INSERT IGNORE` 保证幂等——重复写入不会产生重复记录

2. **尝试直投**：写入后立即尝试投递。如果目标 Agent 空闲，直接投递成功，删除 Outbox 记录

3. **入队等待**：如果目标 Agent 忙，消息留在 Outbox 表中等待

4. **定时补偿**`CollabScheduledProcessor` 每 120 秒扫描 Outbox 表，重试卡住的记录

5. **空闲触发重放**：当 Agent 完成当前任务变为空闲时，主动重放该 Agent 的待投递消息

### 1.8 事件驱动

#### 应用场景

协作状态收敛。多 Agent 协作中，Task 的状态不是由某个中心控制器主动轮询的，而是由各种事件触发的——Todo 完成、Agent 失败、Agent 空闲、任务超时。每个事件触发相应的状态检查和推进动作。

#### 事件类型和响应动作


|                     |                  |                                                        |
| ------------------- | ---------------- | ------------------------------------------------------ |
| 事件                  | 触发条件             | 响应动作                                                   |
| `onTodosCreated`    | Agent 创建新 Todo   | 检查依赖是否满足，满足则调度分发                                       |
| `onTodoCompleted`   | Agent 完成一个 Todo  | 级联检查依赖此 Todo 的其他 Todo 是否可执行；检查所有 Todo 是否都已完成，是则关闭 Task |
| `onTaskTimeout`     | 定时任务检测到超时        | CAS 将 Task 从执行中转为超时失败；将相关 Todo 标记为阻塞                   |
| `onAgentFailed`     | Agent 执行失败       | 将该 Agent 的待执行 Todo 标记为阻塞；检查 Task 是否可以关闭                |
| `onAgentBecomeIdle` | Agent 完成当前任务变为空闲 | 重放该 Agent 的待投递 Outbox 消息；重试失败的 A2A 消息                  |


#### 伪代码展示

```Java
// ========== 事件处理器接口 ==========
public interface CollabEventHandler {
    void onTodosCreated(String taskNo, List<Todo> todos);
    void onTodoCompleted(String taskNo, String todoId);
    void onTaskTimeout(String taskNo);
    void onAgentFailed(String taskNo, String agentId, String error);
    void onAgentBecomeIdle(String taskNo, String agentId, String sessionId);
}

// ========== 事件处理器实现 ==========
@Service
public class CollabEventHandlerImpl implements CollabEventHandler {

    @Override
    public void onTodoCompleted(String taskNo, String todoId) {
        // 1. 级联调度：检查依赖此 Todo 的其他 Todo 是否可以执行
        taskDispatcher.cascadeDispatch(taskNo, todoId);

        // 2. 状态收敛：检查所有 Todo 是否都已完成
        if (allTodosTerminal(taskNo)) {
            // CAS 将 Task 从"执行中"转为"已完成"
            int updated = taskMapper.casUpdateTaskStatus(
                taskNo, TaskStatusEnum.RUNNING, TaskStatusEnum.COMPLETED);
            if (updated > 0) {
                // Task 完成后的后续动作
                notifyTaskComplete(taskNo);
            }
        }
    }

    @Override
    public void onAgentBecomeIdle(String taskNo, String agentId, String sessionId) {
        // 重放该 Agent 的待投递 Outbox 消息
        List<DispatchQueue> pending = dispatchQueueMapper
            .selectPendingByTargetSession(taskNo, sessionId, now);
        pending.forEach(q -> taskDispatcher.retryOutboxDelivery(q));

        // 重试失败的 A2A 消息
        retryFailedA2aMessages(taskNo, sessionId);
    }
}

// ========== 事件触发点 ==========
// AgentChatEndHook 在对话结束时触发事件
public class AgentChatEndHook implements Hook<ParamPassingDTO> {
    @Override
    public void execute(ParamPassingDTO dto) {
        if (dto.getStatus() == WorkflowFailed) {
            eventHandler.onAgentFailed(dto.getTaskNo(), dto.getAgentId(), "Workflow failed");
        } else if (dto.getStatus() == Idle) {
            eventHandler.onAgentBecomeIdle(dto.getTaskNo(), dto.getAgentId(), dto.getSessionId());
        }
    }
}
```

> **实际文件**`CollabEventHandler.java`（接口）`CollabEventHandlerImpl.java`（实现）`AgentChatEndHook.java`（触发点）`CollabEventLog.java`（事件日志）

系统还使用了 Spring 原生事件机制：`OpenClawStatusChangeEvent` + `@EventListener`，当 Bot 从 STARTING 变为 RUNNING 时自动安装默认技能和导入模板快照。

#### 面试怎么讲

"多 Agent 协作的状态推进是事件驱动的。Task 不由某个控制器主动轮询，而是由 5 种事件触发状态收敛：Todo 完成、Agent 失败、Agent 空闲、任务超时、Todo 创建。比如 `onTodoCompleted` 事件会做两件事：一是级联检查依赖此 Todo 的其他 Todo 是否可以执行，二是检查所有 Todo 是否都已完成来决定是否关闭 Task。事件触发点在 `AgentChatEndHook` 中——对话结束时自动触发。**好处是解耦**：事件发出方不关心后续动作，事件处理器自动推进状态，整个协作流程像多米诺骨牌一样自动运转。"

### 1.9 依赖 DAG

#### 应用场景

Todo 任务调度。协作任务中的 Todo 之间存在依赖关系——Todo B 必须等 Todo A 完成后才能执行。多个 Todo 之间的依赖关系构成一个有向无环图（DAG）。

#### blocks/blockedBy JSON 数组实现

每个 Todo 的 `blocked_by` 字段存储一个 JSON 数组，列出它依赖的所有 Todo ID。只有当所有依赖 Todo 都处于"已完成"或"已取消"状态时，这个 Todo 才能被调度执行。

#### 伪代码展示

```Plain
假设一个协作任务有 4 个 Todo：

  Todo A (无依赖)     Todo B (无依赖)
       │                   │
       ▼                   ▼
  Todo C (依赖 A)     Todo D (依赖 A, B)

数据库中的 blocked_by 字段：
  Todo A: blocked_by = "[]"           → 无依赖，立即可执行
  Todo B: blocked_by = "[]"           → 无依赖，立即可执行
  Todo C: blocked_by = "[\"todoA\"]"  → 依赖 Todo A
  Todo D: blocked_by = "[\"todoA\", \"todoB\"]" → 依赖 Todo A 和 B
```

```Java
// ========== 依赖验证器 ==========
public class TodoDependencyValidator {

    // 检查所有依赖是否已满足
    public boolean allDependenciesMet(String taskNo, List<String> blockedByIds) {
        if (blockedByIds == null || blockedByIds.isEmpty()) return true;

        // 查询所有依赖的 Todo
        List<Todo> deps = todoMapper.selectByExample(...blockedByIds...);

        // Fail-closed：数量不匹配说明有无效引用，返回 false
        if (deps.size() != blockedByIds.size()) return false;

        // 所有依赖必须处于"已完成"或"已取消"状态
        return deps.stream().allMatch(d ->
            d.getStatus() == COMPLETED.getCode()
            || d.getStatus() == CANCELLED.getCode()
        );
    }

    // 解析 blockedBy JSON 数组（容错处理）
    public List<String> parseBlockedBy(String blockedByJson) {
        if (StringUtils.isBlank(blockedByJson)) return Collections.emptyList();
        try {
            return objectMapper.readValue(blockedByJson, new TypeReference<>(){});
        } catch (Exception e) {
            // JSON 解析失败：fail-closed，返回空列表意味着"无依赖"
            // 但调用方会检查原始字符串是否非空来决定是否跳过
            return null;
        }
    }
}

// ========== DAG 调度 ==========
public class TaskDispatcherImpl {

    // 检查 Todo 是否可以调度
    public void dispatchIfReady(String taskNo, Todo todo) {
        List<String> blockedBy = dependencyValidator.parseBlockedBy(todo.getBlockedBy());
        if (!dependencyValidator.allDependenciesMet(taskNo, blockedBy)) {
            return;  // 依赖未满足，跳过
        }
        // 依赖已满足 → CAS 转换状态并分发
        int updated = todoMapper.casUpdateStatus(todo.getId(), PENDING, ASSIGNED, ...);
        if (updated > 0) {
            doDispatch(taskNo, todo, sessionId);
        }
    }

    // 级联触发：Todo 完成后检查依赖它的其他 Todo
    public void cascadeDispatch(String taskNo, String completedTodoId) {
        List<Todo> pendingTodos = todoMapper.selectByExampleWithBLOBs(...PENDING...);
        for (Todo t : pendingTodos) {
            List<String> deps = dependencyValidator.parseBlockedBy(t.getBlockedBy());
            if (deps != null && deps.contains(completedTodoId)) {
                dispatchIfReady(taskNo, t);  // 会重新检查所有依赖
            }
        }
    }
}
```

> **实际文件**`TodoDependencyValidator.javaTaskDispatcherImpl.java`（dispatchIfReady, cascadeDispatch）

**设计特点**：这里没有预计算拓扑排序，而是用**惰性求值**——每次有 Todo 完成时，只检查直接依赖它的待执行 Todo。这比预计算拓扑排序更灵活，能处理动态添加 Todo 的场景，且天然防止环依赖（自引用的 Todo 永远无法满足 `allDependenciesMet`）。

#### 面试怎么讲

> "协作任务中的 Todo 之间存在依赖关系，构成一个 DAG。每个 Todo 的 `blocked_by` 字段存一个 JSON 数组，列出它依赖的 Todo ID。调度采用惰性求值而非预计算拓扑排序：每次有 Todo 完成时，通过 `cascadeDispatch` 检查所有直接依赖它的待执行 Todo，调用 `allDependenciesMet` 重新检查全部依赖是否满足。这种设计的好处是支持动态添加 Todo，且天然防止环依赖——一个自引用的 Todo 永远无法通过依赖检查。这是任务编排的核心机制。"

### 1.10 快照模式

#### 应用场景

协作执行记录。多 Agent 协作过程中，需要记录"谁参与了哪个任务、用了哪个 Session、什么时候开始/结束"——这些记录是不可变的历史快照，用于审计、回溯和故障恢复。

#### 不可变历史记录


|      |     |     |
| ---- | --- | --- |
| 快照类型 | 表   | 作用  |


| **成员执行记录** | `agent_collab_record` | 记录每个 Agent 参与了哪个 Task、绑定了哪个 Session、是否入口 Agent |

| **A2A 消息日志** | `agent_a2a_message_log` | 记录每条 Agent 间消息的完整 payload、状态、重试次数、时间戳 |

| **事件日志** | `CollabEventLog`（内存日志） | 追加式记录每个协作事件的触发、状态转换、动作执行 |

#### 伪代码展示

```Java
// ========== 成员记录快照 ==========
// agent_collab_record 表是不可变的执行快照
// upsertMemberSessionRecord 只 patch 变化的字段，并记录旧值
public void upsertMemberSessionRecord(String taskNo, String agentId, String sessionId) {
    AgentCollabRecord existing = recordMapper.selectByTaskAndAgent(taskNo, agentId);
    if (existing != null) {
        // 记录旧值用于审计
        log.info("[collab-record] update id={}, taskNo={}, agentId={}, sessionId={} (was {})",
                existing.getId(), taskNo, agentId, sessionId, existing.getSessionId());
        // 只更新变化的字段，不覆盖历史
        existing.setSessionId(sessionId);
        recordMapper.updateByPrimaryKeySelective(existing);
    } else {
        // 新增快照记录
        AgentCollabRecord record = new AgentCollabRecord();
        record.setTaskId(taskNo);
        record.setAgentId(agentId);
        record.setSessionId(sessionId);
        recordMapper.insert(record);
    }
}

// ========== A2A 消息日志快照 ==========

        .payload(stored.getJSONObject("payload"))
        .context(stored.getJSONObject("collabContext"))
        .build();
    // 从不可变的历史快照中恢复出可投递的消息对象
}

// ========== 事件日志（追加式）==========
// CollabEventLog 是 append-only 的事件追踪日志

[CollabEvent] taskNo=XXX event=onTodoCompleted phase=action action=cascadeDispatch todoId=YYY
```

"协作过程中的执行记录用快照模式——每次事件产生不可变的历史记录。比如 `agent_collab_record` 表记录谁参与了哪个任务、绑定了哪个 Session；`agent_a2a_message_log` 记录每条 Agent 间消息的完整 payload 和状态流转。这些快照有两个用途：一是审计回溯，二是故障恢复——`CollabDeliverMessageFactory.fromMessageLog()` 可以从历史快照重建消息对象用于重试。另外还有一个 append-only 的事件日志 `CollabEventLog`，记录每个事件的触发、状态转换和动作执行，方便按 Task ID grep 排查问题。**这就像 Git commit——每次提交是不可变快照，你可以回到任何一个历史点**。"

## 二、面试高频问题详解

### Q1: 你们平台怎么把不同的 AI 引擎统一封装的？

#### 3 分钟版本

> "我们平台支持 7 种 AI 引擎：Claude、Gemini、OpenClaw、Codex、Cursor 等。核心是三层抽象：
>
>

第一层是**策略模式 + 注册表**。定义 `BotProvider` 接口，每个引擎实现一个 Provider 类，注册表在 Spring 启动时自动收集所有实现并构建 Map。运行时根据引擎类型从 Map 取策略，零 if-else。

>

第二层是**模板方法**。7 种引擎的对话流程有 80% 相同（加锁、心跳、消费 Stream、释放锁），只有 20% 不同（构建请求、调用 API）。抽象类 `AbstractChatExecutionService` 定义 7 步骨架，子类只实现差异化的抽象方法。

>

第三层是**管道 + 过滤器**。对话前后有 20 多个处理逻辑（查询重写、知识库注入、文件检查等），每个封装为独立的 Hook，通过管道顺序执行，Hook 之间用 try-catch 隔离互不影响。

>
>
> 效果是：新增引擎只需要写一个 Provider 类 + 一个 ChatExecutionService 子类，平均 100-200 行代码，2 天内完成接入。"

#### 10 分钟版本

在 3 分钟版本基础上，展开以下细节：

> "我详细讲一下每一层的设计决策。
>
>

> **策略模式的关键是注册方式**。我们没有用配置文件或手动注册，而是利用 Spring 的 `List<Interface>` 自动注入——所有实现了 `BotProvider` 接口的 Bean 会被 Spring 自动收集。注册表在 `@PostConstruct` 中遍历这个 List，以 `capacityType()` 返回值为 Key 构建 Map。这样新增引擎只需要加一个 `@Service` 注解的类，系统自动识别注册。

>

> **模板方法的关键是区分'不变'和'变化'**。不变的部分——分布式锁获取/释放、心跳续期、Stream 消费循环——放在父类实现。变化的部分——构建请求参数、调用引擎 API、解析流式消息——声明为抽象方法由子类实现。还有一些可选步骤（预处理、消息前置处理），用默认空实现的钩子方法，子类需要时才覆写。这样 7 个子类的代码量平均只有 100 行左右。

>

> **管道模式的关键是隔离性**。每个 Hook 实现 `Hook<T>` 接口，接收一个共享上下文对象。管道运行器顺序执行所有 Hook，每个 Hook 用 try-catch 包裹——一个 Hook 出异常不会中断管道，只会记录错误日志。这保证了即使某个预处理逻辑（如知识库查询）出问题，主对话流程仍然可以继续。

>

另外还有一层**装饰器**用于 Bridge 消息聚合。Bridge 渠道的 AI 回复是流式碎片，需要聚合为完整消息再转发给 IM 系统。装饰器通过 `@Primary` 注解透明替换原始服务，非 Bridge 会话直接透传不受影响。

>

最后是**工厂方法**用于 Git 平台适配。根据 `gitType` 字段返回 DevTools 或 GitHub 实现，调用方不需要知道具体平台。"

#### 可能的追问及回答

**追问 1："如果两个引擎的对话流程差异很大，模板方法还适用吗？"**

> "如果差异到连骨架都不一样，那就不能用模板方法了。我们的做法是：70% 相同的放模板方法，如果某个引擎有完全不同的流程，就单独实现不走模板方法。比如 OpenClaw 的群聊模式有特殊的路由逻辑，就是独立实现的。模板方法适用于'骨架相同、细节不同'的场景，不是银弹。"

**追问 2："注册表用 Map 存储，如果运行时动态新增引擎怎么办？"**

> "目前是启动时注册，不支持运行时动态新增。但 Map 是 `Collections.unmodifiableMap` 包装的不可变 Map，如果需要动态新增，可以改为 `ConcurrentHashMap` 并暴露注册方法。实际上我们的引擎类型是枚举管理的，新增引擎需要发版，所以启动时注册就够了。"

**追问 3："Hook 管道有顺序要求吗？怎么控制？"**

> "有顺序要求。比如查询重写 Hook 必须在知识库注入 Hook 之前执行——先改写查询，再用改写后的查询检索知识库。目前通过 Spring `@Order` 注解或 `Ordered` 接口控制顺序。如果两个 Hook 没有依赖关系，顺序无所谓。"

### Q2: 多 Agent 协作的核心技术挑战是什么？怎么解决的？

#### 3 分钟版本

> "多 Agent 协作有三大挑战：
>
>

> **第一是并发状态安全**。多个 Agent 同时操作 Todo 和 Task，状态转换可能冲突。解决用 CAS 乐观锁—`UPDATE ... WHERE status = 期望值`，返回 0 行说明已被其他线程处理，直接跳过。比分布式锁轻量，因为协作场景竞争概率低。

>

> **第二是消息可靠投递**。Agent 给 Agent 发消息（A2A），目标 Agent 可能在忙、可能 crash 了。解决用 Outbox 模式——消息先 `INSERT IGNORE` 幂等写入 Outbox 表，再尝试直投。投递失败留表等待，有两条补偿路径：定时任务每 120 秒重试卡住的记录，Agent 变空闲时主动重放待投递消息。

>

> **第三是任务编排**。Todo 之间有依赖关系构成 DAG。解决用惰性求值——每个 Todo 存 `blocked_by` JSON 数组，Todo 完成时通过 `cascadeDispatch` 检查依赖它的待执行 Todo。不需要预计算拓扑排序，支持动态添加 Todo，天然防环。

>
>
> 整个协作流程是事件驱动的：Todo 完成、Agent 失败、Agent 空闲等事件触发状态收敛，像多米诺骨牌一样自动推进。"

#### 10 分钟版本

在 3 分钟版本基础上展开：

> "我展开讲一下每个挑战的具体实现。
>
>

> **并发状态安全**。协作中有三层状态：Todo（待完成/已完成/已取消/运行中/阻塞）、Task（待执行/执行中/已完成/失败）、Outbox（待投递/投递中）。所有状态转换都用 CAS。比如 Todo 从'待完成'到'已完成'，SQL 是 `UPDATE agent_collab_todo SET status=1 WHERE id=? AND status=0`。如果返回 0 行，说明这个 Todo 已经被其他 Agent 完成或取消了，当前操作直接跳过。关键设计是 **fail-fast 不重试**——CAS 失败说明已有其他线程在处理，重试反而可能导致重复操作。

>

> **消息可靠投递**。Outbox 表有唯一索引 `(task_no, todo_db_id)`，写入用 `INSERT IGNORE` 保证幂等。投递成功后删除 Outbox 记录。如果投递失败，记录留在表中。定时任务 `CollabScheduledProcessor` 每 120 秒扫描卡住超过 5 分钟的记录，用 SQL CAS 抢锁`UPDATE ... SET status=1 WHERE status=0`），重试投递。重试超过 20 次标记为永久失败，触发 `onAgentFailed` 事件。还有一条空闲触发路径——Agent 完成任务变空闲时，主动重放自己的待投递消息。

>

> **任务编排 DAG**。每个 Todo 的 `blocked_by` 字段存 JSON 数组。调度器 `dispatchIfReady` 检查所有依赖是否处于'已完成'或'已取消'状态。有一个 Todo 完成时`cascadeDispatch` 遍历所有待执行 Todo，检查是否依赖刚完成的 Todo，是的话重新检查全部依赖。这种惰性求值方式的好处是：不需要维护全局拓扑排序，支持运行时动态添加 Todo，且天然防止环依赖——自引用的 Todo 永远无法通过依赖检查。

>

> **事件驱动状态收敛**。5 种事件触发状态推进`onTodosCreated`（检查依赖调度分发）`onTodoCompleted`（级联调度+检查 Task 是否可关闭）`onTaskTimeout`（CAS 关闭 Task）`onAgentFailed`（标记相关 Todo 为阻塞）`onAgentBecomeIdle`（重放 Outbox+重试 A2A）。事件触发点在 `AgentChatEndHook`——对话结束时自动触发。所有事件都有结构化日志 `CollabEventLog`，按 Task No 可 grep 排查。

>

> **故障恢复**。如果系统 crash，恢复机制是：定时任务检测超时任务`detectTaskTimeouts`）、卡死的 Todo`detectStuckTodos`）、卡住的 Outbox 记录`detectStuckDispatches`）。Outbox 表中的记录不会因为 crash 丢失，重启后定时任务继续重试。"

#### 可能的追问

**追问："如果两个 Agent 同时完成各自的 Todo，怎么保证状态正确？"**

> "用 CAS 乐观锁。两个 Agent 同时完成两个不同的 Todo，各自的 CAS 操作针对不同的行，不会冲突。如果两个 Agent 同时尝试完成同一个 Todo（理论上不应该发生，但防御性设计），CAS 保证只有一个成功——`UPDATE ... WHERE status=0` 返回 1 行的那个成功，返回 0 行的那个直接跳过。然后成功的那个触发 `onTodoCompleted` 事件，做级联调度和 Task 关闭检查。Task 关闭也是 CAS——`UPDATE task SET status=2 WHERE status=1`，保证只有一个 Agent 能关闭 Task。"

**追问："如果 Agent 处理非常慢，消息一直投递不上怎么办？"**

> "Outbox + 重试 + 超时三重保障。第一，消息在 Outbox 表中不会丢，每 120 秒定时重试。第二，Agent 变空闲时主动重放待投递消息，不需要等定时任务。第三，如果 Task 整体超时（`team.time_out` 配置），定时任务 `detectTaskTimeouts` 会 CAS 将 Task 标记为超时失败，触发 `onTaskTimeout` 事件，将相关 Todo 标记为阻塞。最后，A2A 消息重试超过 20 次标记为 `RETRY_FAILED`，触发 `onAgentFailed`。不会无限重试。"

**追问："如果系统 crash 了，任务状态怎么恢复？"**

> "三个定时检测任务负责恢复。`detectTaskTimeouts`：检测超过 `team.time_out` 的任务，CAS 关闭。`detectStuckTodos`：检测长时间处于'运行中'状态的 Todo，可能是 Agent crash 了没上报完成，CAS 转为阻塞。`detectStuckDispatches`：检测 Outbox 表中卡住超过 5 分钟的记录，CAS 抢锁重试投递。所有恢复操作都基于数据库中的持久化状态，不依赖内存——所以 crash 后重启，定时任务会自动扫描并恢复。"

### Q3: 异步通信架构是怎么设计的？

#### 回答要点

> "异步通信基于 Redis Stream + WebSocket 双通道。
>
>
>
> 用户发消息时，后端通过 WebSocket 接收，调用引擎 API 后立即返回 `accepted` 和 `messageId`。引擎的流式回复通过 Redis Stream 推送，消费端监听 Stream 消费消息，再通过 WebSocket 推给前端。
>
>

消费端有**分布式锁**保证同一会话只有一个消费者——Redis `setIfAbsent` 获取锁，心跳线程定期续期。如果消费者 crash，锁超时自动释放，其他实例可以接管。

>

Redis Stream 有**消费者组**机制，未 ACK 的消息可以被重新消费。如果消费端 crash，消息不会丢——Stream 有持久化，重启后可以从上次未 ACK 的位置继续。

>
>
> 选择 Redis Stream 而不是 Kafka 的原因：一是已有 Redis 基础设施，无需额外运维 Kafka 集群；二是会话级隔离，每个会话有独立的 Stream Key，消息量不大但 Key 很多，Redis 比 Kafka 更适合这种场景；三是轻量级，Redis Stream 的延迟在毫秒级，满足实时对话需求。"

#### 可能的追问

**追问："为什么用 Redis Stream 而不是 Kafka？"**

> "三个原因。第一，轻量——我们已经有 Redis 基础设施（做分布式锁和缓存），不需要额外引入 Kafka 集群。第二，会话级隔离——每个会话有独立的 Stream Key（如 `chat:stream:{sessionId}`），Key 数量多但单个 Key 的消息量不大。Kafka 的 Topic 是重量级资源，不适合动态创建大量 Topic。第三，延迟——Redis Stream 毫秒级延迟，满足实时对话需求。Kafka 更适合高吞吐、少 Topic 的场景。"

**追问："分布式锁怎么实现的？"**

> "Redis `setIfAbsent`（即 SETNX）+ TTL。获取锁时 `SET lockKey token NX EX 30`，返回 true 表示获取成功。锁的 TTL 是 30 秒，心跳线程每 10 秒续期一次（重新 SET EX 30）。释放锁时用 Lua 脚本先验证 token 再 DEL，防止误删别人的锁。如果持有锁的实例 crash，30 秒后锁自动过期，其他实例可以获取锁接管消费。"

**追问："如果消费端 crash 了消息会丢吗？"**

> "不会。Redis Stream 有持久化机制——消息写入 Stream 后会持久化到 AOF/RDB。消费端使用消费者组（Consumer Group）消费，每条消息消费后需要手动 ACK。如果消费端 crash 没来得及 ACK，这条消息还在 Stream 的 PEL（Pending Entry List）中。重启后可以通过 `XREADGROUP` 从上次未 ACK 的位置继续消费，或者用 `XPENDING` + `XCLAIM` 把超时未 ACK 的消息转移给其他消费者。"

### Q4: 容器管理怎么做的？

#### 回答要点

> "容器管理核心是三件事：分配、扩缩容、重启。
>
>

> **分配**用最少进程数 + 加权随机算法。每个容器最多 20 个 Claude 进程，权重 = 21 - 当前进程数，进程越少权重越高。但不是严格选最少的，而是在最高优先级层内加权随机，避免多个请求同时涌入同一个'最空闲'的容器。还有操作日志分三层优先级：已重启完成的容器 > 空闲容器 > 正在操作的容器。

>

> **扩缩容**走 5 步流水线（清理旧容器 -> 创建新容器 -> 健康检查 -> 注册资源池 -> 统计结果），每步有断点恢复——如果服务重启导致扩容中断，定时任务检测超过 30 分钟的 EXECUTING 操作，从数据库恢复参数重新执行。Step 2 会计算 `remainingCount = 目标数 - 已创建数`，只创建差额部分，保证幂等。

>

> **重启**用滚动部署。每轮处理 30% 的空闲容器，每批最多 5 个，30 秒轮询间隔，最多 60 轮（30 分钟超时）。优先处理 IDLE 容器，OCCUPIED 容器等进程结束后再处理。保证至少 70% 容器在线。"

#### 可能的追问

**追问："容器怎么分配的？"**

> "最少进程数 + 加权随机。权重 = (MAX + 1) - processCount，进程数 0 的容器权重 21，进程数 19 的权重 2，进程数 20 的被排除。然后在最高优先级层内按权重随机选取。三层优先级：Tier 1 是已重启完成的容器（最高），Tier 2 是空闲容器，Tier 3 是正在操作中的容器（最低）。只在最高可用层内做加权随机。这避免了简单轮询不考虑负载的问题，也避免了严格最少导致请求集中到单个容器的问题。"

**追问："扩容时怎么不影响在线用户？"**

> "滚动部署。每轮只处理 30% 的空闲（IDLE）容器，保证至少 70% 的容器在线。优先处理 IDLE 容器（无进程运行），OCCUPIED 容器等进程结束后再处理。每批最多 5 个，30 秒轮询间隔，给容器恢复时间。每轮重新检查容器状态，确保不会重启正在使用的容器。还有 Redis 任务心跳（10 分钟 TTL），确保任务存活可追踪。"

**追问："容器挂了怎么发现？"**

> "带重试的健康检查 + 心跳超时。分配容器前会做健康检查（HTTP 请求 `/health/check/detail`），5 次重试，30 秒间隔。定时任务也会周期性探活所有容器，更新 `lastHealthCheckTime` 和 `lastHealthStatus`。如果健康检查失败，容器状态变为 `INVALID`，不会被分配。另外 `keepAlive` 定时任务调用 `deviceAPi.keepAlive(deviceId)` 防止容器被平台回收。"

### Q5: 你觉得这个项目最有技术含量的设计是什么？

#### 三个推荐方向

**方向一：多引擎统一封装架构（推荐指数最高）**

> "我觉得最有技术含量的是多引擎统一封装。这不是简单地用了个策略模式，而是三层抽象的系统性设计：
>
>
>
> 第一层策略模式解决'路由'问题——7 种引擎各有不同的容器管理逻辑，通过注册表动态分发。
>
> 第二层模板方法解决'复用'问题——7 种引擎的对话流程 80% 相同，抽象类固化骨架，子类只填差异化部分。
>
> 第三层管道模式解决'扩展'问题——20 多个前后置处理逻辑可插拔，互不影响。
>
>
>
> 这三层叠加的效果是：新增引擎从'改一堆 if-else + 拷贝整个对话流程'变成'写一个 Provider + 一个 ChatService 子类'，2 天完成接入。而且三层各自独立演进——管道加 Hook 不影响策略路由，策略加引擎不影响模板骨架。"

**方向二：多 Agent 协作的状态机设计**

> "最有技术含量的是协作状态机。多 Agent 协作本质上是一个分布式状态机——Todo、Task、Outbox 三层状态在并发环境下需要正确流转。
>
>
>
> 核心设计是 CAS + 事件驱动 + Outbox 三件套。CAS 保证并发状态安全，事件驱动实现状态自动收敛，Outbox 保证消息至少一次投递。这三个模式不是孤立使用的，而是组合在一起形成完整的可靠性保障。比如 Todo 完成触发 `onTodoCompleted` 事件 -> 事件处理器做级联调度和 Task 关闭检查 -> Task 关闭用 CAS 保证只有一个 Agent 能关闭 -> 关闭后通知相关方。整个链路在任何一步 crash 都能通过定时任务恢复。"

**方向三：容器扩容流水线的断点恢复**

> "最有技术含量的是容器扩容流水线的断点恢复机制。扩容是 5 步流水线，可能因服务重启中断。我们没有用复杂的工作流引擎，而是用'操作日志 + 幂等重放'实现断点恢复。
>
>
>
> 每次扩容生成唯一 `operationId`，每步执行状态记录在数据库。定时任务检测超过 30 分钟仍处于 EXECUTING 的操作，从日志恢复参数重新执行。关键是 Step 2（容器创建）会检查已创建的流水线记录，计算 `remainingCount = 目标数 - 已创建数`，只创建差额部分。这保证了幂等——即使重复执行也不会创建多余的容器。这个设计很简单但很实用，比引入 Airflow 等工作流引擎轻量得多。"

### Q6: 如果让你重新设计，你会做什么改进？

#### 回答策略

这个问题考察的是反思能力。不要说"没有改进空间"，但也不要全盘否定现有设计。推荐的回答策略是：先肯定现有设计的合理性，再提出 2-3 个具体的改进方向，说明原因和预期收益。

#### 建议提到的改进点

**改进 1：Hook 管道引入显式依赖管理**

> "目前的 Hook 管道通过 `@Order` 控制执行顺序，但 Hook 之间的依赖关系是隐式的——比如知识库注入 Hook 依赖查询重写 Hook 的输出，但这种依赖只体现在代码逻辑中，没有在框架层面声明。如果有人不小心改了 Order，可能导致知识库注入用到了未重写的查询。
>
>
>
> 改进方向是引入显式依赖声明，比如 `@DependsOn(QueryReWriteHook.class)`，框架在运行时自动计算拓扑排序。这样依赖关系一目了然，且框架可以检测循环依赖。"

**改进 2：A2A 消息投递引入幂等消费**

> "目前 Outbox 模式保证了'至少一次投递'，但消费端没有幂等保护。如果同一条消息因为重试被投递了两次，目标 Agent 可能会执行两次相同的任务。
>
>
>
> 改进方向是在消息中加 `messageId`，消费端维护一个已处理消息的去重表（Redis SET 或数据库唯一索引），处理前先检查是否已处理过。这样从'至少一次'升级为'恰好一次'语义。"

**改进 3：协作状态机引入状态机框架**

> "目前 Todo 和 Task 的状态转换散落在多个 Service 方法中，状态流转规则通过 CAS SQL 隐式表达。虽然功能正确，但状态转换的全貌不够直观——要看多个文件才能理清所有合法转换路径。
>
>
>
> 改进方向是引入轻量级状态机框架（如 Spring StateMachine 或自研），将状态、事件、转换规则集中声明。好处是状态转换规则可视化，新增状态或事件时不容易遗漏边界情况。当然这也有成本——状态机框架本身的复杂度，需要权衡。"

## 三、面试讲述技巧

### 3.1 STAR 法则应用

以"多引擎统一封装"为例：


|     |     |
| --- | --- |
| 要素  | 内容  |


| **Situation** | 平台需要支持 7 种 AI 引擎（Claude、Gemini、OpenClaw、Codex、Cursor 等），每种引擎的容器管理、对话流程、消息格式都不同。最初用 if-else 分支，代码维护困难，新增引擎需要改大量已有代码 |

| **Task** | 设计一套统一封装架构，让新引擎接入成本低、已有代码不被修改、各引擎逻辑相互隔离 |

| **Action** | 三层抽象设计：策略模式+注册表（解决路由）、模板方法（解决复用）、管道+过滤器（解决扩展）。策略通过 Spring 自动注册，模板固化 7 步骨架，管道用 try-catch 隔离 Hook |

| **Result** | 新引擎接入只需 2 天（写 1 个 Provider + 1 个 ChatService 子类），代码量 100-200 行。7 个引擎共用同一套锁、心跳、Stream 消费逻辑，公共代码只维护一份。支持灰度切流——通过 Apollo 配置切换引擎路由 |

| **滚动部署** | 每轮 30%，保证 70% 在线 | 展示高可用 |

| **协作规模** | 多 Agent 协作，CAS 并发安全 | 展示分布式能力 |

| **消息投递** | Outbox + 20 次重试 + 120 秒补偿 | 展示可靠性 |

**如何用数据增强说服力**：

> 不要只说"效率提高了"，要说"新引擎接入从改 5 个文件变成写 1 个类，2 天完成"。
>
> 不要只说"代码复用好"，要说"7 个引擎共用 1 套锁和心跳逻辑，子类平均只有 100 行代码"。
>
> 不要只说"很可靠"，要说"Outbox 模式保证至少一次投递，120 秒定时补偿 + 20 次重试上限"。

### 3.3 技术深度展示

**如何在回答中自然展示技术深度**：

1. **主动提到权衡**：不只说"用了 X"，还说"考虑过 Y，但因为 Z 选了 X"。比如"考虑过 Kafka 但选了 Redis Stream，因为会话级隔离需要大量 Key，Kafka Topic 太重"。

2. **提到失败场景和兜底**：不只说正常流程，还说"如果 crash 了怎么办"。比如"如果消费端 crash，Redis Stream 的 PEL 机制保证未 ACK 消息可重新消费"。

3. **提到边界条件**：比如"CAS 失败不重试而是跳过，因为说明已有其他线程在处理"、"DAG 用惰性求值而非预计算拓扑排序，因为支持动态添加 Todo 且天然防环"。

4. **从已知推导**：如果被问到没准备过的场景，从已有设计推导。比如被问"如何实现消息顺序性"——可以从"Redis Stream 单 Key 内消息天然有序"推导。

**避免背诵感的方法**：

- 用"我们当时考虑过..."而不是"最佳实践是..."
- 用"踩过的坑"引入设计决策："之前用 if-else，后来发现改一个分支可能影响其他分支，所以改成了策略模式"
- 准备 2-3 个"故事性"的细节：比如"枚举名全大写但数据库存驼峰，硬编码字符串导致查询为空，排查了一下午"

### 3.4 遇到不会的问题怎么办

**策略一：诚实承认 + 展示思考过程**

> "这个具体实现我没有直接经验，但如果让我设计，我会这样考虑：首先分析需求是强一致性还是最终一致性，如果是最终一致性，可以用 Outbox 模式..."

**策略二：从已知推导未知**

> "我没有用过 XX 框架，但我们项目中用 YY 解决了类似的问题。核心思路是 ZZ，我理解 XX 框架应该也是类似的设计理念..."

**策略三：提问澄清 + 分场景回答**

> "这个问题取决于具体场景。如果是低竞争场景，我会用 CAS 乐观锁；如果是高竞争场景，可能需要分布式锁。您指的是哪种场景？"

**绝对不要做的事**：

- 不要说"不知道"然后沉默
- 不要假装知道然后瞎编
- 不要说"这个我们没做过所以不关心"
