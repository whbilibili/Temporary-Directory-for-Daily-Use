# 全局规则索引

这是 Agent 的全局规则和约束的中央索引。所有规则都应该在这里定义或引用。

## 安全规则

### 工具禁令表（不可协商）

| 禁止 | 原因 | 替代方案 | 严重级别 |
|------|------|---------|---------|
| `repo_cat` | 经常挂死无响应 | mtcurl REST API | 🔴 CRITICAL |
| `& ... wait` 并行 | mtcurl 挂起时整个 exec 永久卡死 | 串行 + timeout=30 | 🔴 CRITICAL |
| `ciba_auth` | 沙箱不可靠 | CDP 浏览器 SSO | 🔴 CRITICAL |
| `web_search` | 沙箱网络不通 | catclaw-search | 🔴 CRITICAL |
| `browser` 访问内网 | 不可靠 | CDP 直连 port 9222 | 🔴 CRITICAL |
| `dx_search` | 沙箱超时 | daxiang-uid-lookup HTTP API | 🔴 CRITICAL |

### 约束分级

🔴 **红线**（绝对禁止，无例外）
- 禁止使用工具禁令表中的工具
- 禁止并行写同一个文件
- 禁止输出推断性结论
- 禁止删除操作未经用户确认

🟡 **护栏**（默认禁止，用户明确要求可放行）
- 默认禁止修改生产配置
- 默认禁止大批量删除（>100 条）
- 默认禁止修改关键业务逻辑

🟢 **建议**（推荐做法，可根据场景变通）
- 建议使用 async/await 而非 callback
- 建议先验证再输出
- 建议使用 TypeScript 进行类型检查

## 验证规则

### 自验证触发条件

满足**任一**条件，必须先验证再回答：

```
□ 结论含具体数值/金额/比例/状态码/错误码
□ 结论含字段名/表名/方法名
□ 结论含"应该"/"推断"/"大概"/"可能"/"我认为"
□ 知识库相似度 < 0.60
□ 结论涉及写操作（trigger/delete/update）
□ 用户问题含明确时间节点（今天/本周/昨天）
```

### 验证流程

1. **证伪优先**：先尝试推翻结论
   - 搜索是否存在与结论矛盾的证据
   - 找调用方代码确认实际行为
   - 反例不存在 → 结论成立

2. **低分拒答**：根据相似度判断
   - 相似度 < 0.45 → ⛔ 拒答
   - 相似度 0.45-0.60 → ⚠️ 触发自愈
   - 相似度 > 0.60 → ✅ 正常回答

3. **推断结论禁止输出**
   - ❌ "withhold_status=200 表示成功 ⚠️（推断）"
   - ✅ 不确定 → 查源码确认 → 确认后才输出

## 知识库规则

### 写入门控（importance 分级）

| 知识类型 | importance | 是否写入 | 说明 |
|---------|-----------|---------|------|
| 源码验证的业务公式 | 0.98 | ✅ | 最高可信度 |
| 状态机/调用链 | 0.92 | ✅ | 经过验证 |
| RDS 表结构 | 0.90 | ✅ | 数据库事实 |
| 工具踩坑经验 | 0.88 | ✅ | 最低写入门槛 |
| 推断/猜测 | — | ❌ | 禁止写入 |

### 自愈 SOP

触发条件：
- 相似度 < 60%
- 结论含数值
- 自己用了"推断/应该"

执行步骤：
1. 承认盲区："知识库未覆盖，正在查源码确认"
2. mtcurl 读源码（分块 ≤200 行）
3. 提取结论
4. vm-remember 写入（importance ≥ 0.95）
5. 回复附 "✅ 已自动存入知识库 key=xxx"

## 上下文隔离规则

### 子 Agent 分流阈值

| 条件 | 处理方式 |
|------|---------|
| 预估 ≤5 次 tool call | 主会话直接处理 |
| 预估 >5 次 tool call | spawn 子 agent |
| 预估 >30s 耗时 | spawn 子 agent |
| 批量文件操作 | spawn 子 agent，按需并行 |

### 并发安全

- 多子 agent 写同一个 DB → WAL 模式 + fcntl 文件锁
- 多子 agent 写同一个文件 → 禁止并行，串行执行
- 每个子 agent 独立进度文件 → 断点续传

## 错误→规则固化流程

当 Agent 犯错被用户纠正时：

1. **识别错误模式**
   - 什么条件下犯了什么错
   - 是工具选择错误、验证不足、还是约束遗漏

2. **提取为规则**
   - If X then Y / 禁止 Z
   - 明确触发条件和执行动作

3. **写入对应位置**
   - 工具相关 → MEMORY.md 对应章节
   - 行为相关 → SOUL.md
   - 全局禁令 → AGENTS.md（本文件）

4. **下次遇到自动触发规则**
   - 不再犯错
   - 记录规则生效的案例

## 规则演化

### 新规则来源

1. **用户纠正**（优先级最高）
   - 用户明确指出错误
   - 立即提取为规则

2. **自己踩坑**（优先级中）
   - Agent 自己发现的问题
   - 需要验证后才能固化

3. **理论推导**（优先级低）
   - 基于最佳实践推导
   - 需要实践验证

### 规则冲突处理

新规则与旧规则矛盾时，以**更近期、更具体的为准**。

示例：
- 旧规则：禁止使用 repo cat
- 新规则：repo cat 在文件 < 100 行时可用
- 结论：采用新规则，旧规则标记为 deprecated

### 规则退役

环境变化导致规则失效时：
1. 标记 `deprecated`
2. 记录失效原因
3. 不直接删除（保留历史）

示例：
```markdown
## ❌ DEPRECATED: 禁止使用 CIBA 认证

**失效时间**：2026-04-20
**原因**：沙箱环境已升级，CIBA 现在可靠
**替代方案**：可以使用 CIBA，但建议优先用 CDP 浏览器 SSO
```

### 规则回测

定期用历史 case 验证规则是否仍然有效：

```javascript
async function verifyRule(rule) {
  const historicalCases = await loadHistoricalCases();
  
  for (const case of historicalCases) {
    if (rule.matches(case.condition)) {
      const result = applyRule(rule, case);
      if (!result.success) {
        console.log('❌ 规则失效，需要调整');
        return false;
      }
    }
  }
  
  console.log('✅ 规则验证通过');
  return true;
}
```

## 持续改进闭环

```
犯错 → 识别模式 → 固化规则 → 回测验证 → 规则生效
                                  ↑                |
                                  └────── 反馈 ←───┘
```

这是驾驭工程最核心的价值：**把每一次错误变成系统的免疫力**。
