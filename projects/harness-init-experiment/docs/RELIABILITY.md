# Task Queue Service — 可靠性

## SLO（服务水平目标）

| 指标 | 目标 | 测量方式 | 说明 |
|------|------|---------|------|
| 可用性 | 99.9% | HTTP /health 探活 | API 层可响应 |
| 任务不丢失 | 100% | 入队任务必达终态 | completed 或 failed |
| 入队延迟 P99 | <50ms | API 响应时间 | ZADD 单次操作 |
| 调度延迟 | <5s | 入队到开始执行 | 取决于 poll interval |

## 错误处理模式

### 原则

1. **不吞掉错误** — 每个异常都有 Pino 结构化日志（包含 taskId）
2. **快速失败** — Zod 校验在 API 入口处拒绝非法请求，不传入队列
3. **可恢复 > 可重试 > 失败** — 按此优先级设计错误路径
4. **幂等** — 同一 taskId 重复入队产生相同效果

### 错误分类

| 类型 | 处理策略 | 示例 |
|------|---------|------|
| 参数校验错误 | 立即返回 400，不入队 | Zod 校验失败 |
| Redis 连接中断 | 指数退避重连，请求排队 | 网络抖动 |
| 任务执行失败 | retry()，retryCount++ | handler 抛异常 |
| 超过最大重试 | markFailed()，记录日志 | retryCount >= maxRetries |
| 未知异常 | 兜底 catch，结构化日志 | 非预期错误 |

### 关键 ID 日志规范

每条关键日志必须包含以下字段：

```
taskId: string     — 任务唯一标识
type: string       — 任务类型
priority: number   — 优先级
retryCount: number — 当前重试次数（仅失败场景）
```

## 故障恢复

### 恢复手册

| 故障场景 | 影响 | 恢复步骤 |
|---------|------|---------|
| Redis 宕机 | 无法入队/出队 | 1. 检查 Redis 状态 2. 恢复连接 3. 验证队列数据完整 |
| Scheduler 崩溃 | 任务堆积 | 1. 重启服务 2. 检查队列深度 3. 确认消费恢复 |
| 内存溢出 | 服务不响应 | 1. 重启 2. 检查并发数设置 3. 排查大 payload |

### 回滚策略

- 部署回滚: 切回上一版本 Docker 镜像
- 数据回滚: Redis 队列数据持久化（RDB/AOF），恢复快照
- 配置回滚: 环境变量回退，重启服务
